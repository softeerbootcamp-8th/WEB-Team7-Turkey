# Flyway 마이그레이션 그라운드룰

## 1. 파일명 규칙

마이그레이션 파일은 다음 형식을 사용한다.

```text
V{yyyyMMddHHmmss}__{description}.sql
```

예시:

```text
V20260723143000__create_delivery_order_table.sql
V20260724101530__add_status_to_delivery_order.sql
```

- 버전은 타임스탬프를 사용한다.
- 설명은 소문자 스네이크 케이스로 작성한다.
- `update`, `fix`처럼 변경 내용을 알 수 없는 이름은 사용하지 않는다.

## 2. 파일 작성 원칙

- 파일 하나는 하나의 논리적 변경 목적을 가진다.
- 동일 테이블 생성에 필요한 기본 제약조건과 인덱스는 같은 파일에 포함할 수 있다.
- DDL과 초기 데이터 삽입은 가능하면 분리한다.

## 3. 기존 파일 수정 금지

한 번 `main`에 머지되었거나 다른 환경에서 실행된 마이그레이션 파일은 수정하지 않는다.

스키마를 변경하거나 이전 변경을 되돌려야 하는 경우 기존 파일을 고치지 않고 새로운 마이그레이션 파일을 추가한다.

```text
기존 파일 수정 X
새로운 마이그레이션 추가 O
```

## 4. 작업 및 머지 규칙

마이그레이션 파일을 포함한 PR은 머지 전에 최신 `main`을 반영하고 버전 충돌 여부를 확인한다.

PR을 올리기 전에 다음을 확인한다.

- 로컬에서 `flyway migrate`가 성공하는가
- 애플리케이션이 정상 실행되는가
- 기존 마이그레이션 파일을 수정하지 않았는가
- 파일명과 버전이 다른 파일과 충돌하지 않는가

## 5. 실행 정책

- 스키마 변경은 Flyway 마이그레이션 파일로만 수행한다.
- GUI나 콘솔에서 스키마를 직접 수정하지 않는다.
- 운영 환경에서는 `flyway clean`을 비활성화한다.

```properties
spring.flyway.clean-disabled=true
```

운영 데이터가 존재하거나 대량 데이터 변경이 필요한 경우에는 컬럼 추가, 데이터 보정, 제약조건 추가를 단계적으로 나눈다.
