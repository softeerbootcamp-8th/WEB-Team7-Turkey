## 무릎·병목 판정 (완전한 곡선 기준)

**무릎은 Hikari 풀 크기 부근(~10~15 VU)이다.** 근거가 세 신호로 일치한다:

1. **처리량이 25 VU 부터 평탄**하다 — 25 VU 982 req/s, 200 VU 1,012 req/s 로 **거의 안 늘고**
   ~1,000~1,100 req/s(≈510 cyc/s)에서 천장. VU 를 8배 올려도 처리량은 그대로다.
2. **지연은 VU 에 선형 증가**(p95 41→253ms), **Hikari 대기도 선형**(15→190). 처리량은 그대로인데
   큐만 깊어지고 지연만 커지는 것 — 닫힌 모델 포화의 정의다.
3. **Hikari 활성이 25 VU 부터 10(만석) 고정.** 풀이 25 VU 에서 이미 꽉 찼고, 그 위 VU 는 전부
   대기열로 간다. 무릎은 활성이 10 에 닿는 지점, 즉 **VU ≈ 풀 크기(10) + 인플라이트 여유**다.

**병목은 HikariCP 풀(10)이고, CPU 가 아니다.** 앱 CPU 최대 165%·MySQL 평균 123%로 **2코어 cap(200%)에
여유가 있다.** 즉 CPU 는 더 일할 수 있는데 커넥션 10개가 동시 처리량을 묶고 있다.

> **실행 가능한 결론**: 이 워크로드에서 **풀(10)을 키우면 처리량이 실제로 늘 여지가 크다** — CPU 가
> 놀고 있기 때문이다. 이는 콜드 런(앱 CPU 219% cap)에서 "풀 확대 무의미"라던 판정과 정반대다.
> 풀 크기 비교 실험이 다음 후보다(단 스킬 원칙 3대로 **웜 상태에서** 비교할 것). MySQL 은 문장/요청
> ~18.5, 실행 스레드 최대 11, CPU 평균 123%라 풀을 어느 정도 키워도 받아 줄 여력이 있어 보인다.

## 새로 관찰된 것 (변함없음)

- **MySQL 데드락 (warm2 create 실패 2건 = 0.0005%; warm 컨테이너 누적 8건, 전부 `insert into
  delivery_order`)**: **미해결**. 이번 작업(name 태그·힙·시드)은 앱 로직을 안 건드려 그대로 재현된다.
  **원인 확정**(재현 버스트에서 `SHOW ENGINE INNODB STATUS` LATEST DETECTED DEADLOCK 캡처, 2026-08-17
  12:21:44): 서로 다른 두 고객(customer_id 988·989)의 `insert into delivery_order` 가 유니크 인덱스
  **`uk_delivery_active_customer` 의 같은 gap**(active_customer_id=990 레코드 앞)에서 충돌했다. 양쪽
  모두 `HOLDS ... lock mode S locks gap before rec`(중복검사 공유 gap 락) → `WAITING ... X ... insert
  intention waiting`(삽입 의도 락)으로 교차 대기 → InnoDB 가 Tx-2 롤백. RR 격리의 전형적 "유니크
  인덱스 동시 INSERT" 데드락이며, 포인트 잠금은 무관(락이 전부 이 인덱스에 잡힘, point 테이블 0건).
  active_customer_id 가 STORED 생성 컬럼(진행 중=customer_id, 종료=NULL)이라 non-null 영역이 극히
  희소(실측 3/419,891)해 gap 이 크고 인접 고객(988·989·990)의 insert 가 같은 gap 에 몰리는 것이 원인.
  **대응**: create 는 `requestKey` 멱등키가 있어 **앱단 데드락 재시도(`CannotAcquireLockException`)가
  가장 안전·저비용** / READ COMMITTED(gap 락 제거, 영향 범위 큼) / 락 순서·인덱스 재구조화.
  **전체 분석(덤프 해독·gap 락 원리·대응 비교)**: GitHub Discussion #550
  (https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/discussions/550).
- **앱 컨테이너 RSS 922 MiB / 1 GiB** — 512m 힙 + 비힙이 1 GiB cap 에 근접(여유 ~100 MiB). 배포
  사이징에서 확인 필요(힙이 아니라 총 RSS 기준).
