## 목적

`2026-08-14-...hikari10-vs-hikari30.md`(위치 전송 2.4초 간격)는 커넥션 경합이 없어 Hikari
풀 크기 비교가 무의미했다. 이 실험은 **원래 강도(0.5초 간격)**로 되돌려 Hikari 10 vs 30을
다시 잰다. 또한 "저번 비슷한 부하에서 CP가 아니라 DB CPU 처리량 부족이 병목이었다"는 가설을
앱/MySQL 컨테이너 CPU 배분으로 직접 확인한다. 웜업 절차(`.claude/skills/loadtest/SKILL.md`
「원칙 3」)를 그대로 따랐고, DURATION은 웜업·측정 모두 180초로 유지했다.

## 절차

1. 설정별로 앱 재기동(`-Xms=-Xmx=512m` 고정, `-Djdk.tracePinnedThreads=full` 추가 — 가상
   스레드 핀 여부 직접 확인용) → 재시드 → 웜업(180s, 0.5초 간격, 결과 버림) → 재시드 →
   측정(180s, 0.5초 간격)
2. 컨테이너 CPU 샘플러(`sample-stats.sh`)를 매 설정마다 새로 띄워 전 구간 동행시켰다(이전
   실험에서 중간에 죽었던 문제를 `disown`으로 방지).

## 웜업 확인

| 설정 | 측정 구간 JIT 컴파일 부하(전체/1단) |
|---|---|
| Hikari=10 | 8.1 / 5.4 ms/s |
| Hikari=30 | 29.7 / 17.8 ms/s |

둘 다 콜드 스타트 기준(수천 ms/s)보다 현저히 낮다 — 웜업 성립.

## 결과 — k6 자체 집계(가장 신뢰할 수 있는 값)

k6 터미널 summary는 이 스크립트가 보낸 요청만 집계하므로, 같은 앱을 쓰는 다른 호출자의
트래픽과 섞이지 않는다.

| 항목 | Hikari=10 | Hikari=30 |
|---|---|---|
| testid | `mixed-realistic-hikari10-0p5s-20260814-123135` | `mixed-realistic-hikari30-0p5s-20260814-135743` |
| 총 요청 | 267,157건 | 264,528건 |
| **p95** | **28.64 ms** | **51.04 ms** |
| **p99** | 187.94 ms | 191.21 ms |
| **avg** | **11.33 ms** | **16.45 ms** |
| 실패율 | 0.00% | 0.00% |

p95·avg는 Hikari=10이 낫고, p99는 사실상 동률이다. **풀을 키운다고 나아지지 않았다** — 오히려
약간 나빠지는 방향이다.

## 컨테이너 CPU 배분 — "DB CPU가 병목"이었나?

| 항목 | Hikari=10(1단) | Hikari=30(1단) |
|---|---|---|
| 앱 CPU 평균/최대 | 77% / **198%**(2코어 만석) | 81% / **196%**(2코어 만석) |
| MySQL CPU 평균/최대 | 42% / 75% | 41% / 84% |
| Redis CPU 평균/최대 | 5% / 7% | 5% / 9% |
| Hikari 활성 최대 | 4 | 30 |
| Hikari 대기 최대 | 0 | 1 |
| 힙 사용 최대 / 상한 | 473 / 512 MiB | 446 / 512 MiB |

**앱 CPU가 두 설정 다 2코어를 거의 다 쓴다(196~198%)인 반면 MySQL은 최대치도 75~84%로 여유가
있다.** 즉 이 부하에서 병목은 **DB CPU가 아니라 앱 CPU**다 — "저번엔 DB CPU 부족이 병목이었다"는
회상과 반대다(과거 `README.md`의 단일 엔드포인트 실험에서도 같은 결론이었다 — "Hikari 대기는
결과지 원인이 아니다, 앱 CPU가 이미 포화라 병목"). Hikari 대기 큐도 두 설정 다 거의 0이라
**커넥션 풀 자체도 병목이 아니다.**

**힙도 문제없었다** — "VU를 늘리면 힙이 부족할 것 같다"던 우려와 달리, 0.5초 간격(2.4초의
약 5배 요청량)에서도 힙 사용은 446~473 MiB로 512 MiB 상한 안에 여유 있게 들어왔다. Evacuation
Failure/Full GC가 간헐적으로 있었지만(다른 실험에서도 봤던 수준) OOM 근처에는 전혀 안 갔다.

## 참고: 측정 구간에 섞인 외부 트래픽(Hikari=30 쪽 원본에 남음)

Hikari=30 측정 런의 **전체 구간(Micrometer 집계) 표**에는 `5xx 응답 509건`, `Hikari 대기
최대 708`, `서버측 평균 처리시간 581ms` 같은 수치가 남아 있다 — 겉보기엔 심각해 보이지만
**우리 시나리오가 만든 게 아니다.**

- 코드를 추적한 결과 이 500은 `DeliveryService.cancelDelivery()`(고객이 배송요청을 직접
  취소하는 API, `POST /api/customer/deliveries/{id}/cancel`)가 운임 스냅샷 없는 주문을
  취소할 때 던지는 `BusinessException(500)` 하나뿐이다(코드에 이 메시지·상태 조합이 유일).
- **`mixed-realistic.js`는 이 취소 엔드포인트를 호출하지 않는다.** 즉 이 500들은 같은 앱
  인스턴스를 동시에 쓴 **다른 호출자의 트래픽**이 우리 측정 구간(Prometheus 는 testid 로
  안 갈라진 전역 지표라 시간만 겹치면 섞인다)에 우연히 들어온 것이다.
- GC 로그(정지 5~140ms, 특이사항 없음)·InnoDB 락 지표(`row_lock_current_waits`=0 전 구간)·
  핀 스레드 로그(0건) 전부 확인해 우리 쪽 원인 가능성을 지웠다.
- k6 자체 집계(위 표)는 이 오염과 무관하다 — k6는 자기가 보낸 요청만 잰다. **그래서 이번
  비교는 k6 집계·1단(steady-state) 수치를 기준으로 삼았다.**
- 별개로: `cancelDelivery`가 스냅샷 없는 주문에서 500을 내는 경로 자체는 실제 버그로 보인다
  (`orderId`/`deliveryId` 형태로 보아 우리 시드 데이터가 아닌 다른 데이터셋 소유로 추정) —
  이 로드테스트 범위 밖이라 별도 이슈로 확인이 필요하다.

## 결론

1. **Hikari 10 vs 30: 이 부하(0.5초 간격, 700 BUSY 라이더)에서도 30이 10보다 낫다는 근거가
   없다.** p95·avg는 오히려 10이 낫다. 병목이 커넥션 풀이 아니므로 풀을 키워도 득이 없다.
2. **병목은 DB CPU가 아니라 앱 CPU다**(2코어 거의 만석, MySQL은 최대 84%로 여유). "DB CPU가
   부족했다"는 회상은 이번 데이터로는 재현되지 않았다 — 과거 위치갱신 단일 엔드포인트
   실험과 같은 결론(앱 CPU 포화)이다.
3. **힙은 이 부하에서 부족하지 않았다**(512MiB 중 최대 473MiB 사용).

앱 CPU 2코어가 실제 천장이므로, 다음으로 볼 만한 건 **SerialGC vs G1GC**(원래 계획한 두 번째
실험)이거나 **CPU 코어 배분 자체**(app cpuset을 2코어보다 늘려보는 실험)일 것 같다.
