# 라이더 위치 갱신 — VU 100→1000 계단 램프

- **목적**: 라이더가 위치를 보낼 때 병목이 어디인지 판정한다.
- **대상**: `POST /api/rider/location` (BUSY 라이더 전용 상시 쓰기 경로)
- **testid**: `location-stair-20260811-204322` · 측정 구간 epoch `1786448663~1786449673`(1010초)
- **raw 시계열**: `2026-08-11-location-stair-20260811-204322-raw.json`
  (5초 간격 15계열 + Grafana 패널 쿼리 138개)

## 부하 패턴

VU 100 → 1000 을 100 단위 10단 계단. 각 단은 전이 10초 + **유지 90초**다 — 유지 구간이 90초여야
Prometheus 15초 스크레이프가 `increase()`/`rate()` 창을 채워 단계별 서버측 지표를 따로 뽑을 수 있다.

**라이더와 VU 는 1:1**(계정 1000개, `RIDER_COUNT=1000`). 계정을 공유하면 같은 행·같은 Redis 키만
두드려 버퍼풀 지역성이 비현실적으로 유리해진다. 요청당 왕복 수가 전 단계에서 MySQL 13.0 /
Redis 5.0 으로 이론값에 붙어 있는 것이 공유가 없었다는 증거다.

```bash
# 시드는 @n=1000 으로 덮어 돌렸다(파일 기본값은 100, 재귀 CTE 상한도 함께 올려야 한다).
cd backend
(echo "SET SESSION cte_max_recursion_depth = 5000;"; \
 sed 's/^SET @n := 100;/SET @n := 1000;/' scripts/seed-loadtest-riders.sql) \
  | docker compose exec -T mysql mysql -uturkey -plocal turkey

docker compose run --rm -e BASE_URL=http://app:8080 \
  -e RIDER_COUNT=1000 -e MAX_VU=1000 -e STEPS=10 \
  k6 run --tag testid=location-stair-20260811-204322 /scripts/local/rider-location-update.js
```

### 환경 — 기존 실측과 직접 비교 불가

앱 컨테이너는 종전과 같은 **1GiB / 2 vCPU** 인데, 이 런에서는 **MySQL·Redis 컨테이너에도 각
2 CPU / 1 GiB 제한이 새로 걸려 있다**. `loadtest/README.md` 의 60 VU·500 VU 실측은 DB·Redis 에
제한이 없던 상태라 **같은 축에 놓고 회귀 비교하면 안 된다.** 가상 스레드는 양쪽 모두 켜져 있다
(`spring.threads.virtual.enabled=true`).

## 병목 판정

**체제가 두 개다. 100~600 VU 는 앱 CPU, 700 VU 이상은 SerialGC 다.**

### 1) 포화점은 100 VU 아래다 — 계단 전 구간이 이미 포화 이후

처리량이 **한 번도 늘지 않는다**(4,402 → 1,973 단조 감소). 100 VU 에서 이미 앱 CPU 가
203%(2코어 만석)이고, 무릎은 그보다 아래에 있다. 이전 실측의 무릎 추정(28 VU)과 방향이 같다.
따라서 이 런은 **무릎 측정이 아니라 포화 이후 열화 곡선**이다.

지연은 동시성에 거의 정비례한다(p95 43.7ms @100VU → 435.8ms @1000VU, 약 10배). 리틀의 법칙이
정확히 성립한다 — `처리량 × 서버측 평균`이 VU 수와 일치한다:

| | 100 VU | 500 VU | 1000 VU |
|---|---|---|---|
| 처리량 × 서버측 평균 | 4,402 × 0.0222 = **97.5** | 4,017 × 0.1237 = **496.9** | 1,973 × 0.5035 = **993.4** |

즉 **동시성 전량이 앱 안에 대기로 쌓인다.** 늘어난 지연은 전부 큐 대기이고 처리 능력은 고정이다.

### 2) 100~600 VU: 앱 CPU 가 천장

- 앱 CPU 가 203%/200% 로 **제한을 100% 채운다**. MySQL 71%, Redis 6% — 둘 다 포화 아님.
- 요청당 왕복 수가 전 단계에서 **MySQL 13.0 / Redis 5.0 고정**이다. 부하가 10배가 돼도 일의 양이
  요청당 그대로라는 뜻 — 락 경쟁·재시도·N+1 폭발 같은 게 없다.
- 요청당 CPU: 2코어 ÷ 4,402 rps = **0.45 ms/요청**. 이 중 MySQL 왕복 13회가 큰 몫이고,
  그 13회 중 **10회가 트랜잭션 부대비용**(SET 8 + COMMIT 2)이다(기존 실측, 이 런에서도 동일).

### 3) 700 VU 이상: SerialGC 가 CPU 를 빼앗는다

여기서 성격이 바뀐다. **앱 CPU 가 오히려 떨어지는데**(203% → 168%) 처리량도 같이 무너진다
(3,644 → 1,973). 자원이 남는데 못 쓰는 상태다. 원인은 GC 다:

- GC 정지가 90초 중 **19.85초(22%) → 46.18초(51%)** 로 폭발한다.
- **GC 횟수는 오히려 줄고**(941 → 532) **1회 정지가 21ms → 87ms 로 4배** 길어진다.
- 1GiB 컨테이너라 JVM 이 **SerialGC**(단일 스레드)를 고른다. 정지 중에는 코어 1개만 도니까
  CPU 가 200% 를 못 채운다 — 관측된 168% 가 그 산술과 맞는다.
- 왜 동시성이 늘면 힙이 아픈가: 대기 중인 요청 1000건이 각자 요청·응답 객체를 붙잡고 있어
  **살아 있는 객체가 동시성에 비례**한다. 힙 상한이 248 MiB 인데 사용량이 191~239 MiB 로 상시
  거의 꽉 차 있다.

### 4) Hikari 대기(988)는 원인이 아니라 결과다

Hikari 활성은 전 구간 **10(풀 상한 고정)**, 대기는 `VU − 11` 로 정확히 따라온다. 즉 **동시성이
전부 커넥션 획득 앞에 줄을 선다** — 겉보기엔 커넥션 풀이 병목이다. 그런데 그 앞에서 앱 CPU 가
이미 100% 다. 풀을 키워도 **더 돌릴 CPU 가 없다.** 예측: 풀을 늘리면 동시에 CPU 를 다투는
요청만 늘어 처리량은 그대로거나 줄고 지연은 나빠진다.

같은 종류의 오독으로 과거에 "커넥션 풀이 병목"이라고 결론 냈다가 철회한 이력이 있다
(`loadtest/README.md` 「측정 이력」). **확증하려면 `maximum-pool-size` 를 바꿔 다시 재야 한다 —
이 런으로는 단정하지 않는다.** 남겨 둔 유일한 열린 항목이다.

### 5) 과부하는 실패가 아니라 지연으로 나온다

1000 VU 에서도 **실패 0건 · 5xx 0건 · 드롭 0건**이다. 최댓값이 2.65초까지 늘어날 뿐이다.
이 구간의 사용자 경험은 서버가 아니라 **클라이언트 타임아웃 설정**이 좌우한다.

## 실사용 환산 (#391 미결 항목에 대한 답)

지속 가능한 처리량은 **약 4,400 req/s**(피크 4,534)다. BUSY 위치 전송은 최소 0.5초 간격
제약이므로 라이더당 **최악 2 req/s**:

| 라이더당 전송 | 동시 BUSY 라이더 수용치 |
|---|---|
| 2 req/s (최악, 0.5초 간격 연속) | 약 **2,200명** |
| 0.2 req/s (5초 주기 상당) | 약 **22,000명** |

단일 인스턴스(1GiB/2vCPU)에서 이 수치다. **MVP 규모와 자릿수가 달라 지금 고칠 이유는 없다.**
CLAUDE.md 미결 항목 「BUSY 위치 전송 서버 요청량 영향 미확인(#391)」은 이 값으로 닫을 수 있다.

## 개선 방향 (필요해지면)

우선순위대로. 앞의 둘이 이 API 전용이 아니라 **모든 라이더 API 공통**이라는 점이 중요하다.

1. **GC** — 700 VU 이상의 붕괴는 전적으로 이것이다. 1GiB → 2GiB 로 올려 G1 이 선택되게 하거나
   `-XX:+UseG1GC` 를 명시하면 정지가 병렬화된다. **사이징을 올리기 전에 이 항목을 먼저 본다.**
2. **요청당 MySQL 왕복 13회 중 10회가 트랜잭션 부대비용** — ① 인터셉터의 member·rider_profile
   조회를 한 쿼리로 합치기 ② 커넥션 속성(`useLocalSessionState` 등)으로 SET 왕복 줄이기.
3. **스케일 아웃이 그대로 먹힌다** — 병목이 앱 CPU 이고 MySQL 은 71%, Redis 는 6% 다.
   인스턴스를 늘리는 쪽이 가장 단순하다(다만 MySQL 이 다음 천장이 된다: 71% × 인스턴스 2대면 초과).

## 무효 처리한 런

`location-stair-20260811-201929`(같은 조건 1차 시도)는 **VU 400 이후 전부 무효**다. 측정 중에
사람이 같은 로컬 스택에서 ① MySQL·Redis 컨테이너 재시작(20:26:28) ② 앱 컨테이너 재시작(20:28:27)
③ 별도 60 VU 부하 추가(20:29:47~20:31:25)를 했다. 데이터에 그대로 찍혔다 — 앱 rps 4,127 → 4,
MySQL qps 53,820 → 2, Hikari 활성 10 → 0, status=0 즉시 실패 30만 건. 깨끗한 100~300 VU 구간은
이 런의 같은 단계와 일치했다(피크 4,484 / 4,274 / 4,261 vs 4,534 / 4,410 / 4,297).

**재측정 시 실행 전에 활성 런을 확인한다:**

```bash
curl -s --get 'localhost:9099/api/v1/query' --data-urlencode 'query=sum(k6_vus)'
# 0 이 아니면 누군가 돌리는 중이다 — 시작하지 않는다
```

이 런은 사후 유효성 게이트도 통과했다: 앱·MySQL `uptime` 단조증가(재시작 없음), 램프 구간
`sum(k6_vus)` 가 내 testid 의 VU 와 완전히 일치(외부 부하 없음).
