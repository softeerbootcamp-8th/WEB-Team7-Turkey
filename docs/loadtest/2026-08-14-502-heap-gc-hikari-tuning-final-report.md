# #502 힙·GC·Hikari 튜닝 실험 종합 보고서

이틀(2026-08-13~14)에 걸친 실험을 정리한다. **가장 큰 소득은 특정 튜닝값이 아니라
측정 방법론이었다** — 콜드 스타트가 힙·GC·Hikari 어떤 옵션 차이보다 몇 배 더 큰 잡음을
만든다는 걸 발견했고, 그걸 통제하는 절차(웜업)를 세운 뒤에야 마지막 실험에서 처음으로
믿을 만한 신호를 얻었다.

## 요약

| 질문 | 답 |
|---|---|
| 힙을 `-Xms=-Xmx`로 고정하면 램프 구간 스파이크가 없어지나? | **처음엔 그래 보였으나, 콜드/웜 조건이 안 맞은 비교였다(재검증 필요, 아래 1장)** |
| IHOP 30/45/60 중 뭐가 나은가? | **판단 불가 — 콜드 스타트 잡음이 신호를 덮었다** |
| Hikari 10 vs 30? | **가벼운 부하에선 차이 없음. 무거운 부하에선 30이 p99를 21% 낮추지만 GC 정지 비율을 올린다**(4장) |
| G1 vs SerialGC? | **VU 2000(가벼움)에선 차이 없음. VU 2100(무거움)에선 SerialGC의 GC 정지 비율이 G1의 2배 이상**(4장) |
| 지금 서버가 견딜 수 있는 VU 상한은? | **정밀 측정 안 함. 앱 CPU(2코어)가 유일한 병목이고, 평균 기준 아직 여유는 있다(3장)** |

## 1. 발단 — exp3의 램프 구간 스파이크, 그리고 뒤집힌 첫 결론

`-XX:MaxRAMPercentage=50`(동적 힙, 작게 시작해 부하 아래서 커짐) 조합(exp3)이 램프 구간에서
p95 1,525ms·Hikari 대기 877까지 튀었다. `-Xms=-Xmx=512m`(고정 힙)로 바꾼 exp4는 같은 구간에서
p95 798ms·Hikari 대기 0으로 훨씬 나아 보였다 — **"힙을 고정하면 리사이징 중 GC/커밋 정지가
없어져 램프 스파이크가 사라진다"**는 결론을 내리고 GC 로그로 근거까지 확인했다(exp3는 램프
구간 3초 만에 힙 커밋이 154M→512M로 뛰며 초당 8.3회 GC가 몰렸고, exp4는 초당 3회 수준이었다).

**그런데 이 결론은 나중에 재검증이 필요한 것으로 드러났다**(2장). exp4가 우연히 **이미
데워진 컨테이너**(직전 오염된 런을 4분간 돌린 뒤 이어서 잰 것)였고, exp3는 **콜드 스타트**였다
— 비교 자체가 공정하지 않았다. 힙 고정의 효과 자체를 부정하는 건 아니지만, 이 특정 비교로는
증명되지 않는다.

## 2. 방법론적 전환점 — 콜드 스타트가 진짜 지배 변수였다

IHOP 30/45/60을 힙 고정 상태에서 스윕했다. 1회차에서 IHOP=30이 가장 좋아 보였는데(exp4와
같은 값), 2회차에 **같은 설정(IHOP=30)을 한 번 더 돌렸을 뿐인데** 램프 구간 p95가
**798ms → 3,173ms**로 4배 벌어졌다.

원인을 GC 로그·`jvm_compilation_time_ms_total`로 추적했다:

| | 웜업된 런(exp4) | 콜드 런(IHOP 스윕 전체) |
|---|---|---|
| 측정 구간 JIT 컴파일 부하 | 3,111 ms(누적) | 19,995~27,227 ms(누적) |
| JVM uptime(측정 시작 시점) | 986초 | 78~245초 |

**컨테이너를 새로 띄운 직후엔 JIT 컴파일러가 코어 2개를 요청 처리 스레드와 나눠 써야 한다.**
이 경쟁이 힙·GC·Hikari 어떤 옵션을 바꾸든 그 차이보다 몇 배 더 크게 결과를 흔든다. exp4가
"좋았던" 것도, IHOP 스윕이 "들쭉날쭉했던" 것도 전부 이 콜드/웜 차이로 설명됐다.

**대응**: `.claude/skills/loadtest/SKILL.md`에 「원칙 3」과 웜업 절차를 추가했다 — 설정을
바꿀 때마다 (1) 재기동 (2) 재시드 (3) 같은 시나리오로 최소 90초(이후 실험은 180초 사용)
웜업, 결과 버림 (4) 재시드 (5) 실제 측정 (6) `JIT 컴파일 부하`(신설 지표, `collect.py`)가
낮은지 확인. 콜드 런과 웜 런을 같은 비교표에 섞지 않는다.

## 3. 병목 소재 확인 — DB CPU가 아니라 앱 CPU(2코어)

"저번엔 DB CPU 부족이 병목이었다"는 회상을 컨테이너 CPU 배분으로 직접 확인했다(0.5초 간격,
웜업 완료 후):

| | Hikari=10 | Hikari=30 |
|---|---|---|
| 앱 CPU 평균/최대(2코어=200%) | 77%/**198%** | 81%/**196%** |
| MySQL CPU 평균/최대(2코어=200%) | 42%/75% | 41%/84% |

**앱 CPU가 두 설정 다 거의 만석인 반면 MySQL은 최대치도 84%로 여유가 있다** — 병목은 DB가
아니라 앱 CPU 2코어였다(과거 `backend/loadtest/README.md`의 단일 엔드포인트 실험과 같은
결론). VU 상한 추정은 이 CPU 여유(평균 74~81% vs 피크 196~198%)를 근거로 2,500~3,000 부근을
잠정 제시했으나 실측은 안 했다.

**steady-state CPU 피크 원인도 규명했다**: 1초 해상도 샘플링 + GC 로그 대조로, SerialGC에서
힙이 365M→421M로 차오르는 약 7초 동안 단일 스레드 Young GC가 초당 1~2회 연달아 발생하며
개별 정지 시간이 5ms→67.5ms로 늘어나는 걸 직접 확인했다(G1에서는 같은 피크가 GC·DB 어느
쪽과도 안 맞아 원인 불명으로 남겼다 — 컬렉터에 따라 원인이 다를 수 있다는 뜻).

## 4. 실제 신호 — 부하를 무겁게 만든 뒤에야 나온 결론

가벼운 부하(위치 전송 2.4초 간격, Hikari 대기 0~10)에서는 Hikari 10 vs 30·IHOP·GC 알고리즘
어느 것도 차이가 안 났다 — 커넥션 풀도 GC도 압박을 받은 적이 없었기 때문이다(GC 정지 비율
최대 1.5%, README의 "SerialGC 붕괴" 사례 51%의 30분의 1 수준).

시나리오를 실사용에 가깝게 무겁게 바꿨다(BUSY 라이더가 `ASSIGNED→...→COMPLETED`까지 실제로
진행시킴, AVAILABLE 라이더 500명이 콜 목록을 닫힌 모델로 두드림, VU 2,100). 그 결과:

| | G1·Hikari10(기준) | G1·Hikari30 | SerialGC·Hikari10 |
|---|---|---|---|
| p99(k6 정본) | 629ms | **496ms** | 499ms |
| avg(k6 정본) | **146ms** | 203ms | 199ms |
| GC 정지 비율 | **4.7%** | 7.0% | **10.1%** |
| 힙 할당률 | 813 MiB/s | 1,013 MiB/s | 1,123 MiB/s |

- **GC 알고리즘**: 이 규모에서 처음으로 SerialGC가 뚜렷이 나쁘다는 신호가 나왔다(정지 비율
  2배 이상). 아직 지연에 직결되진 않았지만, 부하를 더 올리면 README의 "SerialGC 붕괴" 지점이
  이 근처에 있을 가능성이 높다.
- **Hikari 풀 크기**: 30이 p99를 21% 낮췄지만 GC 정지 비율을 올렸다. 메커니즘을 힙 할당률로
  확인했다 — 풀이 클수록 동시에 "진짜 일하는" 요청 수가 늘어 할당률이 오르고(813→1,013
  MiB/s), G1이 Young GC를 더 자주 돌려야 한다. 대신 **커넥션 대기 큐에서 줄서던 지연이
  줄어드니 p99는 개선된다** — 풀 크기는 "커넥션 대기 지연을 GC 정지 시간으로 바꿔치기"하는
  트레이드오프다. 할당률 자체는 힙 크기(512MB)와 무관하다 — Eden이 초당 4~5번 400M대까지
  찼다가 Young GC로 비워지는 게 반복되며 누적 처리량이 힙 크기를 넘어서는 것뿐이다(GC 로그로
  직접 확인, 힙이 512MB를 넘은 적은 없다).

## 5. 도구·시드 결함 (부수적으로 발견·수정)

실험 도중 드러난, 이 실험 자체와는 별개인 실제 버그들:

- **`GlobalExceptionHandler`가 문제였던 게 아니라 시드가 문제였다**: `order_fare_snapshot`이
  없는 상태로 콜 목록·취소·전이·완료 API를 부르면 전부 400/500으로 죽는다 — 이 패턴을
  **세 번** 만났다(초기 데이터 오염, `lt_c` 주문 스냅샷 누락, 이번 세션에서 재확인).
- **`lt_r`(BUSY 라이더)에 완료 정산용 `point_wallet`이 없었다** — `/complete`가 실패.
- **재시드 자체가 FK 위반으로 깨졌다** — `rider_settlement`·`delivery_proof`·라이더 쪽
  `point_transaction`(SETTLEMENT, `delivery_order_id` NULL)을 정리 순서에서 빠뜨렸다.
- **k6가 URL(배송ID·좌표 포함)별로 별도 시계열을 만들어** 표본 1~2개짜리 시리즈의 우연한
  실패가 "100% 실패"로 보였다 — `tags.name` 고정으로 해결.
- **`collect.py`의 실패율 쿼리 자체가 구조적으로 틀려 있었다**(`max(k6_http_req_failed_rate)`가
  상태코드별로 이미 쪼개진 시리즈에 `max()`를 거는 꼴) — 분자·분모 각각 `sum()` 후 나누는
  진짜 비율로 고쳤다(실패 0건일 때 빈 값이 나오는 엣지 케이스도 `or vector(0)`로 보강).
- **Grafana MySQL 대시보드의 CPU/Load 패널이 처음부터 빈 채였다** — `$host` 변수가
  mysqld_exporter의 instance를 가리키는데 실제 CPU 데이터는 node_exporter(다른 instance)에서
  나온다. `fetch-dashboards.sh`에 mysql 전용 패치를 추가해 고쳤다(다른 대시보드는 안 건드림).
- **Dockerfile에 GC 알고리즘이 하드코딩(`-XX:+UseG1GC`)돼 있어 SerialGC 비교 자체가
  불가능했다** — `JAVA_GC_ALGO` 환경변수로 분리.
- (사소) `sample-stats.sh`를 같은 기본 파일명으로 두 번 띄우면 뒤엣것이 앞 데이터를
  truncate한다 — 설정마다 출력 파일을 다르게 지정해야 한다(한 번 겪음).
