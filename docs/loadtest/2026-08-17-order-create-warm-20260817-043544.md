## 이 런의 목적 — 스킬 원칙 3(콜드 JVM) 반영 재측정

직전 런(`2026-08-14-order-create-20260814-211542.md`)은 **컨테이너를 방금 띄운 직후**(콜드 JVM,
옛 `-Xmx228m` 힙)에 쟀다. 그 사이 dev 에 두 가지가 들어왔다:

1. **loadtest 스킬 원칙 3 신설**(#502): 코어 제한 컨테이너에서 JIT 컴파일러가 요청 스레드와 같은
   코어를 놓고 경쟁 → 콜드/웜 차이가 설정 차이보다 크게 나온다. **측정 VU 와 동일 부하로 웜업 후 측정.**
2. **배포 힙 설정을 #502 결론(`-Xms512m -Xmx512m` / G1)으로 변경.**

그래서 **① 웜업(120 VU · 120초, 결과 폐기) → ② 재시드 → ③ 측정** 순서로, 최신 dev 코드 + 512m 힙 +

## 병목 판정 (웜 512m, 120 VU 까지)

- **앱·MySQL CPU 모두 2코어 cap 미달**(앱 188%, MySQL 167% 피크). 콜드 런에서 cap 을 친 것과 대비 —
  웜 JVM 이 JIT 오버헤드 없이 요청당 CPU 를 덜 쓴다.
- **Hikari 풀(10)이 여전히 유일하게 꽉 찬 자원**(active=10, 대기 20VU 10 → 40VU 29). 다만 이번엔
  대기가 얕고 지연이 낮아(p95 205ms) **완만한 큐**로 동작 — 콜드 런의 깊은 대기(145)·30초 타임아웃과 다르다.
- **결론**: 웜 512m 에서 이 쓰기 경로의 무릎은 **콜드 런의 40 VU 보다 위**다 — 120 VU 까지 콜드 런
  같은 붕괴(CPU cap·30초 타임아웃·409 캐스케이드)가 없었다. **다만 무릎이 정확히 어디인지, 120 VU
  단계의 p95 가 얼마인지는 60~120 VU per-step 유실로 미측정이다** — "120 VU 까지 건강"이 아니라
  "120 VU 까지 붕괴 신호(실패·타임아웃·CPU cap) 없음"까지가 근거 있는 말이다. 풀(10)이 앞으로도 첫
  천장이겠지만, CPU 여유가 있어 풀을 키우면 처리량이 늘 여지가 있다(콜드에선 CPU cap 이라 무의미했다).
  **무릎을 정확히 짚으려면 OOM 안 나는 조건(≤60~120 VU, Prometheus 메모리 한도)으로 재측정이 필요하다.**

## 새로 관찰된 것

- **MySQL 데드락 6건**(258,226 create 중 0.002%): `insert into delivery_order` 가
  `Deadlock found when trying to get lock` 로 실패(→ 5xx). `uk_delivery_active_customer` 유니크
  인덱스의 갭락 또는 포인트 잠금(`point_charge`→`point_wallet`) 교차로 추정. 운영상 무시 가능한
  빈도지만, 생성 실패를 재시도로 흡수할지(#37 계약) 별도 판단 필요.
- **앱 컨테이너 RSS 918 MiB / 1 GiB** — 512m 힙 + 비힙(Metaspace·스레드·직접버퍼)이 1 GiB cap 에
  근접. #502 는 "힙이 512MiB 를 넘은 적 없음"을 근거로 512m 를 골랐으나, 그건 **힙**이고 **컨테이너
  총 RSS 는 918 MiB 까지** 올랐다. 여유가 약 100 MiB 뿐이라, 부하가 더 커지면 컨테이너 OOM 여지를
  배포 사이징에서 확인할 것.

## 웜업 검증

측정 구간 JIT 컴파일 부하 **13.6 → 8.1 ms/s**(단계별). 콜드였다면 수백 ms/s 다(#502). 낮고
감소 추세라 이 런은 웜 상태로 잰 것으로 본다. 웜업 런(120 VU·120초) 직후 JIT 는 2.5 ms/s 였다.

## 측정 한계 (반복되는 인프라 문제)

- **Prometheus OOM 이 두 런 연속 재발**했다(200 VU → 120 VU 로 낮췄어도). **원인은 VU 도 일반적
  카디널리티도 아니라 시나리오의 한 줄이었다**: cancel 요청 `PATCH /api/customer/deliveries/{deliveryId}/cancel`
  에 k6 `name` 태그를 안 줘서, k6 가 URL(=deliveryId 포함)을 name 라벨로 썼다. iteration 마다
  deliveryId 가 달라 매 cancel 이 새 시계열을 만들고, 그게 name 라벨을 가진 모든 k6 메트릭
  (`http_reqs`·`http_req_duration` trend·`http_req_waiting/sending/receiving/blocked/connecting`·
  `http_req_failed` …)에 곱해져 **수백만 시리즈**가 됐다. Prometheus 는 활성 시리즈마다 인메모리
  인덱스+head 청크를 들어 메모리가 시리즈 수에 비례하고, 새 deliveryId 가 계속 도착해 **분당
  ~0.9GiB 로 선형 증가**하다 VM(7.75GiB)을 넘겨 커널이 prometheus 를 OOMKill(exit 137, 컨테이너
  자체엔 mem limit 없음)했다. **실측 근거**: 유실 전 20/40 VU 5분 구간만으로 `k6_http_reqs_total`
  이 69,238 시리즈, 그중 cancel URL 69,234 종.
  - create(고정 URL `/api/customer/deliveries`)·위치 갱신(고정 URL `/api/rider/location`)이 안
    터지는 이유가 이것이다 — path param 이 없어 name 이 하나다.
  - **수정 적용**: cancel 요청에 `name: '/api/customer/deliveries/{id}/cancel'` 상수 태그를 달아
    카디널리티를 1 로 묶었다(이 리포트 이후 커밋). 이제 full-VU 계단도 OOM 없이 돌 것이라, 유실됐던
    60~120 VU per-step 을 다시 잡아 무릎을 확정할 수 있다.
  - **런 단위 결론은 k6 summary 로 확정되므로 이 유실이 판정(콜드 대비 개선)을 바꾸지 않는다.**
- 호스트 node-exporter 다운(rslave, macOS) — 컨테이너 CPU 는 `sample-stats.sh` 로 확보.
