## 해석

- **처리량을 정하는 것은 CPU 다.** 2 vCPU 가 192~198% 로 붙어 있다. Hikari 대기(34)가 있지만
  위치 갱신 측정에서와 같은 상황이다 — CPU 가 이미 만석이라 대기만 보고 커넥션 풀을 병목으로
  단정할 수 없다(README 「측정 이력」에서 한 번 철회한 결론).
- **GC 는 이 arm 에서 문제가 아니다.** 힙 최대 160/248 MiB, 정지 합계 8.34초(101초의 8.3%).
  1GiB 컨테이너라 JVM 이 SerialGC 를 고르는 것은 위치 갱신 때와 같다.
- **인덱스는 의도대로 걸린다.** `EXPLAIN`: `type=range`, `key=idx_delivery_waiting_location`,
  `Using index condition`(ICP), 추정 rows=1. 8,000건 중 후보가 291건으로 줄고, 그 291건만
  요약 변환 + 반경(원) 필터 + 정렬을 거친다.
- **요청당 MySQL 21.89 문장은 상한이다**(exporter 스크레이프·만료 스캐너·setup 로그인이 분자에
  섞인다). 코드 경로상 실제 쿼리는 인터셉터 2회 + bounding box 1회 + 스냅샷 IN 1회 = 4회 +
  트랜잭션 부대비용(SET/COMMIT)이다.
- **Redis 1.19/요청은 세션 조회(HGET) 뿐이다.** 이 경로는 Redis 를 쓰지 않는다.
