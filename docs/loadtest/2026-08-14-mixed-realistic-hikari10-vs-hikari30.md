## 목적

Hikari 커넥션 풀 크기(10 vs 30)가 지연·처리량에 영향을 주는지 확인한다. 이전 IHOP 스윕에서
콜드 스타트가 결과를 지배한다는 걸 확인했으므로(`2026-08-13-...ihop-sweep-round2.md`), 이번엔
`.claude/skills/loadtest/SKILL.md`「원칙 3」의 웜업 절차를 그대로 따랐다:

1. 새 설정으로 앱 컨테이너 재기동
2. 재시드
3. 웜업 실행(같은 시나리오, 3분, 결과 버림)
4. 재시드(WAITING 풀 5분 창 리셋)
5. 측정 실행(기본 150s)
6. `JIT 컴파일 부하`가 구간 내내 낮은지 확인 — 웜업 성립 여부의 근거

## 바뀐 것 (이전 실험과 조건 차이)

- **시나리오**: `mixed-realistic.js`의 BUSY 라이더 위치 전송 간격을 0.5초 → **2.4초**로 변경
  (요청 사항). 요청량이 크게 줄어 이전 실험(1,200~1,500 req/s)보다 훨씬 가벼운 부하(300~400
  req/s)가 됐다.
- **시드**: WAITING 주문 비율을 전체의 **10%**로 맞췄다(`seed-loadtest-mixed.sql` 갱신,
  나머지 90%는 lt_w 고객의 과거 COMPLETED 이력).
- **힙**: `-Xms=-Xmx=512m`(컨테이너 메모리 1GiB의 50%) 고정, GC는 G1 기본값(IHOP 오버라이드 없음
  — 이전 실험의 IHOP 결론이 불확실했으므로 이번엔 안 건드림).
- **`-Djdk.tracePinnedThreads=full`**을 추가했다 — 이 앱은 가상 스레드가 켜져 있어서
  (`spring.threads.virtual.enabled: true`), DB 호출 중 캐리어 스레드가 핀될 가능성을 직접
  확인하기 위함이다. **결과: 두 설정 모두 실제 부하 처리 중 핀 이벤트 0건**(웜업·측정 통틀어
  유일한 핀 이벤트 1건은 앱 부팅 시점의 Spring Data JPA 클래스 초기화 락이었다 — 요청 처리와
  무관). 가상 스레드 핀닝은 이번 비교의 교란 요인이 아니다.

## 판정: 이 부하 수준에서는 Hikari 풀 크기가 결과를 가르지 않는다

- **Hikari 대기(pending) 큐가 두 설정 다 0이다.** 커넥션 풀이 병목이었다면 10에서 대기가
  쌓이고 30에서 풀렸어야 하는데, 애초에 병목이 아니었다는 뜻이다 — 활성 커넥션도 최대
  2~17개 수준으로, 10개짜리 풀조차 포화된 적이 없다.
- 지표별로 우열이 갈린다: p95는 10이 낮고(132 vs 143), p99는 30이 낮고(337 vs 364),
  avg는 10이 낮다(24.65 vs 33.16). **한쪽이 일관되게 낫다고 할 근거가 없다** — 방향이
  엇갈리는 것 자체가 "차이 없음"의 신호다.
- 원인은 **시나리오 변경**이다. 위치 전송 간격을 0.5초 → 2.4초로 늘리면서 요청량이 약
  4~5배 줄었고(이전 1,200~1,500 req/s → 이번 300~400 req/s), DB 커넥션 수요 자체가 10개
  풀로도 전혀 부족하지 않은 수준으로 낮아졌다. **Hikari 풀 크기 비교를 다시 의미 있게
  하려면, 이 정도 가벼운 부하가 아니라 커넥션이 실제로 경합하는 부하 강도(예: 이전
  0.5초 간격 시나리오, 또는 VU 를 더 올린 조건)에서 재야 한다.**
