## 목적

주문 생성은 무거운 쓰기 트랜잭션이다(요금 재계산+대조, order→payment 한 트랜잭션 포인트 차감,
진행 중 1건 제한 검사, 주문+요금 스냅샷 insert). 이 경로의 **처리량 포화점과 병목**을 찾는다.
주문 생성은 상태 소진형(고객당 진행 중 1건)이라, 매 iteration 에서 생성 직후 취소해 슬롯을 비우는
**생성→취소 사이클**로 반복 부하를 만들었다. 측정 대상은 create(`api:order-create` 태그).

## 병목 판정 — 쓰기 경로 CPU + 커넥션 풀 (다신호 일치)

**하나만 보고 단정하지 않았다.** 세 신호가 모두 40 VU 부터 천장을 가리킨다:

1. **앱 CPU 가 40 VU 에서 이미 2코어 cap(212%)** 에 닿는다. 이후 단계에서도 ~200% 로 고정 —
   VU 를 올려도 앱이 더 처리할 CPU 가 없다.
2. **Hikari 풀(10)이 40 VU 에서 이미 active=10(만석) + 대기 30.** 대기 큐만 깊어진다
   (30 → 71 → 110 → 145). 처리량은 ~300 req/s 로 정체하는데 지연만 커진다(p95 546→1,244ms) —
   **닫힌 모델 포화의 정의 그대로다. 무릎은 40 VU 이하.**
3. **MySQL CPU 가 상위 단계에서 2코어 cap(201%)** 에 합류한다. 요청당 MySQL 문장이 ~37개로
   많고(사이클이 expireIfStale 조회 + 활성 검사 + point_charge·point_wallet 잠금 + 주문·요금
   스냅샷 insert + 취소 환급), 쓰기 경로가 DB CPU 도 밀어 올린다.

GC(2.3%)·힙(125/228 MiB)·Redis(13%)는 여유 — 병목이 아니다.

> **핵심 시사점**: 풀을 10 → 더 키우는 것만으로는 처리량이 안 늘 가능성이 크다. 앱·MySQL CPU 가
> 이미 2코어 cap 이라, 풀은 그 앞의 큐일 뿐이다. 처리량을 늘리려면 (a) 인스턴스 CPU 상향 또는
> (b) 요청당 DB 왕복(≈37 문장) 축소가 선행돼야 한다. 풀 확대는 그 다음이다.

## 409 1,330건 — 서버 버그 아님, 시나리오 아티팩트

- 409 는 전부 `uk_delivery_active_customer` 중복키(진행 중 1건 제한 위반)다.
- **딱 3명의 고객(id 85·97·169)이 1,330건 전부** 냈다(463+457+410). k6 의 "cancel 200 실패 3건"과
  정확히 일치한다.
- 메커니즘: 포화 시 **cancel 이 Hikari 30초 타임아웃(14건 중 3건이 cancel)** → 그 주문이
  WAITING(active)로 남음 → 해당 고객의 이후 create 는 매번 중복키 409 → 3명이 남은 시간 동안
  각 ~450건씩 빠른 409 를 쏟아냄.
- **서버는 진행 중 1건 제한을 정상 시행**한 것이다. 생성→취소 사이클 설계가 풀 고갈과 부딪혀
  슬롯이 안 비면 그 계정이 남은 런 내내 409 를 낸다 — **테스트 설계의 취약점**이다.
- 시나리오 개선안(다음 런): create 가 409 면 그 고객의 기존 active 주문을 먼저 취소해 슬롯을
  복구하고 재시도한다. 그러면 3명이 갇히지 않고 409 캐스케이드가 사라진다.

## 실사용 환산

- 실사용에서 주문 생성은 사용자당 드문 1회성 행위다(위치 갱신 같은 상시 요청이 아님).
- 이 런의 ~150 사이클/s(생성+취소)는 **동시 주문 생성 폭주**를 인위적으로 만든 값이라, 실제
  트래픽의 SLO 판정이라기보다 **쓰기 경로의 상대적 한계·병목 구조**를 본 것이다.
