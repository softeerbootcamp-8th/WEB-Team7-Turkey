# 배송 주문 취소 작업 기록

- 브랜치: `feature/42-req-ord-004-auto-cancel-timeout` (신규 브랜치 없이 #42/#38 브랜치에 이어서 진행)
- 범위: backend
- 작성일: 2026-08-05

## 무엇을 만들었나

`PATCH /api/customer/deliveries/{deliveryId}/cancel`을 구현했다. 그동안 DTO(`DeliveryCancelRequest`/
`DeliveryCancelResponse`)와 컨트롤러·인터페이스 스텁은 이미 있었지만 `return null`이었던 자리다.

WAITING 상태인 본인 주문을 시간 제약 없이 언제든 취소할 수 있다. 취소는 항상 포인트 전액 환급을
동반한다(#38). 배차 확정(#56)과 동시에 요청이 오면 조건부 UPDATE(`DeliveryOrderRepository.
cancelIfWaiting`, #42/#56이 이미 쓰던 메서드를 그대로 재사용)가 하나만 통과시킨다.

이 작업 중 배포 전에 발견한 버그도 같이 고쳤다: `CustomerWebMvcConfig`의 세션 인터셉터 경로
목록에 `/api/customer/deliveries/*/cancel`이 빠져 있었다(스텁 상태였을 때부터 누락돼 있었다).

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| PATCH | `/api/customer/deliveries/{deliveryId}/cancel` | 배송요청 취소 + 포인트 환급 | 404 없음·타인 것 / 409 이미 배차·완료됨 |

### 화면

해당 없음. 프론트 연동은 이 이슈 범위 밖이다.

### 스키마 변경

해당 없음. 기존 컬럼(`cancel_reason`, `canceled_at`)과 `ORDER_REFUND` 트랜잭션 유형이 이미 있었다.

## 사람이 고른 선택

이 이슈의 계약은 #42/#38 작업 중 팀 논의로 대부분 사람 확인이 끝난 채로 시작됐다(2026-08-04).

### 1. 조건부 "환급받기" 버튼 vs 범용 "취소하기" 버튼

- **물었던 것**: 배차 대기 타임아웃(5분) 이후에만 나타나는 "환급받기" 버튼을 새로 만들지, 시간
  제약 없이 언제든 가능한 범용 "취소하기" 버튼을 만들지.
- **선택지**:
  - (A) 조건부 "환급받기" — 5분 지나야 노출. 타임아웃 개념과 강하게 결합됨
  - (B) 범용 "취소하기" — 시간 무관, 취소=환급(#38)을 겸함. 5분을 안 기다리고 취소하고 싶은
    고객도 커버
- **고른 것**: (B)
- **근거**: 취소는 항상 환급을 동반하므로 (A)는 (B)의 부분집합에 불과하다. (B)가 더 넓고
  구현도 하나로 끝난다.
- **영향**: 이슈 본문의 "취소" 개념 자체가 이미 이 방향과 일치했다(사전 조건에 시간 제약이
  없다). `DeliveryDetailQueryService.getDetail`(#46)에 만료 판정을 얹으려던 이전 시도는 이
  결정으로 인해 불필요해져 되돌렸다(별도 기록: `2026-08-04-42-auto-cancel-timeout.md`).

### 2. 담당자 재배정

- **물었던 것**: 원래 githings 담당이던 이 이슈를 emes-g가 가져올지.
- **고른 것**: 가져옴(재배정 완료, 2026-08-04).
- **근거**: #42 작업 중 "환급 로직·조건부 UPDATE 패턴을 그대로 재사용할 수 있다"는 게 드러나서,
  같은 사람이 이어서 하는 게 자연스럽다고 판단.

## 스스로 판단한 것

- **기존 인프라 재사용**: 새 리포지토리 메서드를 만들지 않고 `cancelIfWaiting`(#42/#56)과
  `refundForCancel`(#38)을 그대로 불렀다. `cancelIfWaiting`은 애초에 취소 사유를 파라미터로
  받게 만들어져 있어서(고정 문자열이 아니다), 고객이 직접 입력한 사유를 그대로 전달할 수 있었다.
- **멱등 처리 패턴**: 이미 CANCELED인 주문에 다시 취소 요청이 오면 조건부 UPDATE를 아예
  시도하지 않고 기존 값을 그대로 반환한다 — `CustomerPaymentService.cancelPointCharge`(#34)가
  이미 종료 상태 재요청을 200으로 흡수하는 것과 같은 판단.
- **응답 조립 시 재조회하지 않음**: 취소 성공 후 `DeliveryOrder`를 다시 조회해 응답을 만들지
  않고, 조건부 UPDATE에 넘긴 `canceledAt` 값을 그대로 응답에 실었다. `DeliveryDetailQueryService`
  (#46)를 만들며 같은 세션에서 재조회하면 Hibernate 1차 캐시가 갱신 전 인스턴스를 돌려주는
  문제를 실측으로 확인했기 때문에, 애초에 그 함정을 피하는 방식으로 짰다.
- **소유권 확인 방식**: `#46`이 쓰는 `findByIdAndCustomer_Id`(없음/타인 것을 같은 404로 응답)를
  그대로 재사용해, 존재 여부를 노출하지 않는 이 저장소의 기존 원칙과 일관되게 갔다.
- **404 vs 409 판정 순서**: 소유권 확인(404) → 이미 CANCELED면 멱등 200 → 조건부 UPDATE 시도 →
  0행이면 409. 이미 CANCELED 여부를 조건부 UPDATE 전에 먼저 갈라낸 이유는, 그 경우 굳이
  UPDATE를 시도할 필요가 없고(항상 0행) 의도(멱등 vs 진짜 충돌)가 코드에서 더 분명해지기
  때문이다.
- **운임 스냅샷 없음 → 500**: `DeliveryDetailQueryService.fare()`가 같은 상황에 쓰는
  `BusinessException(INTERNAL_SERVER_ERROR)` 패턴을 그대로 따랐다(데이터 불변식 위반이지
  사용자 입력 오류가 아니므로).

## 일부러 하지 않은 것

- **프론트 클라이언트 사이드 카운트다운**: 상세화면에서 `requestedAt + 5분` 기준으로 화면을 켜둔
  채 자동으로 "만료됨" 안내로 전환되는 기능은 이 백엔드 이슈 범위 밖이다. 프론트가 이 API를
  연동할 때 함께 구현해야 한다(서버 재폴링 없이 순수 클라이언트 계산). 후속: 프론트 연동
  이슈 미등록 — #46/#47 프론트 담당자에게 전달 필요.
- **`order_status_history`에 취소 이력 기록**: 이 테이블은 아직 아무 코드도 쓰지 않는다(#42
  worklog에서도 같은 판단). 이번에도 손대지 않았다.
