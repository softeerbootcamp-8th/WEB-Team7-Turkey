## 무엇을 만들었나

`POST /api/rider/login` — `CustomerLoginService`(#26)와 처리 흐름·실패 응답 정책이 동일하다.
다른 점은 역할이 `RIDER`라는 것과, 응답에 라이더 프로필의 현재 운행 상태(`operatingStatus`)를
함께 반환한다는 것뿐이다. 이슈 비고대로 로그인만으로 운행 상태를 바꾸지 않는다 — 조회만 한다.

`#48`~`#50` 배치 진행 결정은 `docs/worklog/2026-07-28-48-rider-signup.md`에 기록.

## 사람이 고른 선택

없음 — `#48`(라이더 회원가입) 워크로그의 배치 진행 결정을 그대로 따른다. TTL(2시간 고정)·쿠키
정책(`SameSite=Lax`+프로파일별 `Secure`)은 `#26`에서 이미 확정된 정책을 그대로 재사용해서
다시 묻지 않았다.

## 스스로 판단한 것

- **활성 라이더 계정에 프로필이 없는 경우를 별도로 검증하지 않음**: `RiderSignupService`(#48)가
  회원 저장과 라이더 프로필 생성을 하나의 트랜잭션으로 묶어서, 활성 라이더 계정에 프로필이 없는
  상태는 구조적으로 나올 수 없다. `riderProfileRepository.findById(member.getId()).orElseThrow()`로
  존재를 가정하고, 있을 수 없는 경우를 위한 방어 코드(별도 예외 메시지 등)를 추가하지 않았다
  (CLAUDE.md "존재할 수 없는 시나리오에 대한 검증 추가 금지" 원칙).
- **세션 TTL 상수를 고객 로그인과 공유하지 않고 별도로 둠**: `CustomerLoginService.SESSION_TTL`과
  값(2시간)은 같지만, 라이더 세션 정책이 나중에 고객과 달라질 수 있어(예: 운행 중 세션은 더
  길게) 지금 공용 상수로 묶지 않았다. 실제로 달라질 필요가 생기면 그때 분리하면 되고, 지금
  합쳐두면 오히려 나중에 "공용 상수를 라이더만 다르게 바꿔야 하는" 리팩터링이 생긴다.

## 일부러 하지 않은 것

- **로그인 시 운행 상태 변경**: 이슈 비고에 "로그인만으로 운행 상태를 AVAILABLE로 변경하지
  않는다"고 명시돼 있어, `RiderProfile`을 조회만 하고 상태 전이 메서드(`goOnline()` 등)는
  호출하지 않는다.
