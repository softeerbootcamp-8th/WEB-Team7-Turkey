# 배송 추적 스냅샷 REST 작업 기록

- 이슈: [#79](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/79) SSE 재연결 및 최신 상태 복구
- 브랜치: `feature/79-tracking-snapshot`
- 범위: backend
- 작성일: 2026-07-31

## 무엇을 만들었나

이슈 제목은 "SSE 재연결"이지만, **처리 흐름 ②~⑥(세션·소유권 재검증 → MySQL 상태 → Redis 최신 위치
→ 연결 등록 → 스냅샷 전송)은 #77 이 이미 구현해 놨다.** 브라우저 `EventSource` 가 같은 URL 로
재연결하면 그 경로가 그대로 다시 돌고 `init` 이벤트가 "과거 재생 없이 현재 상태 + 최신 위치"를
준다 — 이슈의 성공조건 그대로다.

그래서 실제로 비어 있던 것은 두 개였고, 사람이 그중 **스냅샷 REST 하나만** 이번 범위로 골랐다:
`return null` 스텁이던 `GET /api/customer/deliveries/{deliveryId}/tracking` 을 구현했다.
남은 하나(흐름 ① 기존 연결 정리)는 「일부러 하지 않은 것」에 결함 내용과 함께 적었다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| GET | `/api/customer/deliveries/{deliveryId}/tracking` | 추적 화면 진입 스냅샷(상태·타임라인·라이더·요금) | 401 세션 / 404 없음·타인 주문 / 409 추적 불가 상태 / 500 예상 운임 스냅샷 없음 |

`estimatedArrivalAt` 은 항상 null 이고, `steps` 는 도달한 단계만 담는다. 상세 계약은
`docs/04-frontend-api-map.md` §1·§7.

### 화면

해당 없음. 화면은 #209, 훅은 #196. **스펙(`@Operation`)이 이미 선언돼 있어 Orval 생성물이 바뀌지
않으므로** 프론트 재생성도 필요 없었다(추가한 `AuthenticatedCustomer` 파라미터는
`@Parameter(hidden = true)` 이고 클라이언트가 채울 수 없다).

### 스키마 변경

없다. `delivery_order`(V10)와 `order_fare_snapshot`(V12)만 읽는다.

## 사람이 고른 선택

### 1. #79 범위를 스냅샷 REST 로 한정

- **물었던 것**: 재연결 안정화(흐름 ①)와 스냅샷 REST 중 무엇을 이번에 할지. 조사 결과 ②~⑥ 은 이미
  구현돼 있고, #77 워크로그와 `docs/04` §7 이 **둘 다 스냅샷 REST 를 #79 후속으로 지목**해 놨다
- **선택지**:
  - (A) 재연결 안정화만 — 실제로 깨지는 결함을 고친다 / 프론트가 오류를 판정할 통로가 계속 없다
  - (B) 둘 다 — 분량 2배
  - (C) 스냅샷 REST 만 — 프론트(#196·#209)가 막혀 있는 것을 뚫는다 / 429 결함이 남는다
- **고른 것**: (C)
- **근거**: 사람 확인.
- **영향**: `docs/04` §7 이 "오류 판정은 #79 스냅샷 REST 로 한다"고 적어 둔 약속이 이제 지켜진다.
  대신 아래 3번 결함이 그대로 남는다.

### 2. 상태 게이트를 스트림과 동일하게(추적 불가 상태는 409)

- **물었던 것**: 소유권만 확인해 모든 상태에 200 을 줄지, 스트림처럼 WAITING·COMPLETED·CANCELED 를
  409 로 거를지
- **선택지**:
  - (A) 소유권만, 모든 상태 200 — 완료·취소 화면까지 이 API 하나로 그릴 수 있다 / 프론트가 status 로
    직접 분기해야 하고 스트림 판정과 어긋날 수 있다
  - (B) 스트림과 동일하게 409 — 추가 쿼리 0(기존 `DeliveryTrackingAccessService` 재사용),
    "이 REST 가 200 이면 스트림도 열린다"가 보장된다 / 완료·취소된 배송 화면은 이 API 로 못 그린다
- **고른 것**: (B)
- **근거**: 사람 확인.
- **영향**: 판정 코드가 한 곳(`DeliveryTrackingAccessService`)에 남아 스트림과 갈라질 수 없다.
  대가로 **완료·취소 배송의 추적 화면은 배송요청 상세 API(아직 스텁)가 필요**해졌다 —
  화면 이슈(#209)가 이 사실을 알아야 한다.

### 3. `estimatedArrivalAt` 은 항상 null

- **물었던 것**: 산정 근거가 없는데 기존 `DeliveryService.estimateMinutes`(직선거리 600m당 1분)로
  값을 만들지, 비워 둘지
- **선택지**:
  - (A) `assignedAt + estimateMinutes` — 값이 안정적이고 시간이 지나면 도착에 가까워 보인다 / 근거가
    직선거리 36km/h 뿐이라 실제와 어긋난다
  - (B) 항상 null — DTO 가 이미 "산정 불가하면 null" 을 허용한다 / 화면에 「도착 예정」이 없다
  - (C) `now + estimateMinutes` — 남은 시간처럼 보인다 / 항상 "지금부터 N분"이라 값이 줄지 않고 계속
    밀려나 화면이 오해를 산다
- **고른 것**: (B)
- **근거**: 사람 확인.
- **영향**: 지도·경로 API 를 붙이는 이슈가 이 필드를 채운다. 임의의 값을 넣어 두면 화면이 그것을
  약속으로 취급하게 되므로, 비워 두는 것이 되돌리기 쉽다.

## 스스로 판단한 것

- **`steps` 를 `order_status_history` 가 아니라 `delivery_order` 의 시각 컬럼에서 파생시켰다.**
  그 테이블은 엔터티(V13)만 있고 **행을 쓰는 코드가 하나도 없다**(리포지토리조차 없어 런타임에 비어
  있다). 작성기를 넣는 것은 상태 전이 API 이슈 몫이고, 시각 컬럼은 전이 메서드가 DDL CHECK 와 같은
  조합으로 채우므로 지금 신뢰할 수 있는 유일한 출처다. 나중에 history 로 옮겨도 **응답 형태는 같다.**
- **예상 운임 스냅샷이 없으면 400 이 아니라 500 이다.** 라이더 콜 상세는 같은 상황에
  `IllegalStateException` 을 던지는데, 그건 `GlobalExceptionHandler` 가 **400** 으로 바꿔 "클라이언트가
  잘못 보냈다"로 읽히게 만든다. 실제로는 데이터 불변식이 깨진 상태라 `BusinessException(500)` 으로
  던져 `ApiResponse` 형태를 유지하면서 사유를 맞췄다.
- **주문 행을 두 번 읽는다**(게이트가 투영, 서비스가 엔터티). 게이트는 SSE 가 트랜잭션 밖에서 값을
  쓰기 때문에 투영이어야 하고, 여기서는 타임스탬프·라이더 정보가 필요해 엔터티가 필요하다. 판정
  정책을 복사하지 않는 대가로 조회 한 번을 더 쓰는 쪽을 골랐다 — 화면 진입당 1회다. 문제가 되면 투영
  쿼리 하나로 합칠 수 있고, 그때는 404/409 정책도 함께 옮겨야 한다.
- **응답 조립을 트랜잭션 안에서 끝낸다.** 라이더 이름·연락처가 `order → assignedRider → member` 두
  단계 지연 로딩이고 OSIV 가 꺼져 있다. 통합 테스트에 `@Transactional` 을 **붙이지 않은 것**이 이
  판단의 검증 장치다.
- **새 서비스 클래스를 만들었다**(`DeliveryTrackingQueryService`). `DeliveryService` 는 요금 정책
  리포지토리만 들고 있고, `DeliveryTrackingAccessService` 는 인가 담당이다. 조회 책임을 둘 중 아무
  쪽에 얹어도 그 클래스의 이름이 거짓이 된다.
- **`TrackingFixture` 에 예상 운임 스냅샷을 추가했다.** 실제로는 주문 생성 트랜잭션이 함께 만드는
  값인데 그 API 가 스텁이라 픽스처가 대신 만든다. 요금 정책을 시나리오마다 새로 만들되 INACTIVE 로
  두는데, `uk_fare_policy_version` 은 버전이 겹치면 안 되고 `uk_fare_policy_active` 는 ACTIVE 가 두 건이면
  안 되기 때문이다(추적 조회는 정책 상태를 보지 않는다).
- **`CustomerDeliveryApi` 를 새 명세 분리 방침(#278: 인터페이스=문서, 구현=매핑)으로 이전하지 않았다.**
  이 파일은 매핑을 인터페이스에 두는 이전 스타일이고, 6개 메서드를 옮기는 것은 이 이슈 범위 밖이다.
  건드린 메서드 하나만 기존 스타일에 맞췄다.
- **나머지 스텁 5개(`createDelivery` 등)에 고객 식별 파라미터를 넣지 않았다.** #55 에서 라이더 API 에
  생긴 것과 같은 종류의 누락이지만, 각 API 를 구현하는 이슈가 자기 인터셉터 등록과 함께 넣는 것이
  맞다(등록 없이 파라미터만 있으면 그 API 는 500 이 된다).

## 일부러 하지 않은 것

- **SSE 재연결 시 연결 자리 정리(흐름 ①)**: 사람 결정(위 1번). **남는 결함**: 연결 한도가 3이고
  서버가 `retry: 3000` 을 지정하는데, SSE 는 쓰기를 시도할 때만 끊김을 알 수 있어 죽은 연결이 stale
  임계(45초)까지 자리를 잡고 있다. 즉 **45초 안에 3번 끊겼다 붙으면 4번째가 429** 이고, 브라우저
  `EventSource` 는 200 이 아닌 응답에 재연결하지 않으므로 **추적 화면이 수동 새로고침까지 죽는다**
  (지하철·엘리베이터에서 현실적으로 발생한다). 고치는 방법은 조사해 뒀다: 클라이언트가 보낸
  불투명 식별자를 emitter id 로 쓰면 Lua 의 `ZSCORE` 분기가 이미 재획득을 허용하므로 자기 자리를
  재사용한다. 단 그때는 **죽어 가는 이전 연결의 늦은 `onCompletion` 이 같은 id 를 이어받은 새 연결을
  지우는** use-after-free 를 함께 막아야 한다(`complete()` 는 콜백을 동기로 돌리지 않는다) —
  레지스트리 제거를 값까지 비교하는 형태로 바꾸면 된다. 후속: 미등록(아래 미결 1)
- **`order_status_history` 작성기**: 상태 전이 API 이슈 몫. 후속: 미등록(전이 API 이슈에서)
- **완료·취소 배송의 추적 화면 데이터**: 게이트가 409 로 거른다(위 2번). 배송요청 상세 API 몫
- **최종 운임(FINAL) 처리**: 완료된 배송이 게이트에 걸려 이 경로에 오지 않으므로 ESTIMATE 만 읽는다
- **다른 스텁 API 구현**: `createDelivery`·`getDeliveries`·`getDelivery`·`cancelDelivery` 는 그대로다.
  그래서 **이 API 는 아직 픽스처·시드 데이터로만 실측할 수 있다**

### 검증하지 못한 것

- **실제 주문 생성 경로**: `createDelivery` 가 스텁이라 주문·운임 스냅샷을 픽스처가 만든다. 주문 생성이
  붙었을 때 "ESTIMATE 스냅샷이 같은 트랜잭션에서 만들어진다"는 전제가 지켜지는지는 그 이슈가 봐야 한다.
- **프론트 소비**: `useTrackingStream`(#196)·추적 화면(#209)이 아직 없어 "스냅샷 REST → 스트림 연결"
  순서를 실제 브라우저에서 돌려 보지 못했다.
- **동시 요청·중복 요청**: 읽기 전용 API 라 상태를 바꾸지 않아 해당 사항이 없다고 판단했다.

## 새로 생긴 미결 사항

1. **SSE 재연결이 연결 자리를 재사용하지 않아 45초 안에 3회 이상 재연결하면 429 로 추적 화면이 죽는다**
   (위 「일부러 하지 않은 것」). 고치는 방법과 함께 물려 있는 use-after-free 위험까지 조사해 뒀다.
   사람 결정으로 이번 범위에서 뺐고, 별도 이슈로 올릴지 판단이 필요하다.
2. **완료·취소된 배송의 추적 화면을 그릴 API 가 없다.** 이 API 는 게이트에서 409 를 주고, 배송요청
   상세 API 는 아직 스텁이다. 화면(#209)이 어느 쪽에 기대는지 정해야 한다.
