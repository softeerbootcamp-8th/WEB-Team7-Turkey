# 계정 설정 화면 로그아웃 연동 작업 기록

- 범위: frontend
- 작성일: 2026-08-06

## 무엇을 만들었나

`account/settings.tsx` 가 `Hello "/account/settings"!` 껍데기였다. 고객·라이더 홈의 설정 아이콘이
이미 이 경로를 가리키고 있었는데 도착하면 아무것도 없었다. 이 화면을 만들고 **로그아웃만** 연결했다.

이슈가 함께 요구한 비밀번호 재설정(#23)·회원 탈퇴(#95)는 백엔드가 둘 다 OPEN(미구현)이라
이번 범위에서 뺐다(아래 「사람이 고른 선택」 2번).

### API

새로 만든 것 없음. 이미 있는 두 API 를 소비만 했다.

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/customer/logout` | 고객 로그아웃(#28) | 없음 — 세션 없음·만료도 200 |
| POST | `/api/rider/logout` | 라이더 로그아웃(#51). `AVAILABLE→UNAVAILABLE` 전이 포함 | 409(BUSY, 배송 수행 중) |

Orval 훅(`useCustomerLogout`·`useRiderLogout`)이 이미 생성돼 있어 `pnpm generate:api` 를 돌리지 않았다.
백엔드 변경이 없으므로 재생성해도 결과가 같다.

### 화면

- `frontend/src/routes/account/settings.tsx` — 설정 화면. `account/route.tsx` 의 인증 가드
  (역할 무관) 아래에 있고, 가드가 context 로 넘겨준 `session.role` 로 **호출할 로그아웃 훅 하나를 고른다.**
- `frontend/src/routes/account/-accountSettings.ts` — 실패 분류 순수 함수(`resolveLogoutFailure`).
  라우터·네트워크 의존이 없어 단위 테스트 대상이다(`rider/_authed/-riderHome.ts` 와 같은 형태).

### 스키마 변경

해당 없음.

## 사람이 고른 선택

### 1. 로그아웃 성공 후 이동 목적지

- **물었던 것**: 이슈가 "랜딩 또는 로그인 화면"으로 둘 다 열어 뒀다. 어디로 보낼 것인가.
- **선택지**:
  - (A) 랜딩 `/` — 역할 무관 화면이라 어느 역할이든 같은 경로로 끝난다. 랜딩은 이미 비로그인 전제로
    역할 선택 버튼을 보여주고, 로그인 상태면 역할 홈으로 되돌려 보내는 가드가 있어 캐시 정리가
    제대로 됐는지 확인하는 데도 유리하다 / 재로그인이 한 단계 길다
  - (B) 역할별 로그인 화면 — 재로그인이 짧다 / 다른 역할로 갈아타려는 사람은 랜딩으로 한 번 더 이동해야 한다
- **고른 것**: (A) 랜딩 `/`
- **근거**: 사람 확인(2026-08-06).
- **영향**: 랜딩 가드(`resolveLandingGuard`)가 로그아웃 직후 상태를 그대로 드러낸다 — 캐시나 역할 힌트가
  덜 지워졌으면 랜딩이 역할 홈으로 되돌려 보내므로 회귀가 눈에 보인다. `replace: true` 로 이동해
  뒤로 가기가 로그아웃된 설정 화면으로 돌아가지 않게 했다.

### 2. 비밀번호 재설정(#23)·회원 탈퇴(#95) 항목 처리

- **물었던 것**: 백엔드가 없는 두 항목을 화면에 둘 것인가.
- **선택지**:
  - (A) 비활성 항목으로 표시 — 설정 화면 골격이 완성되고 나중에 훅만 붙이면 된다 / 쓰지 못하는 버튼이 남는다
  - (B) 로그아웃만 두기 — 동작하는 것만 보여준다 / 나중에 항목을 다시 배치해야 한다
- **고른 것**: (B) 로그아웃만 두기
- **근거**: 사람 확인(2026-08-06).
- **영향**: #23·#95 구현 시 이 화면의 「계정 관리」 섹션에 항목을 추가하면 된다. 이슈 #222 의 체크박스
  중 비밀번호·탈퇴 항목은 미완으로 남으므로 이슈를 닫을 때 판단이 필요하다.

## 스스로 판단한 것

- **실패를 세 갈래로 나눴다** (`resolveLogoutFailure`) — 근거: "실패"를 한 덩어리로 다루면 대응이
  정반대인 두 경우가 섞인다. 409(라이더 BUSY)는 **서버 세션이 확실히 살아 있는** 명시적 거부라
  캐시를 비우면 안 되고, 네트워크·5xx 는 **성사 여부를 모르는** 상태라 이 기기의 캐시만이라도
  비워야 다음 사용자에게 이전 사용자 데이터가 남지 않는다. 401 은 "이미 세션이 없다"는 뜻이라
  성공 경로로 흡수한다(이슈의 예외 흐름 「이미 만료된 세션으로 로그아웃 시도」).
- **`local-only` 실패에서 자동 이동하지 않고 안내 + 버튼(다시 시도 / 처음 화면으로)을 띄웠다** —
  근거: 이슈는 "캐시는 정리하고 로그인 화면으로 보내되 실패 사실을 알린다"고 적었는데, 곧바로
  이동시키면 알림을 띄울 자리가 없다(랜딩에는 메시지를 실어 보낼 search 파라미터가 없고,
  `validateRedirectSearch` 는 `redirect` 만 허용한다). 캐시·역할 힌트 정리는 **즉시** 하고 이동만
  사용자 확인에 맡겨, "정리는 됐지만 알림은 보인다"는 두 요구를 모두 만족시켰다.
- **`queryClient.clear()` 를 쓰고 세션 쿼리만 지우는 `clearSessionQueries` 를 쓰지 않았다** — 근거:
  이슈가 명시한 대로 배송·포인트 등 개인 데이터 캐시까지 버려야 한다. 대신 역할 힌트 정리를 놓치지
  않도록 `clearStoredSessionRole()` 을 함께 부른다(`clear()` 는 localStorage 를 건드리지 않는다).
- **역할별 훅을 조건부로 호출하지 않고 둘 다 인스턴스화한 뒤 `mutate` 만 골라 부른다** — 근거: 훅
  호출 순서 규칙. 실제 요청은 한쪽만 나가므로 #288(반대 역할 401 이 공용 `SESSION_ID` 쿠키를
  만료시키는 문제)과 같은 상황은 생기지 않는다.
- **확인 다이얼로그는 `window.confirm` 이 아니라 기존 배송 취소 다이얼로그와 같은 `role="dialog"`
  마크업으로 만들었다** — 근거: 저장소에 두 선례가 다 있는데(`tracking.tsx` 는 `window.confirm`,
  `deliveries/$deliveryId/index.tsx` 는 커스텀 다이얼로그), 라이더에게는 "운행 상태가 종료로 바뀐다"는
  설명을 함께 보여줘야 해서 문구를 담을 수 있는 쪽을 골랐다.

## 일부러 하지 않은 것

- **비밀번호 재설정·회원 탈퇴**: 백엔드 #23·#95 가 OPEN 이다 — 이유: 소비할 API 가 없다 — 후속: #23, #95
- **`account/index.tsx`·`account/edit.tsx`**: 여전히 `Hello ...` 껍데기다 — 이유: 이슈 #222 는
  `settings.tsx` 만 대상으로 한다 — 후속: 미등록(회원정보 화면 이슈가 따로 있는지 확인 필요)
- **라이더 BUSY 로그아웃 시 진행 배송 화면으로 자동 이동**: 안내와 버튼만 두고 자동 이동은 하지 않았다 —
  이유: 이슈가 "유도"라고만 적었고, 설정 화면에 온 사용자를 동의 없이 다른 화면으로 옮기는 것은 과하다
- **브라우저 E2E**: 이 저장소 프론트에는 E2E 도구(playwright 등)가 없고, `frontend/CLAUDE.md` 가
  "라우터를 띄우지 않고 순수 함수로 테스트한다"를 규칙으로 두고 있어 그 관례를 따랐다

### 검증하지 못한 것

- **화면 동작을 실제 브라우저로 확인하지 않았다.** 로그아웃 성공 후 `queryClient.clear()` →
  랜딩 이동 순서가 의도대로 도는지(중간에 설정 화면이 빈 캐시로 리렌더되며 깜빡이지 않는지)는
  단위 테스트로 잡히지 않는다.
- 라이더 BUSY 409 경로는 실패 분류 함수만 테스트했고, 실제 BUSY 라이더 세션으로 요청해 보지는 않았다.

## 새로 생긴 미결 사항

- **로그아웃 요청이 실패했을 때(네트워크·5xx) 서버 세션이 남는다.** 화면은 이 기기의 캐시만 비우고
  안내하지만, 서버 세션은 TTL(2시간)까지 유효하다. 같은 브라우저에서 다시 로그인하면 새 세션으로
  덮이지만 그 전까지는 쿠키만 있으면 API 를 부를 수 있다. 재시도 큐를 둘지, 감내할지 미결.
