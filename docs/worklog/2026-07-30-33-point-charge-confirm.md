- 브랜치: `feature/33-cus-point-003-포인트-충전-모의-승인` (#32 위에 스택)
- 범위: backend
- 작성일: 2026-07-30

## 무엇을 만들었나

PG 승인을 받아 충전을 확정하는 흐름을 채웠다. 성공하면 충전 `PENDING→PAID`, 지갑 잔액 증가,
CHARGE 원장 1행이 **한 트랜잭션**에서 일어난다. 승인 여부는 `PaymentGateway` 가 결정하고,
MVP 는 `MockPaymentGateway` 가 프로세스 안에서 결과를 만든다 — 실 연동은 구현체 교체로 끝난다.

**PG 호출은 트랜잭션 밖에 있다.** 그래서 `CustomerPaymentService` 는 파사드가 되고 DB 구간은
`PointChargeApprover` 가 맡는다. 이 분리가 이번 작업의 뼈대다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/customer/points/charges/{id}/confirm` | PG 승인 후 충전 확정 | 400 금액 불일치 / 403 본인 아님 / 404 없음 / 409 승인 불가·결제 확인 중 / 502 PG 응답 불명 |

PG 거절은 오류가 아니라 **200 + status=FAILED** 다. 예외로 던지면 트랜잭션이 롤백되어
`PENDING→FAILED` 전이 자체가 사라진다.

### 화면 / 스키마 변경

둘 다 해당 없음. 모의 결제 화면 라우트가 없어 이 API 를 호출할 주체가 아직 없다(아래 「하지 않은 것」).

## 사람이 고른 선택

### 1. 승인 요청에 결제 금액을 받을지

- **선택지**: (A) 받되 검증에만 사용 / (B) 안 받음(서버가 항상 전액 승인이라는 구조로 충족)
- **고른 것**: (A)
- **근거**: 이슈 처리흐름 ④를 우회 설명 없이 만족하고, 실 PG(토스) 승인 요청과 모양이 같아진다
- **영향**: 전달값은 대조에만 쓰고 승인 금액은 항상 DB 의 `requested_amount` 다. 금액을 바꿔 보내도
  포인트를 더 받을 통로가 되지 않는다

### 2. 이미 PAID 인 충전에 재승인 요청이 오면

- **선택지**: (A) 200 + 그때 결과 / (B) 409
- **고른 것**: (A). 기존 `CustomerPointApi` 문서(409)를 고쳤다
- **근거**: 이슈 비고의 "반복 전달되어도 한 번만 증가"를 멱등성의 통상 의미로 해석. 응답 유실 후
  재전송에서 사용자가 오류 화면을 보지 않는다
- **영향**: 반환 잔액은 지갑의 **현재** 잔액이 아니라 승인 시점 원장의 `balance_after` 다. 그 뒤
  다른 거래로 잔액이 바뀌었을 수 있어 현재 잔액은 "승인 반영 후 잔액"이 아니다

### 3. 잔액 갱신의 동시성 제어

- **선택지**: (A) 비관적 락(`SELECT ... FOR UPDATE`) / (B) 조건부 UPDATE + 재조회
- **고른 것**: (A)
- **근거**: 사람 판단 — "자기 계좌 입출금은 동시에 일어나는 일이 거의 없으니 비관적 락을 걸어도
  병목이 거의 없다". 지갑은 회원당 1행이라 회원끼리 경합하지 않는다
- **영향**: `PointTransaction` 이 요구하는 `balanceBefore` 를 얻으려면 읽어야 하는데 조건부 UPDATE 는
  영향 행 수만 준다. (A) 가 아니면 원장을 쓸 수 없다.
  **잠금 순서를 `point_charge` → `point_wallet` 로 고정**했다 — 포인트를 만지는 다른 흐름도 같은
  순서를 지켜야 한다. 엇갈리면 데드락이다

### 4. PG 호출을 트랜잭션 안에 둘지

- **선택지**: (A) 단일 트랜잭션 유지 / (B) 파사드로 분리
- **고른 것**: (B)
- **근거**: `@Transactional` 안에서 외부 호출을 하면 응답을 기다리는 동안 HikariCP 커넥션을 쥔다.
  트래픽이 몰리면 커넥션 풀이 마른다. 모의 PG 는 네트워크 대기가 0 이라 오늘 이득은 없지만, 실 PG 를
  붙일 때 반드시 필요한 모양이고 지금이 옮기기 가장 쉽다
- **영향**: **확정 구간만 잠그므로 동시 요청이 PG 를 각각 부를 수 있다.** 방어선이 DB 잠금에서
  PG 멱등성 + 확정 구간의 상태 재확인으로 옮겨갔다. "PG 호출도 한 번"은 포기하고
  "포인트 증가는 한 번"만 지킨다

## 스스로 판단한 것

- **승인 식별자를 별도 트랜잭션으로 선커밋** — 근거: 확정이 실패해 롤백되면 `providerPaymentKey` 가
  함께 사라져 "돈은 나갔는데 어떤 승인인지 모르는" 건이 된다. 그러면 취소도 대사도 불가능하다.
  `ck_point_charge_state_values` 가 금액·시각 컬럼만 검사해서 **PENDING 상태에 이 값이 있어도 제약
  위반이 아니다** — 마이그레이션 없이 됐다.
  그 결과 `status='PENDING' AND provider_payment_key IS NOT NULL` 이 대사 대상 추출 조건이 된다
- **한 번 기록된 승인 식별자는 덮어쓰지 않는다** — 근거: 동시 요청이 각각 PG 를 불러 서로 다른 승인을
  받아 오면(벤더가 멱등하지 않을 때) 나중 값이 먼저 값을 지운다. 그러면 먼저 받은 승인을 추적할 수
  없다. `markApprovalReceived` 가 `boolean` 을 반환하고, `false` 면 ERROR 로 남긴다
- **`PENDING + 승인식별자 있음` 인 건은 재승인을 409 로 차단** — 근거: PG 를 다시 부르면 새 식별자가
  기존 값을 덮어쓴다. 사실상 `APPROVING` 상태를 enum 값이나 컬럼 추가 없이 표현한 것이다.
  대신 "PENDING 의 의미가 둘"이라는 점이 암묵적이라 도메인 메서드 이름과 주석으로 드러냈다
- **TIMEOUT 과 DECLINED 를 갈랐다** — 근거: 거절은 결과가 확정된 실패라 FAILED 로 못 박아도 되지만,
  응답을 못 받은 경우는 결제 성사 여부를 알 수 없다. FAILED 로 확정하면 실제로 결제된 건을 실패로
  못 박는 셈이라 되돌릴 수 없다. PENDING 을 유지하고 502 로 알린다
- **지갑 존재 확인을 PG 호출 앞으로** — 근거: 가장 흔한 실패를 돈이 움직이기 전에 거른다. 읽기만
  하므로 잠금 시간이 늘지 않는다
- **승인 여부를 요청 필드가 아니라 게이트웨이가 결정** — 근거: 처음엔 `MockPaymentResult` 를 요청에
  뒀는데, 그러면 실 PG 를 붙일 때 그 필드가 사라져야 하고 API 계약과 서비스가 함께 바뀐다.
  모킹 사정이 도메인 요청에 새어든 설계였다

## 일부러 하지 않은 것

- **망 취소 · 결제 조회 API · 대사 스케줄러 · 웹훅**: 이유: 모의 PG 는 돈이 움직이지 않아 동작을
  검증할 방법이 없다. 취소를 짜도 취소될 결제가 없고 대사를 짜도 대조할 상대가 없다 — 후속: 미등록
- **claim 패턴**(PG 호출 권한 선점): 이유: 동시 요청이 PG 를 두 번 부르는 것을 막으려면 필요하지만
  상태나 컬럼 추가가 따라온다. 벤더 멱등성 여부를 확인한 뒤 결정하는 순서가 맞다 — 후속: 미등록
- **`PaymentGateway.prepare()` 를 준비 단계에 배선**: 이유: #32 의 "MVP 는 PG 호출 0회"를 유지.
  구현만 두고 호출하지 않는다 — 후속: 미등록
- **프론트 연동**: 이유: 이슈 처리흐름이 전부 서버 측이다. 모의 결제 화면 라우트가 없어 이 API 를
  호출할 주체가 아직 없고 Orval 도 재생성하지 않았다 — 후속: 미등록

### 검증하지 못한 것

- 실 PG 흐름 전체 — 구현체가 없다
- 확정 구간이 실패했을 때 승인 식별자가 남는지는 **코드 경로로만** 확인했다. 커밋 실패를 인위적으로
  일으키는 테스트는 없다
- 프론트가 멱등키·`authToken` 을 어떻게 만들고 재사용하는지 — 화면 미연결

## 새로 생긴 미결 사항

아래 항목은 `CLAUDE.md` 「확인이 필요한 항목」에도 추가했다.

- PG 벤더 선정 기준 두 가지: **승인 API 가 인증 토큰 기준으로 멱등한가**(아니면 이 구조가 성립하지
  않는다), **결제 조회 API 가 있는가**(타임아웃 건을 판정할 유일한 수단)
- 실 PG 연동 시 필요한 것: 망 취소, 거래·정산 대사, 웹훅 수신. `PaymentGateway` 에 조회 메서드 추가
- 동시 승인 시 PG 중복 호출 — claim 패턴으로 막을 수 있으나 스키마 변경이 따라온다
- 잠금 순서 규칙(`point_charge` → `point_wallet`)이 문서와 주석에만 있다. 강제할 수단이 없다
- `PointChargeApprover.alreadyApprovedResponse` 가 트랜잭션 밖에서 조회한 엔터티를 인자로 받는다.
  현재는 단순 getter 만 써서 안전하지만 연관을 건드리면 `LazyInitializationException` 이 난다
