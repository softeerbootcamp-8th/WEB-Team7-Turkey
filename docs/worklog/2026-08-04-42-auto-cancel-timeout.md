# 배차 대기 시간 초과 자동 취소 + 취소 주문 포인트 환급 작업 기록

- 브랜치: `feature/42-req-ord-004-auto-cancel-timeout`
- 범위: backend
- 작성일: 2026-08-04

## 무엇을 만들었나

WAITING 상태로 5분을 넘긴 배송요청을 취소하고, 차감했던 포인트를 전액 환급한다. #42의 처리흐름
③이 가리키는 #38(환급 로직)이 미구현·다른 담당자였는데, 취소·환급이 "하나의 상위 트랜잭션"이어야
한다는 두 이슈의 비고 때문에 분리할 수 없어 이번 세션에서 같이 만들었다(githings → emes-g로
담당자 변경, 아래 「사람이 고른 선택」 1번).

원래 #42/#41/#101은 "주변 라이더 탐색 → 없으면 반경 확대 → 그래도 없으면 취소"라는 위치 기반
설계로 구상했지만, discussion #338(배차 위치 검색 방향을 "라이더 위치 기준 주변 주문 검색"
하나로 고정)로 #41/#101이 폐기되면서 #42는 순수 시간 기반 판정만 남았다. Redis GEO와 완전히
무관하다.

능동 스캐너(1분 주기, 방치된 주문 정리용 안전망)와 지연 만료(요청이 들어오는 그 순간 실시간으로
만료 여부를 다시 계산하는 방식) 두 접점에 같은 판정을 건다:

1. **주문 생성**(`DeliveryService.createDelivery`) — 고객의 기존 진행 중 주문이 이미 만료된
   WAITING이면, `active_customer_id` UNIQUE 제약에 막히기 전에 먼저 정리하고 새 주문을 만든다.
2. **배차 수락**(`RiderDeliveryRequestService.acceptDeliveryRequest`) — 스캐너가 아직 훑지 않은
   만료 주문을 라이더가 여전히 수락할 수 있는 창을 없앤다. 별도 예외 타입 없이, 정리 후
   조건부 UPDATE가 자연히 0행이 되어 기존 "이미 취소됨" 409 경로로 흘러간다.

### API

신규·변경 엔드포인트 없음. 기존 `POST /api/customer/deliveries`(#37/#40)와
`POST /api/rider/requests/{deliveryId}/accept`(#56)의 서비스 로직에 위 판정을 추가했다.

### 화면

해당 없음.

### 스키마 변경

해당 없음. `DeliveryOrder.cancel()`, `point_transaction`의 `ORDER_REFUND` 유형, `delivery_order`의
`active_customer_id` 생성 컬럼 등 필요한 것이 이미 다 있었다.

## 사람이 고른 선택

### 1. #38(환급 로직)을 이번 세션에서 같이 구현할지

- **선택지**:
  - (A) 이번 세션에서 같이 구현 — `payForOrder`와 대칭 구조라 비용 낮음 / githings에게는 완료 후
    알리고 이슈 정리(닫기·재배정)를 사람이 처리해야 함
  - (B) githings 완료까지 대기 — #42 중 리스크 없는 부분(스캐너 골격, 지연 만료 자리)만 먼저 짜고
    실제 환급 호출은 나중에 연결 / 대기 시간이 헛돎
- **고른 것**: (A)
- **근거**: 크기가 작고 어차피 한 트랜잭션으로 묶여야 해서 분리 자체가 부자연스러움. 이후 사용자가
  #38의 GitHub assignee를 emes-g로 직접 변경.
- **영향**: 브랜치·PR·작업기록 전부 #42/#38 공용(#37/#40 병합 당시와 같은 관례,
  `2026-08-01-37-delivery-create-with-point-payment.md` 참고). PR 병합 시 두 이슈가 자동으로
  닫히려면 `Closes #42`, `Closes #38`를 명시해야 한다 — `(#37)(#40)`처럼 나열만 하면 자동으로 안
  닫힌다는 것을 #37/#40 사례에서 실제로 확인함(#37만 CLOSED, #40은 이 세션 시작 시점까지 OPEN).

### 2. 타임아웃 값

- **물었던 것**: WAITING이 얼마나 지속되면 자동 취소할지.
- **선택지**: 3분(고객 경험 우선) / 5분(균형) / 10분(라이더 확보 시간 우선)
- **고른 것**: 5분
- **근거**: 균형점이라고 판단.
- **영향**: `DeliveryTimeoutService.WAITING_TIMEOUT`(상수, `Duration.ofMinutes(5)`).

### 3. 스캔 주기

- **물었던 것**: 능동 스캐너가 얼마나 자주 WAITING 전체를 훑을지.
- **선택지**: 30초(감지 지연 짧음, 부하 약간) / 1분(균형) / 직접 입력
- **고른 것**: 1분
- **근거**: MVP 규모에서 무난한 기본값이라고 판단.
- **영향**: `DeliveryOrderExpiryScheduler`의 `@Scheduled(fixedRate = 60_000)`.

### 4. 다중 인스턴스 분산 락 여부

- **물었던 것**: 인스턴스가 여러 대면 스캐너가 중복 실행되는데, 지금 막을지.
- **선택지**: (A) Redis 기반 분산 락(`SET NX PX`)을 지금 추가 / (B) 지금은 안 함 —
  조건부 UPDATE(`cancelIfWaiting`)가 이미 정합성을 보장하므로 중복 실행은 효율 문제일 뿐이고,
  현재 단일 인스턴스 운영 전제에서는 그 비용이 0이다
- **고른 것**: (B)
- **근거**: 이 대화 전체를 관통한 "실측 전에 최적화하지 않는다" 원칙과 같은 결.
- **영향**: 실제로 인스턴스가 2대 이상으로 늘어나는 시점에 재검토해야 한다(아래 「새로 생긴 미결
  사항」에도 등록).

### 5. #56(배차 수락)에도 같은 만료 판정을 걸지

- **물었던 것**: 스캐너가 아직 못 훑은 사이, 라이더가 이미 논리적으로 만료된 주문을 여전히
  수락할 수 있는 구멍을 지금 막을지.
- **선택지**: (A) 지금 같이 막음 — 비용 낮고 명백한 정합성 구멍 / (B) 범위 밖으로 미룸
- **고른 것**: (A)
- **근거**: "만료 여부는 항상 실시간으로 재계산해서 그 요청 순간에 처리한다"는 원칙을 재주문
  흐름에만 적용하고 수락 흐름에 안 거는 것은 일관성이 없다고 판단.
- **영향**: `DeliveryTimeoutService.cancelIfExpired(Long orderId)` 신설, `acceptDeliveryRequest`
  맨 앞에서 호출.

### 6. 고객이 "만료됐다"는 사실 자체를 능동적으로 알 수 있게 할지

- **물었던 것**: 지연 만료가 재주문 시도라는 좁은 접점에만 걸려 있는데, 고객이 그냥 기다리기만
  해도 만료·환급 사실을 확인할 방법이 필요하지 않은지.
- **선택지**: (A) #44/#46(주문 상세·상태 조회) 등을 지금 최소 구현해서 접점을 만듦 / (B) 그
  화면들이 아직 없으니 지금은 범위 밖으로 두고, 나중에 그 이슈들이 구현될 때 같은 판정
  (`expireIfStale`/`cancelIfExpired`류)을 적용하도록 기록만 남김
- **고른 것**: (B)
- **근거**: #44/#46 자체가 이 이슈 범위 밖이고, 지금 만들면 이슈 범위를 크게 벗어남. 재주문 흐름은
  이미 지연 만료로 창이 없으므로(같은 트랜잭션 시퀀스), "환불받고 재주문 가능한 상태"라는 최우선
  전제 자체는 이미 충족된다 — 남는 것은 "고객이 스스로 상태를 조회했을 때도 즉시 정확해야 한다"는
  별도 요구인데, 그 조회 창구 자체가 없다.
- **영향**: `CLAUDE.md`의 「확인이 필요한 항목」에 등록(아래 참고). 특히 포인트 잔액 조회
  (`CustomerPaymentService.getPointBalance`)에 이 판정을 걸려면 payment → order 의존이 생겨
  "order → payment 의존 방향 고정" 확정 결정과 정면으로 충돌(순환 참조로 기동 실패)한다는 것도
  같이 남겨, 나중에 이 판정을 조정할 위치(더 위 레이어)를 다시 설계해야 한다는 것을 명시했다.

## 스스로 판단한 것

- **패키지 위치**: `DeliveryTimeoutService`/`DeliveryOrderExpiryScheduler`를 `order/service`에
  뒀다. GEO와 무관해진 뒤로는 `matching` 패키지에 넣을 이유가 없고, `DeliveryService`가 이미
  주문+포인트를 오케스트레이션하는 자리라 같은 결.
- **조건부 UPDATE 재사용**: `cancelIfWaiting`을 `assignIfWaiting`과 똑같은 ADR-006 패턴(WHERE
  status='WAITING', 영향 행 수로 판정)으로 만들었다. 배차 확정과 자동 취소가 동시에 벌어져도
  하나만 성공한다는 #42 성공 조건이 이 패턴 하나로 보장된다 — 동시성 통합 테스트로 실증했다.
- **환급 requestKey**: 새로 만들지 않고 주문의 요청 멱등키를 그대로 썼다. V18이 `point_transaction`
  유니크를 `(request_key, transaction_type)`으로 완화해 둔 게 정확히 이 용도라고 판단.
- **`REQUIRES_NEW` 사용**: 지연 만료·`cancelIfExpired`(#56용) 둘 다 호출자의 트랜잭션과 분리해
  독립 커밋한다. 만료 정리는 호출자(새 주문 생성, 배차 수락 시도)의 성공·실패와 무관하게 이미
  옳은 정리라고 판단했다. 다른 빈에서 호출해야 프록시가 이 전파 속성을 인식한다는 점을 항상
  같이 적어 뒀다(자기 호출 함정, 이 코드베이스에 이미 있던 관례).
- **스캐너와 실제 취소 로직을 별도 빈으로 분리**: `DeliveryOrderExpiryScheduler`(스캐너, `@Scheduled`
  만)와 `DeliveryTimeoutService`(취소·환급 실행)를 나눴다. 스캐너 메서드 자체에 `@Transactional`을
  안 둬야 주문 하나의 실패가 나머지를 막지 않는데, 그러려면 `cancelAndRefund`를 자기 호출이 아닌
  다른 빈의 프록시로 불러야 그 메서드의 `@Transactional`이 실제로 걸린다.
- **"고객에게 배차 실패 알림 전송"(#42 처리흐름 ⑤)**: 로그(`log.info`)로만 남겼다.
  `member_notification`이 아직 없고(CLAUDE.md 확정 결정: 2·3차 MVP 이후), 임의로 앞당기지 않기로
  판단했다.

### 검증하지 못한 것

- **`@Scheduled(fixedRate = 60_000)`가 실제로 60초마다 도는지**: 자동화된 테스트에서 60초를
  기다리는 대신, 스캐너가 부르는 조회(`findByStatusAndRequestedAtBefore`)와 취소 로직
  (`cancelAndRefund`)을 직접 호출해서 검증했다. 스케줄러 자체의 트리거 타이밍은 로컬에서
  `bootRun`으로 눈으로 확인했다.
- **브라우저 E2E**: 화면 변경이 없는 백엔드 전용 이슈라 대상이 아니다.

## 새로 생긴 미결 사항

- 고객이 재주문·배차 수락 시도 없이 그냥 기다리기만 하는 경우, 실제 취소·환급까지 최대 스캔
  주기(1분)만큼 창이 남는다. 이번 세션에서 "감내 가능한 백스톱"이라고 명시적으로 확정하지는
  않았다 — 정밀 타이머(옵션 A, 위 「일부러 하지 않은 것」) 도입 여부는 미결.
- 고객이 자기 주문의 "만료됨" 상태를 능동적으로 조회할 방법이 없다(#44/#46 미구현). 그 화면들이
  생기면 이 이슈가 만든 `DeliveryTimeoutService.cancelIfExpired`류 판정을 같은 원칙으로 적용해야
  한다. 포인트 잔액 조회에 적용하려면 payment → order 의존이 생겨 "order → payment 의존 방향
  고정"과 충돌하므로, 그 조정 로직을 어느 레이어에 둘지 별도 설계가 필요하다.
