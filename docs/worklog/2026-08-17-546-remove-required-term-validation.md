# 회원가입 필수 약관 검증 제거 작업 기록

- 이슈: [#546](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/546)
- 브랜치: `feature/546-remove-required-term-validation`
- 범위: backend
- 작성일: 2026-08-17

## 무엇을 만들었나

배포 환경에서 회원가입이 "필수 약관에 모두 동의해야 합니다"(400)로 막히는 버그를 고쳤다.
프론트(고객/라이더 회원가입 화면)는 약관 체크박스 UI 없이 항상 `agreedTermIds: []`를 보내는데,
백엔드 `CustomerSignupService`/`RiderSignupService`의 `resolveAgreedTerms`는 여전히 활성 필수
약관이 하나라도 있으면 400을 던지고 있었다. 두 서비스에서 "필수 약관 미동의 → 400" 검증 블록만
제거했다. "존재하지 않는 약관 ID → 400" 검증과 동의 이력 저장 로직은 그대로 남겼다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/customer/signup` | 필수 약관 미동의여도 가입 허용 (기존 문서 문구도 함께 수정) | 409(중복), 400(존재하지 않는 약관 ID·형식 오류) |
| POST | `/api/rider/signup` | 위와 동일 | 위와 동일 |

### 화면

해당 없음. 프론트는 이미 `agreedTermIds: []`를 고정 전송하는 상태라 변경하지 않았다.

### 스키마 변경

해당 없음. `term`/`member_term_agreement` 테이블·엔터티는 유지한다(향후 #72 재개 대비).

## 사람이 고른 선택

### 1. 정책 방향: 백엔드 검증 제거 vs 약관 동의 UI 원복

- **물었던 것**: 이슈 본문이 제시한 두 방향(①백엔드 필수 약관 검증 제거 vs ②#72를 다시 열어 프론트
  약관 체크박스 UI·목록 조회 API를 구현) 중 어느 쪽으로 갈지.
- **선택지**:
  - (A) 백엔드 필수 약관 검증 제거 — 코드·프론트·DB가 이미 "약관 미사용" 상태로 수렴해 있어 변경
    범위가 작다. 단, `#25` 명세의 "필수 약관 미동의 예외 처리" 요구와는 어긋난다.
  - (B) 약관 동의를 실제로 받는 방향으로 원복 — `#25` 승인 명세를 그대로 따르지만 `#72`를 다시
    열어 프론트 UI·목록 조회 연동을 새로 구현해야 해서 범위가 크다.
- **고른 것**: (A)
- **근거**: 이슈 코멘트에서 담당자(emes-g)가 "1번 방향으로 진행하려고 하고, 금방할 것 같다"고
  제안했고, 리뷰어(bigbell999)가 "1번으로 이미 수렴해 있다는 의견에 동의합니다"라며 팀 논의
  스크린샷(홍빈님 발언)을 근거로 승인했다(2026-08-17, 이슈 코멘트).
- **영향**: `Term`/`MemberTermAgreement` 관련 코드는 당장 정리 대상이 아니게 됐다 — 필수 약관
  검증만 없앴을 뿐 엔터티·테이블·동의 이력 저장 로직은 그대로 남아 있다. `#72`(약관 목록 조회
  API)를 다시 열 필요가 없어졌다.

## 스스로 판단한 것

- **"존재하지 않는 약관 ID" 검증은 유지**: `resolveAgreedTerms`에서 필수 약관 검증만 제거하고
  unknown term id 검증은 남겼다. 프론트가 항상 빈 리스트를 보내는 한 이 검증은 사실상 트리거되지
  않지만, 향후 다른 클라이언트가 잘못된 id를 보내는 경우의 방어 코드로 제거할 이유가 없었다.
- **`agreedTermIds` DTO 필드·`@NotNull` 제약은 그대로 유지**: 이슈가 요청한 건 "백엔드 검증 제거"이지
  "필드 제거"가 아니다. 필드를 없애면 Orval 생성 스키마(`turkeyQuickDeliveryAPI.schemas.ts`,
  수정 금지 파일)까지 건드려야 해서 범위를 넘어선다고 판단했다.
- **`@Schema`·`@Operation` 설명 문구를 함께 수정**: "필수 약관을 모두 포함해야 한다"/"필수 약관
  미동의는 400" 문구가 실제 동작과 어긋나게 되므로, 코드 검증 로직과 같은 커밋에서 문서 문구도
  고쳤다(springdoc이 유일한 API 계약 문서라 방치하면 다음 사람이 오해한다).
- **삭제한 테스트를 "성공 케이스"로 재작성**: 단순 삭제 대신 "필수 약관에 동의하지 않아도
  가입할 수 있다"는 이름으로 뒤집어, 이 완화된 동작이 회귀되지 않도록 고정했다. `RiderSignupServiceTest`에는
  `CustomerSignupServiceTest`에 이미 있던 "존재하지 않는 약관 ID" 테스트가 없어서 대칭적으로 하나
  추가했다.

## 일부러 하지 않은 것

- **운영 DB의 기존 `term` 행 정리(이슈의 "긴급 조치")**: 이슈는 "배포 DB에서 활성 필수 약관 행을
  `is_active=0`으로 내리거나 삭제"하는 즉시 언블록 조치를 별도로 요구했다. 이건 배포 DB 접근이
  필요한 운영 작업이라 이번 코드 변경과 분리했다 — 이유: 이 세션은 배포 DB 자격 증명·접근 권한이
  없고, 프로덕션 데이터를 직접 수정하는 작업은 코드 리뷰·머지 절차와 별개로 사람이 직접 확인하며
  수행해야 한다고 판단했다. 후속: 이슈 본문에 이미 조치 방법이 적혀 있으므로 별도 이슈 등록은
  하지 않았고, 담당자가 직접 수행해야 한다.
- **배포 DB에 term 데이터가 유입된 경로 확정**: 이슈 5번 항목이 "정확한 유입 경로는 배포 서버 접속
  이력을 확인해야 확정된다"고 이미 명시한 조사 항목이라, 코드 수정과 무관해 손대지 않았다.

## 테스트

| 층 | 파일 | 검증한 것 |
|---|---|---|
| 단위 | `CustomerSignupServiceTest.java` | 필수 약관 미동의여도 가입 성공(신규), 존재하지 않는 약관 ID는 여전히 400, 약관 검증 실패 시 인증 토큰 미소비(트리거를 unknown term id로 변경), 아직 발효 전/만료된 필수 약관은 원래도 통과 |
| 단위 | `RiderSignupServiceTest.java` | 필수 약관 미동의여도 가입 성공(신규), 존재하지 않는 약관 ID는 400(신규 추가) |
| E2E | `CustomerSignupE2ETest.java` | 필수 약관이 DB에 있어도 실제 HTTP 요청으로 200과 계정 생성 확인(기존 400 검증 테스트를 뒤집음) |
| E2E | `RiderSignupE2ETest.java` | 필수 약관이 DB에 있어도 200과 라이더 프로필 생성까지 확인(기존 400 검증 테스트를 뒤집음) |

```text

./gradlew test --tests '*CustomerSignupE2ETest' --tests '*RiderSignupE2ETest' → BUILD SUCCESSFUL (9 + 5 tests, 0 failures)
./gradlew test (전체) → BUILD SUCCESSFUL, 675 tests, 0 failures, 0 errors
```

### 검증하지 못한 것

- 실제 배포 DB에 필수 약관 행이 있는 상태에서 배포 환경 회원가입이 200을 반환하는지는 이 세션에서
  직접 확인하지 못했다(배포 환경 접근 없음). 로컬 E2E 테스트로 동일 조건(활성 필수 약관 존재 +
  빈 `agreedTermIds`)을 재현해 200을 확인했으므로 로직상으로는 동일하게 동작해야 한다.

  이슈 자체가 이미 요구한 별도 운영 작업이라 `CLAUDE.md`에 추가하지 않았다 — 담당자가 이슈를 보고
  직접 처리해야 한다.
