# 추적 API ETA 작업 기록

- 이슈: [#421](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/421) (Part of [#423](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/423))
- 브랜치: `feature/421-tracking-eta-route` (base: `feature/420-osrm-routing-client`)
- 범위: backend
- 작성일: 2026-08-07

## 무엇을 만들었나

추적 스냅샷 API가 항상 `null`로 두던 `estimatedArrivalAt`을 채운다. 출발점은 Redis의 라이더 최신 위치,
도착점은 배송 상태에 따라 픽업지 또는 도착지이며, 소요 시간은 #420이 만든 `RoutingClient`(OSRM)로
구한다. 산정 실패는 전부 그 필드만 `null`인 200이다.

**이슈 범위에서 경로 좌표(`routePath`)를 뺐다**(사람 확인, 2026-08-07 — 아래 「사람이 고른 선택 4」).
한 번 구현했다가 걷어낸 것이라 그 판단 과정을 그대로 남긴다.

**전제**: 이 브랜치는 `dev`가 아니라 `feature/420-osrm-routing-client` 위에 있다. `RoutingClient`가
아직 `dev`에 없기 때문이다 — #420이 먼저 머지돼야 한다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| GET | `/api/customer/deliveries/{deliveryId}/tracking` | 응답의 `estimatedArrivalAt`을 채움(필드는 원래 있었다) | 404(없음·타인 것) / 409(추적 불가 상태) / 500(예상 운임 없음) — **ETA 산정 실패는 실패 응답이 아니다** |

### 화면

해당 없음(백엔드 범위). Orval 타입만 재생성했고 화면 연결은 #422다.

### 스키마 변경

해당 없음.

## 사람이 고른 선택

### 1. 어느 구간의 ETA인가

- **물었던 것**: 픽업 전(`ASSIGNED`·`MOVING_TO_PICKUP`)에도 최종 도착지까지의 ETA를 보여줄 것인가.
- **선택지**:
  - (A) 현재 향하는 지점까지만 — 라우팅 호출 1회, 포트 변경 없음 / 픽업 전 고객은 물건 도착 시각을 모른다
  - (B) 항상 최종 도착지까지 — 고객이 실제로 궁금한 값 / 호출 2회 또는 `RoutingClient`에 경유지 인자 추가(#420 재수정), 게다가 픽업 소요(수령·대기) 시간의 산정 근거가 없어 결국 낙관적 추정이다
- **고른 것**: (A)
- **근거**: 추가 비용을 들여도 정확해지지 않는다 — 픽업 소요 시간을 0으로 두는 순간 (B)의 값도
  추정이고, 그 오차는 구간을 늘려서 줄일 수 있는 종류가 아니다.
- **영향**: 프론트(#422)는 `status`를 보고 이 ETA를 "픽업 예정"과 "도착 예정"으로 나눠 표시해야 한다.
  응답만 보고는 어느 지점의 시각인지 알 수 없다.

### 2. 라이더 최신 위치가 없을 때

- **물었던 것**: 배차 직후(첫 위치 미전송)·Redis TTL 10분 만료로 출발점을 모를 때.
- **선택지**:
  - (A) ETA를 `null`로 — 없는 값을 지어내지 않는다 / 화면이 한동안 비어 있다
  - (B) 픽업지를 출발점으로 대체 — 항상 뭔가 보여준다 / 라이더가 픽업지에 있다는 보장이 없어 크게
    과소평가하고, **픽업 전 상태에서는 출발=도착이 되어 "지금 도착"이라는 명백히 틀린 값**이 된다
- **고른 것**: (A)
- **근거**: 틀린 ETA는 없는 ETA보다 나쁘다. 화면이 그것을 약속으로 취급한다.
- **영향**: 배차 직후 짧은 구간(라이더의 첫 위치 전송 전, BUSY 기준 최대 5초)과 라이더 앱이 죽은
  구간에는 ETA가 비어 있다. 프론트는 이 필드가 `null`인 200을 정상 상태로 다뤄야 한다.

### 3. 경로 좌표 표현 — 4번 결정으로 무효가 됨

- **물었던 것**: GeoJSON `[lng, lat]`를 그대로 흘릴지, 이름 붙은 객체로 변환할지.
- **고른 것**: `{latitude, longitude}` 객체 배열. 근거는 조용히 틀리는 실수를 필드 이름으로 막는
  것이었다(#420이 `Coordinate`를 (위도, 경도)로 고정한 것과 같은 이유).
- **그런데 4번에서 경로 필드 자체를 뺐다.** 이 결정은 나중에 경로를 다시 실을 때 그대로 되살린다 —
  그때 이 논의를 반복하지 않기 위해 지우지 않고 남긴다.

### 4. 경로 좌표를 응답에 실을 것인가 (구현 후 철회)

- **물었던 것**: "고객에게 경로를 보여주기보다 ETA만 알려줘도 될 것 같은데" — 이슈의 구현 범위에
  적힌 `routePath`를 뺄지.
- **선택지**:
  - (A) 빼기 — 응답이 작아지고 #422 작업량이 준다 / 이슈·부모 이슈에 적힌 범위를 줄이는 것
  - (B) 필드는 두고 프론트가 무시 — 나중에 필요할 때 이미 있다 / **아무도 안 쓰는 필드가 계약에
    남는다.** 나중에 빼려면 프론트를 깨는 방향의 변경이 된다
- **고른 것**: (A) — "여기는 경로를 빼자 어쨋든"
- **근거**: 계약에서 안전한 방향은 **추가**지 제거가 아니다. 지금 안 쓰는 필드를 실어 두는 것보다,
  화면(#422)이 실제로 선을 요구할 때 필드를 더하는 편이 되돌리기 쉽다. 덧붙여 #423이 리스크로 적어
  둔 "마커는 SSE로 5초, 경로선은 폴링으로 1분 → 라이더가 경로를 벗어난 것처럼 보인다"는 문제도
  그리지 않으면 발생하지 않는다.
- **영향**: `RoutePointResponse`와 `DeliveryTrackingResponse.routePath`를 삭제하고 Orval을 다시
  생성했다. **OSRM 호출은 그대로다** — 한 번 부르면 소요시간과 경로가 함께 오므로 호출 수·지연은
  달라지지 않고, `DeliveryRouteEstimator`도 `Route`를 그대로 돌려준다(호출자가 `duration()`만 쓴다).
  #421 이슈 본문의 구현 범위 체크리스트("경로 좌표 필드 추가")와 부모 #423의 제목이 실제 구현과
  어긋난 상태이므로, 이슈 쪽 정리가 필요하다.

## 스스로 판단한 것

- **`order` 서비스가 `location` 리포지토리를 직접 주입받는다** — 이슈가 "패키지 의존 방향을 확인하라"고
  한 항목이다. 근거: `location → order` 서비스 의존이 이미 있지만(`CustomerLocationQueryService` →
  `DeliveryTrackingAccessService`) `RiderLocationRepository`는 `order`를 전혀 참조하지 않아 **스프링 빈
  순환이 생기지 않는다.** Boot 3.4는 빈 순환이면 기동이 실패하므로 그게 실질 기준이다.
  포트 인터페이스를 `order`에 새로 뚫는 대안은 구현체가 하나뿐이라 지금은 간접층만 는다.
- **`getTracking`에서 `@Transactional`을 걷어냈다** — 라우팅 호출이 최대 1초(연결 300ms + 읽기 700ms)인데
  트랜잭션 안에 두면 그만큼 DB 커넥션이 잠긴다. 백업 폴링이 1분 주기(#422)라 동시 추적 수에 비례한다.
  대신 준영속 엔터티의 지연 로딩이 문제가 되므로 `findWithAssignedRiderById`(join fetch)를 새로 만들었다.
  대가: 세 번의 읽기가 각자 다른 스냅샷을 본다(표시용 조회라 감내. 원래도 주문 행을 두 번 읽었다).
- **ETA 기준 시각은 응답 시각이다**(라이더 위치의 측정 시각이 아니라). 측정 시각을 쓰면 위치가 오래됐을 때
  이미 지나간 시각을 도착 예정으로 내려보낸다. OSRM 소요 시간이 실시간 교통정보 없는 자유흐름 기준이라
  애초에 그 정도 정밀도를 따질 값이 아니다.
- **Redis 조회 실패를 "위치 없음"으로 흡수한다.** 폴링 API(`CustomerLocationQueryService`)는 같은 실패를
  503으로 올리는데, 그쪽은 위치를 주는 것이 유일한 목적이라 실패를 숨기면 화면이 옛 좌표를 계속 믿는다.
  추적 스냅샷은 위치가 부수적 입력이라, 예외를 올리면 상태·타임라인까지 못 그리게 된다.
- **경로 산정을 별도 컴포넌트(`DeliveryRouteEstimator`)로 뺐다.** `DeliveryTrackingQueryService`에 두면
  "구간 선택" 규칙이 응답 조립 코드에 섞여 단위 테스트에 스프링이 필요해진다.

## 일부러 하지 않은 것

- **경로 결과 캐시** — 같은 주문을 1분마다 조회할 때마다 OSRM을 새로 부른다. 부하 테스트 전에는 캐시
  키(주문 + 라이더 위치 반올림?)와 TTL을 정할 근거가 없다. 후속: 미등록
- **예상 경로 좌표 응답** — 위 「사람이 고른 선택 4」. 후속: #422에서 화면이 선을 요구하면 필드 추가
- **경로 이탈 감지·재계산 트리거** — 경로를 응답에 싣지 않기로 하면서 이 문제도 함께 사라졌다
  (#423의 "경로선과 마커의 갱신 주기가 다르다" 리스크). 경로를 다시 실으면 되살아난다
- **`distanceMeters` 응답 노출** — `Route`에 있지만 이슈가 요구하지 않았고, 요금은 직선거리 기반 정책이
  정본이라 화면에 두 개의 거리가 생기는 혼선만 만든다. 후속: 미등록
- **완료·취소된 배송의 경로** — 게이트가 409로 막아 애초에 이 API에 오지 않는다(#79부터의 성질).

전체 스위트는 돌리지 않았다 — 이 개발 PC에서 Tomcat 바인드 실패로 무작위 실패하는 문제가 있어
(CLAUDE.md 「확인이 필요한 항목」) 영향받는 클래스만 골라 돌렸다.

E2E의 "경로 서버 장애"는 흉내가 아니라 실제 상황이다 — 테스트 프로파일의 `routing.base-url`이
아무도 듣지 않는 `localhost:1`이라 연결이 실제로 거부된다(#420이 그렇게 정해 뒀다).

통합 테스트에서 성공 경로를 지나려면 `RoutingClient`를 `@MockitoBean`으로 바꿔야 했다. 실제 OSRM은
개발 PC·CI 어디에서도 닿지 않기 때문이다(#416: WAS 보안그룹 전용). 이 저장소에서 `@MockitoBean`을
쓰는 첫 테스트다.

### 검증하지 못한 것

- **배포된 OSRM과의 통신**은 여전히 검증하지 못했다(#420에서 남긴 공백 그대로). 다만 이번에 로컬
  PoC 컨테이너(`osrm-seoul-city`, #407)에 직접 질의해 **응답 구조가 `OsrmResponse` 매핑과 일치하고
  `overview=simplified`가 강남→시청 구간에서 14개 좌표를 준다는 것**은 확인했다. 배포 서버가 같은
  extract·같은 버전이라는 전제에서만 유효하다.
- **실제 ETA 정확도**(자유흐름 기준값이 실제 도착 시각과 얼마나 벌어지는지)는 측정하지 않았다.
- **동시 추적 다수에서의 응답 지연** — 트랜잭션을 걷어낸 효과와 캐시 부재의 비용은 부하 테스트 몫이다.

## 새로 생긴 미결 사항

- **ETA가 어느 지점의 시각인지 응답만으로는 알 수 없다.** 프론트가 `status`로 구분해야 한다 —
  필드를 나누거나(`pickupEtaAt`/`arrivalEtaAt`) 대상 지점을 함께 내리는 대안은 화면(#422)에서 실제로
  헷갈리는지 보고 판단한다.
- **경로 캐시가 없어 조회마다 OSRM을 부른다.** 1분 폴링 × 동시 추적 수만큼 호출이 나간다.
- **이슈 본문과 구현이 어긋나 있다.** #421의 구현 범위에 "경로 좌표 필드 추가"가, 부모 #423의 제목에
  "예상 경로 표시"가 남아 있는데 실제로는 ETA만 만들었다. 이슈 코멘트나 본문 정리가 필요하다.
- **추적 API가 이제 외부 의존성을 갖는다.** 백오프(#420)가 연속 3회 실패 시 호출을 건너뛰지만,
  그 앞의 세 번은 각각 최대 700ms 지연된다.
