## 무엇을 만들었나

`CustomerPointApi` 에 계약만 선언돼 있고 구현체가 `return null` 이던 충전 요청을 채웠다.
금액 검증 → 멱등키로 기존 요청 확인 → `point_charge` PENDING 저장까지다. **잔액은 변하지 않는다** —
지갑 증가와 원장 기록은 승인(confirm) 몫이라 이 메서드는 지갑을 조회조차 하지 않는다.

실 PG 연동 자리는 `PaymentGateway` 포트로 뚫어만 뒀다(인터페이스 1개, 구현체 없음). MVP 는 모의
결제라 이 흐름에서 PG 호출이 0회다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/customer/points/charges` | 충전 요청을 PENDING 으로 생성 | 400 금액 범위·단위 위반 / 409 같은 멱등키 동시 요청 |

`CustomerWebMvcConfig` 의 `addPathPatterns` 가 `"/api/customer/points"` 뿐이어서 하위 경로가 세션
인터셉터를 타지 않던 것을 함께 고쳤다(`/api/customer/points/**` 추가). 그대로 두면 이 엔드포인트는
`AuthenticatedCustomer` 를 못 받아 400 으로 죽는다.

### 화면

해당 없음. `customer/_authed/points/charge.tsx` 는 여전히 정적 목업이고 Orval 훅 연결은 하지 않았다.

### 스키마 변경

해당 없음. `V6__create_point_charge.sql` 과 `uk_point_charge_customer_request` 를 그대로 쓴다.

## 사람이 고른 선택

### 1. 결제모듈에 만들 "API 인터페이스"의 정체

- **물었던 것**: 컨트롤러 계약을 보강할 것인가, 외부 PG 연동 포트를 새로 만들 것인가
- **선택지**:
  - (A) PG 연동 포트 신설 — 실 PG 붙일 때 구현체만 교체 / 지금 당장 쓰이지 않는 코드가 생김
  - (B) 컨트롤러 계약 보강 — 새 파일 없음 / 이미 `CustomerPointApi` 에 계약이 있어 할 일이 적음
  - (C) 둘 다 — 변경 범위가 넓어짐
- **고른 것**: (A), 산출물은 **인터페이스 파일만**(모킹 구현체는 다음 단계)
- **근거**: 컨트롤러 계약은 이미 존재하므로 없는 것은 "결제모듈 경계"였다
- **영향**: `payment/service/PaymentGateway.java`. 벤더 중립 최소 스펙(prepare/confirm/cancel)을
  택해서, 실 PG 를 붙일 때 포트와 벤더 API 사이 매핑 코드가 한 겹 필요해진다 — 그 비용은 구현체 안에 갇힌다

### 2. `PaymentGateway.prepare()` 를 남길지

- **물었던 것**: 토스페이먼츠류는 준비 단계에 서버-투-서버 호출이 없는데 이 메서드가 필요한가
- **선택지**:
  - (A) 제거 — 지금 없는 단계를 미리 상정하지 않음 / 카카오페이류로 가면 다시 추가
  - (B) 유지 — 벤더 선택지를 열어둠 / 토스로 가면 아무 일도 하지 않는 메서드가 됨
- **고른 것**: (B) 유지
- **근거**: 벤더가 미정이다
- **영향**: 카카오페이류는 `ready` 호출이 필수라 이 메서드가 있어야 하고, 토스류는 구현체가 외부 호출
  없이 값만 조립한다. 그 차이를 javadoc 에 적어 뒀다

### 3. 동시 재전송을 409 로 거부할지, 같은 응답을 줄지

- **물었던 것**: 멱등키가 완전 동시에 들어왔을 때 패자에게 무엇을 줄 것인가
- **선택지**:
  - (A) 409 유지 — 구조 단순 / 멱등성 관점에서는 패자도 같은 응답을 받아야 맞음
  - (B) 삽입만 별도 트랜잭션으로 떼고 실패 후 재조회 — 진짜 멱등 / 빈 하나 추가, 트랜잭션 경계 둘로 분리
- **고른 것**: (A) 유지 + 프론트 1회 재시도
- **근거**: 아래 실측 결과(8스레드 동시 요청에서 6건이 선조회로 흡수, 2건만 409). 실전 따닥 클릭은
  밀리초 단위로 완전히 겹치지 않으니 409 비율이 이보다 낮고, 준비 단계는 잔액을 건드리지 않아
  실패의 대가가 작다
- **영향**: 원자성이 정말 중요한 곳은 잔액이 움직이는 승인 단계다. 그쪽은 별도로 설계한다

## 스스로 판단한 것

- **`PaymentGateway` 를 `payment/gateway` 가 아니라 `payment/service` 에 둠** — 근거: 모킹 구현체만
  있는 외부 연동 포트라는 점에서 `member/service/SmsSender` 와 같은 역할이고, 팀에 이미 그 선례가 있다
- **준비 단계에서 지갑을 조회하지 않음** — 근거: 잔액을 읽지도 쓰지도 않는다. 지갑은 회원가입 때 함께
  생기니 "지갑 없음"은 사용자 오류가 아니라 정합성 오류이고, 그 판정은 잔액을 실제로 쓰는 승인 단계 몫이다
- **`save` 가 아니라 `saveAndFlush`** — 근거: 지연 flush 로는 유니크 위반이 커밋 시점에 터져 `catch` 가
  잡지 못하고 500 으로 새어 나간다
- **유니크 위반 `catch` 안에서 재조회하지 않음** — 근거: 제약 위반 트랜잭션은 rollback-only 로 표시돼
  있어 같은 트랜잭션에서 추가 조회를 하면 커밋 시점에 다시 터진다
- **`memberRepository.getReferenceById`** — 근거: 세션 인터셉터가 이미 회원 존재·역할·상태를 확인했고,
  여기서는 FK 를 채우는 것이 목적이라 프록시 참조로 충분하다
- **금액 정책을 잠정값으로 고정**(1,000 / 1,000,000 / 1,000원 단위) — 근거: 이슈 처리흐름 ②가 검증을
  요구하는데 팀 합의 수치가 없다. 상수 세 개만 바꾸면 되도록 모아 뒀다. 서버를 화면 프리셋보다 넓게
  잡은 것은, 서버가 더 좁으면 프리셋이 곧바로 깨지기 때문이다
- **리포지토리 메서드명에 `Customer_Id` 밑줄** — 근거: `PointCharge` 에는 `customerId` 스칼라 필드가
  없어 연관 traversal 임을 명시해야 한다(`PointWalletRepository.findByMemberId` 는 실제 필드가 있는 경우)

## 일부러 하지 않은 것

- **`PaymentGateway` 모킹 구현체**: 이유: 이번 산출물을 인터페이스로 한정 — 후속: 미등록
- **충전 승인(`confirmPointCharge`)·거래 내역 조회**: 이유: 다른 이슈 범위. 같은 컨트롤러에 `return null`
  로 남아 있다 — 후속: 미등록
- **프론트 연동**: 이유: 이슈 처리흐름이 전부 서버 측이고 화면 이슈가 따로 있다고 판단 — 후속: 미등록
- **서버가 충전 요청번호를 생성**(이슈 문구 ③): 이유: 멱등키는 재시도 주체가 정해야 의미가 있다.
  서버가 발급하면 재전송을 식별할 방법이 없어 PENDING 이 중복 쌓인다. 대신 클라이언트 UUID 를 받는다
  — 후속: 리뷰에서 확인 필요
- **이미 PAID 인 키로 준비를 재요청할 때의 가드**: 이유: 발견은 했으나 이슈 범위 밖. 현재는 PAID 건을
  그대로 돌려주고, 프론트가 confirm 을 또 호출해 맥락 없는 409 를 보게 된다 — 후속: 미등록
- **`chargeRequestKey` 의 UUID 형식 검증**: 이유: 현재 `@Size(36)` 은 길이만 본다 — 후속: 미등록
- **E2E 테스트**: 이유: 시간. `CustomerPaymentControllerE2ETest` 는 전체 주석 처리 상태다 — 후속: 미등록

## 테스트

| 층 | 파일 | 검증한 것 |
|---|---|---|
| 단위 | `CustomerPaymentServiceTest` | PENDING 생성, 지갑 미접촉, 같은 키 2회 호출 시 1건, 다른 키는 2건, 유니크 위반 → 409, 금액 범위·단위 |
| 통합 | `CustomerPaymentServiceIntegrationTest` | auto increment PK·`@PrePersist` 의 `requestedAt` 실제 채움, 승인 컬럼 비어 있음, 순차 재전송 1건, **8스레드 동시 요청에서 1건만 남음** |
| E2E | 없음 | — |

단위 테스트의 멱등성 검증은 리포지토리 목을 스크립트가 아니라 **(고객, 멱등키) 저장소를 흉내 낸
인메모리 페이크**로 바꿔서 서비스를 실제로 두 번 호출한다. "기존 건이 있다고 스텁해 두고 한 번
호출"하는 형태는 분기 검증이지 멱등성 검증이 아니다. 페이크가 전부 뭉개서 나온 거짓 통과를 막기 위해
"키가 다르면 2건"을 대조군으로 붙였다.

실행 결과 (MySQL 8.4 / utf8mb4_0900_ai_ci / UTC — `docker-compose.yml` 과 같은 설정):

```text
./gradlew test → BUILD SUCCESSFUL, 40개 클래스 267개 테스트, 실패 0 / 오류 0 / 스킵 0

동시성 실측(임시 계측, 커밋에는 포함하지 않음):
[RACE] threads=8 success=6 failure=2 rows=1
       firstFailure=BusinessException: 이미 처리 중인 충전 요청입니다...
```

8건 중 6건은 승자가 커밋한 뒤 `SELECT` 가 실행돼 선조회 경로로 흡수됐고, 2건만 경쟁 구간에 들어갔다.
남은 행은 1건 — 부분 성공이 없었다. 선조회는 순차 재전송만 처리하고 동시성 방어는 유니크 제약이
한다는 것이 수치로 확인됐다.

### 검증하지 못한 것

- HTTP 레벨(세션 인터셉터 통과, 401, `@Valid` 400 변환)을 검증하는 E2E 가 없다. 특히 이 커밋이 고친
  **인터셉터 경로 패턴을 지키는 테스트가 하나도 없다** — 누가 `/**` 를 되돌려도 267개가 전부 통과한다
- 프론트가 실제로 이 API 를 호출하는 흐름(멱등키 생성·재사용 규칙)은 화면 미연결로 검증하지 못했다
- 실 PG 흐름은 `PaymentGateway` 구현체가 없어 검증 대상이 아니다

## 새로 생긴 미결 사항

아래 항목은 `CLAUDE.md` 「확인이 필요한 항목」에도 같은 내용을 추가했다.

- 충전 금액 정책(최소·최대·단위)이 잠정값 — "프리셋 화이트리스트"로 좁히는 선택지도 있음
- 동시 재전송 409 정책 — 실전에서 409 가 자주 발생하면 트랜잭션 분리 재검토
- 화면 결제수단(카카오페이·휴대폰)과 `PaymentMethod` enum(`CARD`·`BANK_TRANSFER`) 불일치.
  `ck_point_charge_method` 도 두 값만 허용한다 — enum 을 넓힐지 화면을 줄일지 미결
- 실 PG 연동 시 `prepare()` 필요 여부는 벤더에 따라 갈림(일단 포트에 유지)
- 이슈 입력값은 "충전 금액"뿐인데 API 는 `chargeRequestKey`·`paymentMethod` 를 필수로 받는다.
  계약 확장이라 리뷰 확인이 필요하다
