## 무엇을 만들었나

WAITING 주문의 논리적 만료(생성+5분)와 물리적 만료(스캐너가 실제로 취소) 사이 간극을, 클라이언트
타이머가 화면을 보고 있는 시점마다 스스로 판정해 기존 수동 취소 API(#47)를 대신 호출하는 방식으로
없앴다. 백엔드는 CANCELED 전이도 다른 다섯 전이(ASSIGNED~COMPLETED, #398)와 같은 SSE 채널로
발행하도록 보완했고, 프론트는 상세·추적 화면에 포커스 재조회를 추가해 세 겹의 방어선을 완성했다.

### API

기존 API 재사용, 신규 엔드포인트 없음.

| 메서드 | 경로 | 설명 | 비고 |
|---|---|---|---|
| PATCH | `/api/customer/deliveries/{id}/cancel` | 배송요청 취소(#47) | 변경 없음 — 클라이언트 타이머가 이 API를 대신 호출 |

### 화면

- `customer/_authed/deliveries/$deliveryId/`(상세), `.../tracking`(추적) 둘 다 `useWaitingExpiryTimer`
  훅을 붙였다. 두 화면 모두 이미 `detail.status`/`detail.requestedAt`을 갖고 있어 별도 조회 없음.
- 두 화면의 `useGetDelivery` 쿼리에 `refetchOnWindowFocus: true`, `staleTime: 0` 추가.

### 스키마 변경

해당 없음.

## 사람이 고른 선택

### 1. 간극을 어떻게 없앨 것인가 — SSE 인프라 vs 클라이언트 타이머

- **물었던 것**: Discussion #402에서 "다른 탭/기기가 못 받는 문제"를 SSE(#409/#410)로 풀어야 하는지,
  아니면 클라이언트 타이머만으로 충분한지.
- **선택지**:
  - (A) SSE CANCELED 발행 + WAITING 구독 허용을 필수 전제로 삼는다 — 인스턴스마다 즉시 반영되지만,
    당시 #409/#410이 미머지 상태라 그게 끝날 때까지 #402 자체를 못 시작한다.
  - (B) 클라이언트 타이머(마감 시각을 미리 알 수 있고, 취소 API가 시간 무관·멱등이라는 이 문제만의
    특수성 활용)를 주 메커니즘으로 삼고, SSE는 보완재로 둔다.
- **고른 것**: (B)
- **근거**: 타이머가 mount·예약된 setTimeout·visibilitychange 세 지점에서 판정하면, "화면을 실제로
  보고 있는 모든 순간에는 이미 최신 판정이 끝나 있다"는 성질이 서지고, 이는 3번(스캐너 단독 감지)·
  4번(다른 인스턴스) 상황 대부분을 SSE 없이 닫는다. 이 트릭은 마감 시각을 클라이언트가 미리 계산할
  수 있는 이 문제(WAITING→CANCELED)에만 성립하고, 배차 이후 다른 전이(라이더 행동에 달림)에는
  일반화되지 않는다 — 그 영역은 여전히 #397·#432의 몫으로 남는다.
- **영향**: #402가 #409/#410/#432의 진행 상황과 완전히 독립적으로 진행될 수 있게 됐다.

### 2. 남은 잔여 간극(다른 인스턴스의 임의 시점 수동 취소)을 어떻게 메울 것인가

- **물었던 것**: 한 기기가 타이머 마감 이전(예: 2분)에 수동 취소하면, 같은 배송을 보는 다른 기기는
  자기 타이머가 5분에 발화하기 전까지 최대 3분간 모른다 — 이 구멍을 메울지, 메운다면 어떻게.
- **선택지**:
  - (A) `refetchOnWindowFocus` + `staleTime: 0`을 기존 `useGetDelivery`에 추가 — 서버 변경 없음,
    포커스 전환마다 이미 쓰던 단일 행 조회를 한 번 더 부른다.
  - (B) 상태만 가볍게 확인하는 새 엔드포인트를 만든다.
- **고른 것**: (A)
- **근거**: `DeliveryDetailQueryService.getDetail`이 이미 단순 단일 행 조회 세 번(주문·운임·인증)뿐이라
  "가벼운 확인"을 새로 만들어도 얻는 게 미미하고, 오히려 상태가 실제로 바뀐 경우엔 (B)가 상태 확인
  + 전체 재조회로 왕복이 하나 더 늘어난다. 포커스 전환 자체가 저빈도 이벤트라 비용 걱정도 크지 않다.
- **영향**: 서버 코드 변경 없이 프론트 쿼리 옵션 한 줄로 해결. 남는 잔여(둘 다 계속 포그라운드로만
  지켜보는 경우)는 최대 5분 상한이 있어 감내 가능하다고 판단했다(사람 확인).

### 3. CANCELED SSE 발행을 추가할 것인가

- **물었던 것**: 위 1·2번으로 필요조건은 충족되는데, 그래도 보완재로 SSE를 마저 갖출지.
- **고른 것**: 갖춘다 — `DeliveryService.cancelDelivery`(수동취소)·`DeliveryTimeoutService.cancelAndRefund`
  (자동취소 스캐너) 두 경로에 `TrackingPublisher.publishStatus(deliveryId, CANCELED, ...)` 추가.
- **근거**: #402 논의 중 "SSE가 보완적으로 해결해주긴 한다"고 이미 언급했던 방향을 마저 완성한 것 —
  필수조건은 아니지만, 연결이 살아있는 인스턴스에는 최대 5분(포커스 재조회 상한)보다 훨씬 빠르게
  반영된다.
- **영향**: `#409`/`#410`이 이미 dev에 머지돼 있어(WAITING 구독 허용·`publishStatus` 인프라) CANCELED
  발행만 추가하면 됐다. `#397`/`#398` worklog가 남겨둔 "CANCELED 발행 여부 재검토" 미결이 이걸로 해소.

## 수동 검증 중 발견한 치명적 버그 — `requestedAt` 타임존 오파싱

로컬 환경(백엔드·프론트 직접 기동 + 시딩 데이터)에서 `c1`으로 실제 배송요청을 만들어 확인하는
과정에서, **생성 직후 0.1초 만에 자동취소되는 버그**를 발견했다.

- **증상**: 새 주문을 만들자마자 "배송이 취소됐어요" 화면이 뜸. DB 확인 결과
  `requestedAt="2026-08-11T02:55:20.5"`, `canceledAt="...02:55:20.639"` — 0.139초 차이.
  스캐너(60초 주기)가 낼 수 있는 간격이 아니라 클라이언트 타이머가 마운트 직후 바로 쏜 것.
- **원인**: 백엔드는 `requestedAt`을 UTC로 만들지만 직렬화 시 `Z`/오프셋을 안 붙인다
  (`"2026-08-11T02:55:20.5"`). `decideExpiry` 안에서 이 문자열을 `new Date(requestedAt)`로 직접
  파싱했는데, 타임존 지정자가 없는 date-time 문자열은 JS 명세상 **브라우저 로컬 타임존**으로
  해석된다. 로컬 환경이 KST(UTC+9)라, UTC 02:55를 "KST 02:55"로 오인 → 그 순간의 진짜 UTC 순간을
  9시간 전(전날 17:55)으로 계산 → `expiresAt`도 9시간 이르게 잡혀 마운트 즉시 "이미 만료"로 판정됨.
- **왜 유닛 테스트가 못 잡았나**: 처음 작성한 테스트가 `requestedAt`에 `Z`를 붙인 문자열만 썼다
  (`'2026-08-10T00:00:00.000Z'`) — 실제 백엔드가 내려주는 형식(`Z` 없음)과 달라 이 버그의 조건을
  재현하지 못했다.
- **고친 것**: 이미 저장소에 있던 `shared/lib/datetime.ts`의 `parseServerDate`(같은 문제를 이미
  문서화해 둔 기존 유틸)를 재사용하도록 `decideExpiry`를 수정. 직접 `new Date()`를 쓰지 않는다.
  파싱 실패 시에도 만료로 오판해 잘못 취소하지 않도록 `pending`으로 안전하게 처리(스캐너가 최종
  백스톱).
- **회귀 테스트 추가**: `Z` 없는 문자열이 UTC로 정확히 해석되는지, 파싱 불가능한 값이 안전하게
  `pending`을 반환하는지 두 케이스를 `useWaitingExpiryTimer.test.ts`에 추가.
- **교훈**: 서버 시각을 다루는 새 코드를 짤 때는 매번 `parseServerDate`를 써야 한다는 게 이미
  `shared/lib/datetime.ts`의 관례였는데, 이 파일을 안 보고 새로 짜서 놓쳤다. 코드 리뷰나 향후
  체크리스트에 "서버 시각 문자열을 다루는 새 코드가 `parseServerDate`를 거치는지" 항목을 넣을 만하다.

## 스스로 판단한 것

- **`publishStatus` 호출 위치**: 환급(`refundForCancel`) 직후, 로그 직전에 뒀다. `TrackingPublisher.
  publishStatus`가 활성 트랜잭션을 스스로 감지해 커밋 후로 발행을 미루므로(#428에서 고쳐진 그대로)
  메서드 안 어디에 둬도 안전하지만, 다른 상태 변경이 다 끝난 뒤라는 게 읽기에 자연스러워 그 위치를
  골랐다.
- **타이머 취소 사유 문구**: `AUTO_CANCEL_REASON`을 스캐너가 쓰는 문구("배차 대기 시간을 초과해
  자동 취소되었습니다.")와 똑같이 맞췄다 — 어느 쪽이 경쟁에서 이기든 고객이 보는 취소 사유가 같아야
  한다.
- **타이머를 새 API 없이 기존 취소 API로**: `decideExpiry`라는 순수 함수로 판정만 분리하고, 실제
  호출은 이미 있는 `useCancelCustomerDelivery`를 그대로 썼다. 서버 쪽 시간 판정 로직을 새로 안 만든
  이유는 문서 참고("2. 클라이언트 타이머의 정확한 동작 방식" 논의) — 취소 API 자체가 시간 무관·
  멱등이라 그 자리에서 새로 뭘 만들 필요가 없었다.
- **`onSettled`에서 무조건 쿼리 무효화**: 성공(200)이든 409(이미 배차됨)든 상관없이 `getGetDelivery`
  쿼리를 무효화한다 — 어느 쪽이든 화면이 최신 상태를 다시 그려야 하는 건 같다.

## 일부러 하지 않은 것

- **타이머 실패를 사용자에게 알리는 UI(확인 다이얼로그 등)**: MVP 단계에서 별도 확인 없이 조용히
  자동 취소하기로 결정함(사람 확인, 대화 중) — 케이스 1(수동 취소)과 결과가 같은 동작이라 굳이
  사용자 개입을 요구하지 않는다.
- **스캐너 스캔 주기(60초) 단축**: 타이머 도입으로 그 지연이 체감상 크게 줄어(타이머가 거의 항상
  먼저 처리) 지금 손댈 이유가 약해졌다. CLAUDE.md 기존 미결 항목 그대로 둔다.
- **다른 브라우저 탭(같은 기기)까지 `BroadcastChannel`로 즉시 동기화**: 검토했으나 다른 기기 간
  동기화는 결국 서버 푸시가 필요해 같은 문제의 부분집합만 풀어주므로 이번엔 넣지 않았다. 후속:
  미등록(필요성 재확인 전까지 보류).
- **`index.tsx`·`tracking.tsx`의 취소 후 동작 통일**: 상세 화면(`index.tsx`)은 수동 취소 성공 시
  목록으로 이동시키는데(`#47`/`#377`부터 있던 동작), 추적 화면(`tracking.tsx`)은 그 자리에서
  재조회만 하고 화면 이동이 없다. 이번 이슈가 만든 차이가 아니고, 수동 검증 결과 추적 화면에
  머무는 쪽이 오히려 자연스러워 굳이 통일하지 않았다(사람 확인). 후속: 미등록.

## 부수적으로 고친 것 — `#445` 이전 통합 테스트 컴파일·환경 오류

이 이슈를 시작하기 전, `dev`가 `#436`(Spring Boot 4.1 업그레이드)의 병합 오류로 컴파일 자체가 안 되는
상태였다(`TrackingPublisher.publish`가 없는 변수 `location` 참조). 별도 핫픽스 브랜치를 파서 조사하던
중 같은 원인(브랜치 병합 시점 불일치)에서 나온 문제 셋(컴파일 오류, `JsonNode` Jackson 3 타입 불일치,
`S3RiderDeliveryProofStorage`가 통합 테스트 프로필에서도 활성화되는 프로필 조건 오류)을 확인했고,
팀원(`githings`)이 이미 `#445`로 세 개를 모두 고쳐 올린 걸 발견해 그쪽을 리뷰·검증(전체 테스트 612개
직접 실행, 0 실패)만 하고 머지를 기다렸다. `#445`가 `dev`에 머지된 뒤 `feature/444`를 그 위로
rebase하고 이어서 진행했다 — 이 이슈 자체의 작업물은 아니라 위 절들에는 포함하지 않았다.
