선택하는 UI로, 정렬은 방향까지 고정된 3개 프리셋으로 계약을 좁혀서 구현했다(아래 "사람이

## 사람이 고른 선택

### 1. 요금·배송거리 범위 필터 — 범위(최소~최대) vs 한쪽 극단만

- **물었던 것**: `fareMin`/`fareMax`, `distanceMin`/`distanceMax`를 각각 범위(양쪽 다) UI로
  만들지, 한쪽만 만들지.
- **선택지**:
  - (A) 한쪽 극단만 — 요금은 최소만, 배송거리는 최대만.
  - (B) 이슈 원래대로 범위(최소~최대) 둘 다.
- **고른 것**: (A)
- **근거**: 라이더 입장에서 "너무 비싼 콜"이나 "너무 짧은 배송"을 피할 이유가 없다 — 돈을
  더 주는 콜, 이동이 적은 콜을 거부할 유인이 없다. 반대로 "너무 싼 콜"(fareMin)과 "너무 먼
  배송"(distanceMax)은 실제로 피하고 싶을 수 있다. 그래서 각 항목에서 라이더에게 실제로
  의미 있는 방향 하나씩만 남겼다. `fareMax`/`distanceMin` 백엔드 파라미터는 그대로 있지만
  이 화면에선 안 쓴다.
- **영향**: 이슈 원문("범위 입력 UI")보다 범위를 좁혔다. `#522`가 이미 두 파라미터 다 받게
  만들어 놨으므로 백엔드 변경은 필요 없었다.

### 2. 요금 프리셋 값 — 10,000/30,000/50,000

- **물었던 것**: 얼마를 기준값으로 잡을지.
- **선택지**:
  - (A) 로컬 시드 `FarePolicy`(기본요금 5,000+km당 1,000+할증 0~2,000) 실측 범위(6,000~
    37,000P)에 맞춘 8,000/10,000/15,000.
  - (B) 실제 유사 서비스(카카오T퀵 등) 감각에 맞춘 10,000/30,000/50,000.
- **고른 것**: (B)
- **근거**: 확인해보니 `fare_policy` 테이블은 Flyway로 스키마만 관리되고 실제 값을 넣는
  시드는 로컬 개발용(`reset-and-seed-local.sql`)뿐이라, 배포 환경에 어떤 요금 정책이 적용될지
  이 코드베이스만으로는 알 수 없었다 — (A)도 로컬 자리표시자에 맞춘 것일 뿐 실제 근거가
  아니었다. 실제 서비스 감각이 더 신뢰할 만하다고 판단함(사람 확인).
- **영향**: **요금 정책 자체가 아직 확정 안 됐다는 게 이번에 드러난 사실**이라 CLAUDE.md에도
  추가함(아래 "새로 생긴 미결 사항" 참고). 실제 정책이 정해지면 프리셋을 다시 조정해야 한다.

### 3. 정렬 기준 라벨 — "가까운 순"/"짧은 순" 대신 "픽업 가까운 순"/"배송 거리 짧은 순"

- **물었던 것**: 세그먼트 버튼 라벨을 뭐라고 쓸지.
- **선택지**:
  - (A) 짧게: "가까운 순"/"비싼 순"/"짧은 순".
  - (B) 풀어서: "픽업 가까운 순"/"요금 높은 순"/"배송 거리 짧은 순".
- **고른 것**: (B)
- **근거**: "가까운 순"·"짧은 순"은 라이더가 픽업거리(라이더→픽업지)와 배송거리(픽업→
  도착지)를 구분하지 못하면 무슨 뜻인지 알 수 없다 — 개발 중 대화에서도 이 둘을 헷갈렸던
  적이 여러 번 있었다(#509/#522 논의). 카드(`RequestCard`)가 이미 쓰는 "픽업"/"도착" 용어를
  그대로 가져와 일관성 있게 풀어 썼다.

### 4. 필터 영역 레이아웃 — 상단 그리드 확장

- **물었던 것**: 컨트롤이 5개(정렬·물품종류·픽업거리·요금·배송거리)로 늘어난 레이아웃을
  어떻게 할지.
- **선택지**:
  - (A) 기존 2열 그리드를 그대로 확장(정렬은 별도 한 줄, 나머지 4개는 2×2).
  - (B) 정렬만 상단에 두고 나머지는 "필터" 버튼으로 여는 별도 시트/패널로 분리.
- **고른 것**: (A)
- **근거**: 구현이 단순하고, 필터 개수가 아직 감당 가능한 수준이라고 판단함.

## 스스로 판단한 것

- **`buildNextRequestCursor`에 `sort` 매개변수를 추가함**(`(hasPosition, lastItem)` →
  `(sort, hasPosition, lastItem)`): 정렬 기준마다 커서 필드가 다르므로(FARE→afterFare,
  DELIVERY_DISTANCE→afterDeliveryDistanceMeters) 함수가 그 기준을 알아야 했다. 위치 유무만
  보던 기존 분기(DISTANCE 전용)를 sort 기준 분기로 일반화했다.
- **`FareMinFilter`/`DistanceMaxFilter` 타입을 `'ALL' | number`로 함**: 기존 `ItemFilter`가
  이미 쓰던 `'ALL'` sentinel 패턴을 그대로 재사용 — 새 규칙을 만들지 않고 일관성을 유지했다.
- **정렬·요금·배송거리 필터도 반경·좌표·물품종류와 같은 초기화 이펙트에 묶음**: 값이
  바뀌면 커서·누적 목록을 버리고 첫 페이지부터 다시 쌓는다(이슈에 명시된 요구사항).

## 일부러 하지 않은 것

- **`fareMax`/`distanceMin` UI**: 위 "사람이 고른 선택 1번" 참고. 백엔드 파라미터는 그대로
  살아있어 필요해지면 UI만 추가하면 된다.
- **물품 종류 다중 선택**: 이슈 범위 밖(`#522`에서 이미 단일 선택으로 확정).
- **컴포넌트 렌더 테스트**: 이 화면에 아직 React Testing Library 같은 인프라가 없어 순수
  함수(`buildNextRequestCursor`)만 단위 테스트하고, 나머지(필터 변경 시 리셋, 세그먼트
  버튼 상호작용 등)는 수동 브라우저 검증으로 대신했다(사용자 직접 확인).

## 새로 생긴 미결 사항

- **`fare_policy`의 실제 값(배포 환경에 어떤 요금 정책이 적용될지)이 확정돼 있지 않다.**
  Flyway는 스키마만 관리하고, 실제 값을 넣는 시드는 로컬 개발용뿐이다. 이번 요금 프리셋
  (10,000/30,000/50,000)은 실제 서비스 감각으로 잡은 잠정값이라, 요금 정책이 확정되면
  다시 조정해야 한다. CLAUDE.md에도 추가함.
