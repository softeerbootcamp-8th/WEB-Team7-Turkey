## 무엇을 만들었나

`GET /api/rider/requests`(콜 목록 조회, #55/#367)에 운임·배송거리 범위 필터, 정렬 방향, keyset
(커서) 페이지네이션을 추가했다. 정렬 기준(DISTANCE/FARE/REQUESTED_AT) 자체는 이미 #55 때부터
있었고, 이번에 새로 채운 건 범위 필터·방향·페이지네이션 세 가지다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| GET | `/api/rider/requests` | 콜 목록 조회 — `fareMin/fareMax`, `distanceMin/distanceMax`, `sortDirection`, `size`, `after*` 파라미터 추가 | 400 범위·페이지 크기·정렬 방향 오류 |

응답 형태가 `List<...>`에서 `{items, hasNext}`(`RiderDeliveryRequestPageResponse`)로 바뀌었다 —
프론트 연동이 아직 없어(이 API를 소비하는 화면 미구현) 하위 호환 문제는 없다.

해당 없음. 프론트 연동은 이 이슈 범위 밖이다.

## 사람이 고른 선택

### 1. 운임·배송거리 범위 필터를 어디서 거를까

- **물었던 것**: (A) 자바 메모리 필터(기존 반경 필터와 같은 구조) vs (B) SQL WHERE로 이관.
- **선택지**:
  - (A) 자바 메모리 필터 — 구현 간단, 기존 코드와 구조 일관. 다만 필터가 빡빡하면 페이지가
    요청한 size보다 적게 찰 수 있다(짧은 페이지).
  - (B) SQL 이관 — 페이지가 항상 가득 차는 걸 보장하지만, 반경(원) 판정은 여전히 자바 몫이라
    완전한 이관은 아니고 구현 범위가 커진다.
- **고른 것**: (A)
- **근거**: 반경 필터가 이미 이 구조(사각형 SQL 조회 → 원 보정은 자바)라, 운임·배송거리만
  SQL로 옮기면 필터링 로직이 두 층(SQL/자바)에 흩어져 오히려 일관성이 떨어진다. 짧은 페이지는
  감수하기로 함(사람 확인).
- **영향**: 결정 2번(페이지네이션 방식)과 직결된다 — 필터가 자바에 있으므로 페이지 자르기도
  자바에서 하는 게 일관적이다(아래 "스스로 판단한 것" 참고).

### 2. 페이지네이션 방식

- **물었던 것**: (A) offset(page&size) vs (B) keyset(커서).
- **선택지**:
  - (A) offset — 구현 쉬움. WAITING처럼 계속 바뀌는 목록에서는 페이지 사이에 항목이 추가·제거되면
    건너뜀·중복이 생길 수 있다.
  - (B) keyset — 목록이 바뀌어도 안전하지만, 정렬 기준마다 다른 커서 비교식이 필요하다.
- **고른 것**: (B)
- **근거**: 콜 목록은 다른 라이더의 수락·주문 취소·신규 주문으로 초 단위로 바뀌는 데이터라,
  offset의 건너뜀·중복 문제가 실제로 발생하기 쉬운 도메인이라고 판단함(사람 확인). 이 논의
  과정에서 "얼마나 자주 바뀌는 목록인가"가 offset 채택 여부를 가르는 기준이라는 걸 짚었다 —
  거의 안 바뀌는 참조 목록이었다면 offset도 무난했을 것이다.
- **영향**: 결정 1번과 합쳐져, 커서 비교(keyset)도 SQL이 아니라 자바에서 수행하게 됐다(아래
  "스스로 판단한 것" 참고) — 애초에 논의했던 "정렬 기준별 SQL 커서 쿼리 3종"은 필요 없어졌다.

## 스스로 판단한 것

- **keyset 비교를 SQL이 아니라 자바에서 수행함**: 결정 1(자바 필터)과 결정 2(keyset)를 합치면,
  운임·배송거리 필터가 이미 자바 메모리에서 걸러진 뒤에야 "최종 후보"가 확정된다. 그 확정된
  후보 목록 위에서 커서 비교(다음 위치 찾기)까지 자바에서 하는 게 유일하게 일관된 방법이라
  판단했다 — SQL 커서 쿼리로 미리 걸렀다가 자바 필터에서 또 걸러내면, "커서 다음 size개"가
  자바 필터를 통과 못 해 페이지가 비게 되는 문제가 생긴다. bounding box 후보 자체가 많아야
  수백 건(#367 실측 참고)이라 자바에서 정렬·필터·커서 비교를 다 해도 성능 문제가 없다고 봤다.
- **커서에 정렬값+deliveryId를 함께 씀(id만으로는 부족)**: id만 커서로 쓰면, 그 사이 그 주문이
  다른 라이더에게 수락돼 목록에서 사라졌을 때 "그 id 다음 위치"를 찾을 방법이 없어진다. 정렬
  기준 값(거리/운임/요청시각)을 함께 받아 "그 값보다 큰(작은) 것"으로 비교하면, 원래 항목이
  사라져도 커서가 여전히 유효하다.
- **커서·필터를 record 두 개(`RiderDeliveryRequestFilter`, `RiderDeliveryRequestCursor`)로 묶음**:
  서비스 메서드에 타입이 겹치는 파라미터(Long/Integer 여러 개)가 나열되면 순서를 헷갈리기
  쉬워서, 관련 있는 것끼리 레코드로 묶어 실수를 줄였다.
- **모든 정렬에 deliveryId 오름차순 tiebreaker를 붙임**: 운임·거리·요청시각이 동점인 경우가
  있을 수 있는데, tiebreaker가 없으면 같은 요청을 반복해도 정렬 순서가 안정적이라는 보장이
  없어 커서 비교가 흔들릴 수 있다.
- **페이지 크기 상한(100) 추가**: 이슈에 명시된 값은 아니지만, 페이지네이션을 도입하는 이번
  이슈 자체의 목적(무제한 응답 방지)에 맞춰 방어적으로 추가했다. 기존에 미결로 남아있던
  `radiusMeters` 상한 미비(CLAUDE.md)와는 별개 사안이다 — 그건 그대로 미결로 남긴다.
- **응답을 `List`에서 `{items, hasNext}`로 바꿈**: 페이지네이션 도입 자체가 요구하는 최소한의
  변경이다. 총 건수는 안 담았다 — keyset은 매 요청마다 최신 목록을 다시 걸러 정렬하므로, 총
  건수를 세려면 별도 COUNT 조회가 필요해 이 조회 자체의 비용과 안 맞다고 판단했다(사람에게
  묻지 않고 결정 — 이슈에 총 건수 요구사항이 없었다).

## 일부러 하지 않은 것

- **여러 정렬 기준 조합(예: "가까우면서 비싼 순")**: 이슈 입력값이 "정렬 기준"·"정렬 방향"을
  단수로 표현하고 있어 단일 기준 선택만 지원한다. 조합 정렬이 필요해지면 별도 이슈에서
  다뤄야 한다(미등록).
- **총 건수(total count) 노출**: 위 "스스로 판단한 것" 참고.
- **`radiusMeters` 상한 도입**: CLAUDE.md에 이미 미결로 남아 있던 별개 사안이라 이번에 손대지
  않았다.
