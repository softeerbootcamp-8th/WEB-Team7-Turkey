# 배송 ETA 폴링 전용 API 작업 기록

- 이슈: [#447](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/447)
- 브랜치: `feature/447-delivery-eta-polling-api`
- 범위: fullstack
- 작성일: 2026-08-10

## 무엇을 만들었나

도착 예정 시각만 담은 폴링 전용 API를 신설하고, 추적 화면이 그것을 1분 주기로 불러 카운트다운으로
보여 주게 했다. 그리고 아무도 부르지 않던 추적 스냅샷 API(`GET .../tracking`, #79)를 삭제했다.

발단은 "#421이 ETA를 추적 스냅샷 응답에 얹었는데 그 API를 프론트가 쓰지 않는다"는 것을 발견한
것이다. 추적 화면은 #371에서 지도 마커(픽업·도착지 좌표)가 필요해지면서 — 추적 스냅샷 응답에는
`pickup`/`destination`이 없다 — 상세 조회 하나로 데이터 소스를 통합했고, 그 뒤로 ETA는 화면에
표시되지 않는 상태로 방치돼 있었다. 즉 **#421의 산출물이 배포돼도 사용자에게 도달하지 않았다.**

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| GET | `/api/customer/deliveries/{deliveryId}/eta` | 도착 예정 시각 + 상태. 폴링 전용 | 401 세션 / 404 없음·타인 것 |
| ~~GET~~ | ~~`/api/customer/deliveries/{deliveryId}/tracking`~~ | **삭제**(#79, 호출자 0) | — |

ETA 산정 실패(배차 전·완료·취소, 라이더 위치 없음, 경로 서버 장애)는 **실패 응답이 아니다** —
`estimatedArrivalAt`만 null인 200이다.

### 화면

`customer/deliveries/$deliveryId/tracking` 의 상태 헤드라인 아래에 ETA 한 줄을 추가했다.
`-components/DeliveryEta.tsx`(폴링 + tick)와 `-eta.ts`(순수 포맷 함수)로 나눴다.

### 스키마 변경

해당 없음.

## 사람이 고른 선택

### 1. ETA를 어디에 실을 것인가

- **물었던 것**: 추적 화면이 ETA를 못 보여주는 상태를 어떻게 풀지.
- **선택지**:
  - (A) 상세 API(`GET .../{id}`)에 `estimatedArrivalAt`을 추가하고 추적 API 삭제 — API가 하나로
    줄지만, 이력 화면도 같은 API를 쓰므로 "추적 가능 상태일 때만 OSRM 호출" 분기가 붙는다
  - (B) 추적 API에 `pickup`/`destination`을 추가하고 게이트를 완화 — 그러면 상세 API와 거의 같아져
    두 API의 존재 이유가 사라진다
  - (C) 화면이 두 API를 다 호출 — 상세로 그리고 추적에서 ETA만 뽑음. 필드가 대량 중복된다
  - (D) **ETA 전용 경량 API 신설** — 변하는 값만 담아 폴링. API가 하나 늘지만 폴링 응답이 최소가 된다
- **고른 것**: (D)
- **근거**: "상세 API, 추적 API 모두 나랑 관계없는 API이고, 사람이 그 화면을 보고 있을 때
  polling으로 ETA만 가져오도록 해야 할 듯. 그러니까 API를 따로 하나 만들어야 할 듯해"
  (사람 확인, 2026-08-10). 처음에는 (A)로 합의했다가, ETA가 폴링 대상이라는 성격이 분명해지면서
  뒤집혔다 — 상세 응답 전체를 1분마다 실어 나를 이유가 없다.
- **영향**: 상세 API·추적 화면의 기존 렌더링 경로는 그대로다. 새 API가 폴링 경로이므로
  **백엔드 호출 1회 = OSRM 호출 1회**라는 관계가 생겼다 — 주기 값이 곧 경로 서버 부하다.

### 2. 폴링 주기

- **물었던 것**: 배송 1건당 OSRM 호출 빈도가 여기에 비례한다.
- **선택지**: 30초(20분 배송에 40회) / **1분(20회)** / 10초(120회) / 5초(위치 전송과 동일).
- **고른 것**: 1분.
- **근거**: 사람 확인, 2026-08-10. `DeliveryTrackingResponse` javadoc과 `docs/04-frontend-api-map.md`가
  이미 "약 1분 백업 폴링(#422)"을 전제로 적혀 있었어서 그 값과 일치한다.
- **영향**: `DeliveryEta.POLL_INTERVAL_MS`. 서버가 **절대 시각**을 주므로 그 사이는 클라이언트가
  스스로 줄여 나간다(아래 3번) — 주기를 늘려도 화면이 멈춰 보이지 않는다.

### 3. 상태 전이만으로 ETA를 갱신할지, 폴링할지

- **물었던 것**: 상태 전이 SSE로 재조회하면 폴링이 필요 없지 않은가.
- **선택지**:
  - (A) 상태 전이만 + 클라이언트 카운트다운 — 서버 호출 최소. 다만 정체로 늦어져도 보정되지 않음
  - (B) 상태 전이 + 저빈도 폴링 — 카운트다운으로 자연스럽게 보이되 몇 분에 한 번 서버값으로 교정
  - (C) 카운트다운 없이 도착 예정 시각을 시각 그대로 표시
- **고른 것**: 처음 (A)로 답했다가, 전용 API를 만들기로 하면서 **(B)** 로 수렴했다(사람 확인).
- **근거**: 상태 전이는 드물게 일어난다 — `DELIVERING` 구간이 20분이면 그 사이 ETA가 진입 시
  계산한 값 하나로 고정된다. 카운트다운만으로는 라이더가 정체에 걸려도 0을 향해 계속 내려간다.
- **영향**: 폴링(1분, 서버값 교정)과 tick(10초, 화면 눈금)이 **서로 다른 주기로 공존한다.**
  둘을 하나로 합치려 들면 안 된다 — 전자는 네트워크, 후자는 렌더링 비용이다.

### 4. 추적 불가 상태(WAITING·COMPLETED·CANCELED)의 응답

- **물었던 것**: 기존 추적 게이트(`DeliveryTrackingAccessService`)를 재사용해 409로 막을지.
- **선택지**:
  - (A) **200 + `estimatedArrivalAt: null`** — 폴링이 에러로 시끄러워지지 않음
  - (B) 409 거부(추적 게이트 재사용) — 다른 API와 일관되지만 프론트가 409를 정상 신호로 다뤄야 함
- **고른 것**: (A)
- **근거**: 사람 확인, 2026-08-10. 1분마다 도는 요청이 오류를 내면 화면이 **정상 상황**(배차 대기,
  배송 완료 직후)을 실패로 처리하게 된다.
- **영향**: 이 API는 추적 게이트를 쓰지 않고 소유권 판정을 쿼리 조건에 직접 둔다
  (`findWithAssignedRiderByIdAndCustomerId`). 그래서 **`left` join fetch 여야 한다** — WAITING은
  라이더가 NULL이라 inner join이면 200이 아니라 404가 된다.

### 5. 안 쓰는 추적 API 처리

- **물었던 것**: #421이 추적 API에 얹은 ETA만 되돌릴지, API 자체를 지울지.
- **경과**: 처음에는 "다른 분의 작업이라 내가 건드린 것만 제거"로 정해 #421/#431 변경분을
  `dev`의 PR #438 직전 상태로 되돌렸다. 그 뒤 **삭제 임무까지 받았다**는 확인이 와서 API 전체를
  삭제했다(사람 확인, 2026-08-10).
- **영향**: `DeliveryTrackingQueryService`·`DeliveryTrackingResponse`와 그 테스트 2개 삭제,
  인터셉터에서 `/api/customer/deliveries/*/tracking` 제거. **`DeliveryTrackingAccessService`는
  존치한다** — SSE 스트림(`CustomerTrackingStreamController`)과 위치 폴링
  (`CustomerLocationQueryService`)이 그 판정을 쓴다. `/tracking/stream` 경로 등록도 그대로다.

### 6. #79의 "200이면 스트림도 열린다" 보장

- **물었던 것**: 그 보장을 포기할지, 다른 형태로 유지할지.
- **고른 것**: 논의 자체가 성립하지 않는다고 판단 — "추적 API 자체를 안 쓰게 됐으니까 거기서의
  결정도 무시되는 거 아니야?"(사람 확인, 2026-08-10).
- **근거**: 그 보장은 추적 API가 **가진 성질**이었다. API를 삭제하면 보장할 대상도 함께 사라진다.
  게다가 프론트는 #371 이후 그 보장을 쓰지 않고 `streamStatus`("연결이 끊겼어요")만 표시해 왔다.
- **영향**: **스트림 실패 사유를 REST로 알 방법이 지금은 없다.** 브라우저 `EventSource`는
  상태코드·본문을 스크립트에 노출하지 않는다. `docs/04-frontend-api-map.md` §7에 이 공백을 명시했다.

## 스스로 판단한 것

- **`status`를 ETA 응답에 함께 담았다**: ETA가 픽업지 기준인지 도착지 기준인지는 상태가 정하는데
  (`DeliveryRouteEstimator.targetOf`), 프론트가 상태를 다른 조회에서 가져오면 **전이 순간에
  "픽업까지"라는 라벨과 도착지 기준 값이 섞인다.** 한 응답 안에서 짝을 맞춘다.
- **`@Transactional`을 붙이지 않았다**: OSRM 호출(최대 1초)을 트랜잭션 안에 두면 그만큼 DB
  커넥션이 잠긴다. #421이 추적 스냅샷에서 세운 원칙인데, **폴링 경로에서는 그 비용이 동시 추적 수
  × 분당 1회로 곧장 비례해** 더 중요해졌다. 대가로 지연 로딩 연관을 트랜잭션 밖에서 만질 수 없어
  `left join fetch`가 한 묶음으로 따라온다.
- **`r.member`까지는 fetch하지 않았다**: ETA 응답에 라이더 이름·연락처가 없다.
  `DeliveryRouteEstimator`가 읽는 것은 `assignedRider.memberId` 하나다.
- **예정 시각이 지나면 "곧 도착"에 멈춘다**: "예정보다 N분 지연"으로 보여 주는 대안을 택하지
  않았다 — OSRM은 실시간 교통정보가 없는 자유흐름 기준이라 원래 낙관적이고, 그러면 정상 배송도
  상시 지연으로 보인다. 이 값은 사람에게 따로 확인받지 않았다(되돌리기 쉬운 표시 규칙).
- **카운트다운 tick(10초)을 별도 컴포넌트에 가뒀다**: 페이지 컴포넌트에 상태를 두면 10초마다
  카카오맵까지 리렌더된다. 표시 단위가 분이라 1초 tick은 불필요하다.
- **`CustomerDeliveryApi`의 옛 형식(인터페이스에 매핑)을 그대로 따랐다**: `references/backend.md`는
  신규 컨트롤러를 명세/구현 분리 형식으로 만들라고 하지만, 이 파일은 전체가 옛 형식이다. 한
  파일 안에 두 형식이 섞이는 것이 더 나쁘고, 파일 전체 이관은 기능과 무관한 대량 변경이다.

### 검증하지 못한 것

- **브라우저에서 실제로 ETA가 갱신되는 것을 눈으로 보지 못했다.** 이 저장소에 프론트 E2E 러너가
  없고(Playwright 미도입, `references/testing.md`), 로컬에서 ETA를 띄우려면 배차된 배송 + BUSY
  라이더의 Redis 위치 + 닿는 OSRM 서버가 동시에 필요하다. 폴링 주기·tick 주기·탭 비활성 시 중단은
  TanStack Query 기본 동작에 맡겼고 테스트하지 않았다.
- **실제 OSRM 응답으로 ETA가 그럴듯한 값인지**는 이 이슈에서 확인하지 않았다(#421과 같은 공백).
- **폴링이 실제로 만드는 OSRM 부하**는 측정하지 않았다.

## 새로 생긴 미결 사항

- **스트림 실패 사유를 알 방법이 없어졌다.** #79 스냅샷 REST가 SSE와 게이트를 공유해
  401/404/409를 대신 알려 주던 통로가 그 API 삭제로 사라졌다. 지금 화면은 `EventSource`의
  `onerror`(readyState로 CLOSED/CONNECTING만 구분)에 기대 "연결이 끊겼어요"만 보여준다. 사유별
  UX가 필요해지면 별도 설계가 필요하다.
- **폴링 주기 1분이 잠정값이다.** 백엔드 호출 1회 = OSRM 호출 1회라, 동시 추적 수에 그대로
  비례한다. 부하 테스트에서 재조정할 항목.
- **ETA 카운트다운은 정체를 보정하지 못한다.** 폴링(1분)이 서버값으로 교정하지만 그 사이에는
  예정 시각을 향해 단조 감소하고, 지나면 "곧 도착"에 멈춘다.
