## 무엇을 만들었나

`CustomerPointApi.getPointTransactions`는 이미 계약(인터페이스)만 있고 컨트롤러 구현체는
`return null` 스텁 상태였다(#69 당시 라이더만 구현하고 고객 쪽은 계약만 맞춰 둔 것으로 보임).
이번 작업은 그 스텁을 라이더 쪽 구현(`RiderPaymentService#getPointTransactions`, #69)과
동일한 구조로 채웠다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| GET | `/api/customer/points/transactions` | 포인트 거래 내역(유형 필터·페이지) + 현재 잔액 | 401 미로그인 |

### 화면

해당 없음 — 이 엔드포인트를 소비하는 프론트 화면·훅은 아직 없다(코드베이스에 참조 0건 확인).

### 스키마 변경

해당 없음.

## 사람이 고른 선택

### 1. 조회 기간(기간 필터) 포함 여부

- **물었던 것**: 이슈 본문은 입력값에 "조회 기간"을 명시하지만, 기존 라이더 구현(#69)은
  유형(type)+페이지만 지원하고 기간 필터가 없다. 고객 쪽도 라이더와 동일하게(기간 필터 없이)
  만들지, 이슈 명세대로 기간 필터를 새로 추가할지.
- **선택지**:
  - (A) 라이더와 동일하게 유형+페이지만 지원 — 기존 계약(`CustomerPointApi`)·리포지토리 재사용,
    작업 범위 최소화 / 이슈에 적힌 "조회 기간" 입력값은 구현하지 않음
  - (B) 이슈 명세대로 기간 필터(from/to) 추가 — 이슈 요구사항을 그대로 충족 / 라이더와 계약이
    갈라지고, 리포지토리에 날짜 범위 쿼리 메서드를 새로 만들어야 함
- **고른 것**: (A)
- **근거**: "라이더랑 똑같이 해" — 라이더 구현을 그대로 따르라는 명시적 지시.
- **영향**: 기간 필터는 미구현 상태로 남는다. 나중에 필요해지면 라이더 쪽에도 같이 추가할지
  결정해야 한다(아래 「새로 생긴 미결 사항」 참조).

## 스스로 판단한 것

- **`toResponse` 매핑을 그대로 복제**: `RiderPaymentService`의 private 메서드를 `common`으로
  추출하지 않고 그대로 복사했다 — `CLAUDE.md`의 "세 번째 사례가 생기기 전까지 공용 추출하지
  않는다"는 원칙(세션 인터셉터 사례)과 같은 결로 판단. 두 서비스가 이미 존재하는 상태에서
  지금 추출하면 아직 없는 차이를 미리 상정하게 된다.
- **리포지토리 변경 없음**: `PointTransactionRepository`의 `findByWallet_MemberId`,
  `findByWallet_MemberIdAndTransactionType`이 이미 고객/라이더 공용으로 구현돼 있어(멤버 ID
  기준, 역할 구분 없음) 새 쿼리 메서드가 필요 없었다.

## 일부러 하지 않은 것

- **기간(from/to) 필터**: 위 결정 1 참조. 후속: 아래 미결 사항에 등록.
- **프론트 연동**: 이슈 범위 판정을 `backend`로 잡았다 — 이슈 본문에 화면·라우트 언급이 없고,
  이 엔드포인트를 소비하는 화면도 아직 저장소에 없다. 화면이 필요해지면 별도 이슈로.
- **테스트 코드**: 사용자 지시(`CLAUDE.local.md` §8, 2026-07-28)로 이번 세션에서는 테스트를
  작성하지 않았다.

  쪽(`RiderPaymentService`)도 함께 확장할지 논의 필요.
