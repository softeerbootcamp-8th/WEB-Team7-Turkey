## 무엇을 만들었나

#416 으로 배포된 자체 호스팅 OSRM(서울시 전용)을 호출하는 **클라이언트 계층만** 만들었다.
`common/routing` 에 포트(`RoutingClient`)와 OSRM 구현체(`OsrmRoutingClient`), 그리고 연속 실패 시
호출을 멈추는 `RoutingFailureBackoff` 가 있다. 좌표 두 개를 주면 소요시간·거리·경로 폴리라인을
돌려주고, **어떤 실패에도 예외를 던지지 않는다**(빈 값).

호출자는 아직 없다. 추적 응답에 값을 채우는 것은 #421 이고, 이슈가 그렇게 나눈 이유는 외부 연동의
실패 처리와 도메인 정책(ETA 를 어느 구간으로 잡을지)을 한 이슈에 섞지 않기 위해서다.

### API

해당 없음 — 엔드포인트를 만들지 않는다. 외부(OSRM)로 나가는 호출만 추가했다.

| 방향 | 호출 | 비고 |
|---|---|---|
| WAS → OSRM | `GET {base}/route/v1/driving/{lng1},{lat1};{lng2},{lat2}?geometries=geojson&overview=simplified` | 배포 `http://10.0.130.0:5000`, 로컬 `http://localhost:5000` (`ROUTING_BASE_URL`) |

해당 없음(#422).

해당 없음.

## 사람이 고른 선택

### 1. 호출 타임아웃

- **물었던 것**: OSRM 호출의 연결·읽기 타임아웃을 얼마로 잡을까
- **선택지**:
  - (A) 연결 300ms / 읽기 700ms — 최악에도 추적 API 가 1초 이상 밀리지 않음 / 아주 느린 응답은 버림
  - (B) 연결 500ms / 읽기 1500ms — 느려진 OSRM 에서도 ETA 를 살림 / 장애 시 매 호출 2초 지연
  - (C) 연결 200ms / 읽기 400ms — 지연 최소 / 부하가 튀면 정상 응답도 버려짐
- **고른 것**: (A)
- **근거**: #407 PoC 실측이 10ms 내외였으므로 70배 여유이고, 정상 상황에서 오탐으로 ETA 가 사라질
  일이 사실상 없다.
- **영향**: #421 이 이 호출을 응답 경로에 넣을 때 추적 API 지연 상한이 여기에 묶인다. 재시도를
  넣으면 그 상한이 배로 늘어나므로 재시도는 두지 않았다.

### 2. 장애가 지속될 때의 동작

- **물었던 것**: OSRM 이 계속 죽어 있을 때 매 호출 타임아웃을 감수할지, 회로를 끊을지
- **선택지**:
  - (A) 연속 실패 시 일정 시간 호출 스킵 — 장애 중 지연이 0 / 상태를 들고 있어야 함
  - (B) 타임아웃만 두고 매번 호출 — 상태 없음, 테스트 쉬움 / 장애 동안 모든 고객의 추적 API 가
    매 호출 700ms 씩 느려짐
- **고른 것**: (A). 다만 형태를 사람이 지정했다 — **"TCP 가 세 번 보내고 응답 없으면 타임아웃하는
  것을 오마주하자"**.
- **근거**: 사람 말 그대로. 서버가 죽은 것을 이미 세 번 확인했는데 네 번째 호출로 또 확인할 이유가
  없고, TCP 의 재전송 백오프가 이미 검증된 형태라는 것.
- **영향**: `RoutingFailureBackoff` 가 연속 3회 실패에서 회로를 열고, 대기 시간을 1초 → 2초 → …
  → 30초(상한)로 두 배씩 늘린다. 성공 한 번이면 전부 초기화된다. 라이브러리(resilience4j)를 쓰지
  않은 것은 새 의존성이 사람 확인 사항인데(CLAUDE.md) 필요한 동작이 이 정도여서다.

### 3. 경로 좌표 상세도

- **물었던 것**: `overview=full` 과 `simplified` 중 무엇으로 요청할지
- **선택지**:
  - (A) `full` — #416 검증에 쓴 값, 골목 단위까지 정확 / 좌표가 수백~수천 개로 늘어 추적 응답이 커짐
  - (B) `simplified` — 페이로드가 훨씬 작음 / 곡선 구간이 각져 보일 수 있음
  - (C) 설정값으로 노출 — 나중에 화면 보고 결정 / 그래도 기본값은 지금 정해야 함
- **고른 것**: (B)
- **근거**: "MVP 수준인데 간단하게 가자, 풀로 가지 말고."
- **영향**: (C)를 고르지 않았으므로 설정 항목이 늘지 않았다. 화면(#422)에서 경로선이 어색하면
  상수 하나를 바꾸는 변경이 된다.

## 스스로 판단한 것

- **패키지를 `common/routing` 에 두었다** — 근거: `PaymentGateway`·`SmsSender` 는 "포트를 소비자와
  같은 도메인 패키지에 둔다"는 관례를 따르지만, 이 포트는 시그니처에 도메인 타입이 하나도 없는 순수
  인프라 어댑터다. 게다가 첫 소비자는 `order`(#421)인데 `location → order` 의존이 이미 있어 어느
  도메인 패키지에 넣어도 방향이 엇갈린다. `common/config/S3Config` 와 같은 자리로 봤다.
- **`Coordinate` 를 새로 만들고 `location/dto/LocationPayload` 를 재사용하지 않았다** — 근거:
  LocationPayload 는 측정 시각·정확도를 포함한 *라이더 위치 보고* 타입이라 주문의 도착지 좌표를
  담을 수 없다. 그리고 위경도 순서를 타입으로 고정하는 것 자체가 이 record 의 목적이다 — 뒤집어도
  서울 좌표는 둘 다 유효 범위라 예외 없이 엉뚱한 위치가 찍힌다(#423 알려진 리스크).
  **뒤집는 코드는 `OsrmRoutingClient` 안 한 곳에만 있다.**
- **4xx 를 회로 차단의 실패로 세지 않는다** — 근거: OSRM 은 경로를 못 찾은 경우(`NoRoute`·
  `NoSegment`)에도 400 을 준다. 서울시 전용 extract 라 서울 밖 좌표가 섞이는 것은 정상적으로 생기는
  일인데, 이걸 장애로 세면 **그런 주문 세 건이 모든 고객의 ETA 를 끊는다.** 5xx·타임아웃·연결
  실패만 장애로 센다.
- **`RestClient` 를 클래스 안에서 직접 만들고 자동설정 `RestClient.Builder` 를 주입받지 않았다** —
  근거: 300/700ms 는 공용으로 쓰기엔 지나치게 짧아서, 공용 빈에 얹으면 다른 호출이 무심코 그 값을
  물려받는다. 새 의존성은 없다(`RestClient` 는 spring-web 내장).
- **거리(`distanceMeters`)도 함께 돌려준다** — 근거: 응답에 이미 들어 있어 공짜다. 다만 요금 계산에
  쓰지 않는다(요금은 `order` 의 직선거리 기반 정책이 정본) — 그 경고를 `Route` javadoc 에 적었다.
- **엄밀한 half-open 을 만들지 않았다** — 근거: 대기가 끝난 뒤 흘려보내는 호출을 1개로 제한하려면
  in-flight 상태가 하나 더 필요한데, 추적 API 는 1분 폴링이라 그 사이 몰릴 요청이 몇 건뿐이고
  그중 하나만 실패해도 즉시 다시 닫힌다.

## 일부러 하지 않은 것

- **추적 응답에 ETA·경로를 채우는 것**: 이슈가 명시적으로 뺐다 — 후속 #421.
- **경로 결과 캐싱**: 같은 주문의 경로를 얼마나 재사용할지는 호출 주기를 아는 쪽이 정해야 한다 —
  후속 #421 에서 판단.
- **재시도**: 응답 경로에 있는 호출이라 재시도가 곧 지연 배증이다 — 미등록.
- **실패 사유를 호출자에게 알리는 것**: 타임아웃·경로 없음·서버 오류를 전부 빈 값 하나로 뭉갠다.
  사유별 UX(예: 서비스 지역 밖 안내)가 필요해지면 반환 타입을 넓혀야 한다 — 미등록.
- **인스턴스 간 실패 상태 공유**: 백오프 카운트는 인스턴스 로컬이다. 공유하려면 Redis 가 필요한데,
  각 인스턴스가 스스로 세 번 확인하는 비용이 그보다 싸다 — 미등록.
- **카카오모빌리티·Tmap 과의 정확도 비교**: #407 에서 카카오 API 사용 권한 심사가 안 끝나 보류된
  상태 그대로다. 인터페이스로 끊어 둔 것이 그 재검토 여지다.

### 검증하지 못한 것

- **실제 OSRM 응답으로 검증하지 않았다.** 배포된 OSRM 은 WAS 보안그룹에서만 접근 가능해 개발 PC 에서
  닿지 않는다(#416). 테스트가 쓰는 응답은 #416 코멘트의 실측값(서울시청→강남역, 9,945.2m /
  730.7초)을 옮긴 것이지만, **필드 구조가 실제와 다르면 스텁은 그 사실을 알려주지 않는다.**
  #421 에서 배포 환경에 한 번 붙여 확인해야 한다.
- **회로가 열린 뒤 대기가 끝나고 실제로 재개되는 흐름**은 백오프 단위 테스트(가짜 시계)로만 봤다.
  클라이언트 테스트는 대기 1초 안에서 끝나므로 재개 구간을 지나가지 않는다.
- **부하 상황에서 300/700ms 가 적절한지** 실측하지 않았다.

## 새로 생긴 미결 사항

- OSRM 은 실시간 교통정보를 반영하지 않아 ETA 오차가 있고, 카카오/Tmap 과의 정확도 비교는 여전히
  미수행이다(#407 에서 보류). 인터페이스로 끊어 뒀으니 교체는 구현체 하나 추가로 끝난다.
- 백오프 값(연속 3회 / 1초→30초)과 타임아웃(300/700ms)이 실측 없이 정한 잠정값이다. 부하 테스트나
  실제 장애 때 재검토한다.
- 라우팅 결과 캐시가 없다. #421 이 호출 주기를 정할 때 함께 판단해야 한다.
- 로컬·CI 어디에도 **실제 OSRM 에 붙는 테스트가 없다.** 스텁이 실제 응답 구조와 어긋나도 드러나지
  않는다.
- (이 이슈와 무관하나 작업 중 확인됨) **전체 테스트를 한 번에 돌리면 이 개발 PC 에서 E2E 컨텍스트가
  `SocketException: Bad address: listen` 로 무작위 실패한다.** 변경 전에도 재현되며, Windows 의
  예약 포트 범위(`netsh interface ipv4 show excludedportrange protocol=tcp`)가 흔한 원인이다.
  CI 에서 테스트를 켤 때(CLAUDE.md 미결) 같은 문제를 만나는지 확인이 필요하다.
