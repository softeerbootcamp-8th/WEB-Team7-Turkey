# 라우트 인증 가드 및 401 공용 처리 작업 기록

## 무엇을 만들었나

두 `_authed.tsx` 는 `beforeLoad` 도 `<Outlet />` 도 없는 `Hello` 껍데기였고 자식 라우트가 하나도
그 아래에 없어서, 모든 화면이 비로그인으로 열렸다. `CLAUDE.md` 가 정한 "프론트 가드 1차" 방어가 비어 있었다.

- 인증 가드 4곳: `customer/_authed`, `rider/_authed`, `account/route`(역할 무관), `auth/route`(비인증)
- 보호 대상 라우트 26개 파일을 `_authed/` 하위로 이동(경로 없는 레이아웃이라 **URL 은 그대로**)
- 401 공용 처리를 `axiosInstance` 인터셉터 + `main.tsx` 배선으로 한 곳에 모음
- 가드 판정을 순수 함수로 분리하고 vitest 로 고정(37케이스)

### API

새 엔드포인트 없음. 기존 `getCustomerSession` · `getRiderSession`(#194 생성 훅) 소비.

### 화면

라우트 이동과 가드만 붙였고 화면 마크업은 건드리지 않았다.

| 라우트 | 가드 | 비로그인 시 |
|---|---|---|
| `customer/_authed/**` (홈·배송·포인트) | 인증 + 고객 역할 | `/customer/login?redirect=…` |
| `rider/_authed/**` (홈·콜목록·진행배송·이력·정산) | 인증 + 라이더 역할 + 운행 상태 정합성 | `/rider/login?redirect=…` |

## 사람이 고른 선택

### 1. 역할을 모르는 상태에서 로그인 여부를 어떻게 확인할까

- **물었던 것**: `auth/*` 비인증 가드와 `account/*`(고객·라이더 공용) 인증 가드는 역할을 모른 채
  로그인 여부를 알아야 한다. 그런데 백엔드 세션 API 는 `customer-session` · `rider-session` 으로
  역할별로 갈려 있고, **역할 불일치도 401** 이라 고객 세션 API 만 보면 "비로그인"과 "라이더로 로그인"을
  구분할 수 없다. (실제 백엔드에 붙여 확인함 — 고객 로그인 상태에서 `/api/rider/session` → 401)
- **선택지**:
  - (A) 백엔드에 역할 무관 `GET /api/session` 추가 — 가드가 한 번의 조회로 단색해짐 / #195 범위 밖의
    백엔드 생산물(엔드포인트 + 인터셉터 등록 + 통합 테스트)이 붙는다
  - (B) 프론트에서 두 API 를 모두 조회해 합성 — 백엔드 변경 없이 범위를 지킴 / 가드마다 요청 2번,
    둘 중 하나는 항상 401 이라 서버 로그가 지저분해짐
  - (C) 로그인 시 역할을 localStorage 에 기억 — 요청 1번 / 쿠키 세션 밖에 출처가 하나 더 생겨
    한쪽만 만료되면 상태가 어긋난다
- **고른 것**: (B)
- **근거**: 사람 확인 — "프론트에서 둘 다 조회해 합성".
- **영향**: `shared/auth/session.ts` 의 `ensureSessionInfo` 가 이 합성을 담당한다. 요청이 2배가 되는 대가를
  줄이려고 **캐시에 신선한 세션이 있으면 그것만으로 판정**하는 단축 경로를 넣었다(아래 「스스로 판단한 것」).
  나중에 역할 무관 세션 API 가 생기면 이 함수 하나만 갈아끼우면 된다.

### 2. `account/*` 가드를 이번에 포함할지

- **물었던 것**: `account/*` 는 고객·라이더 공용이라 `customer/_authed` · `rider/_authed` 어느 쪽에도
  넣을 수 없다. 이슈 「구현 범위」에 account 가 없지만 제외 목록(login·signup·auth/*)에도 없다.
- **선택지**:
  - (A) 이번에 포함 — 보호 누락을 한 번에 메움 / 이슈에 없는 파일(`account/route.tsx`)이 추가됨
  - (B) 후속 이슈로 분리 — 범위 엄정 / `account/*` 가 그동안 무보호로 남음
- **고른 것**: (A)
- **근거**: 사람 확인 — "이번에 포함". `CLAUDE.md` 「프론트엔드 아키텍처」도 `account/` 를
  "로그인 후, 인증 가드"로 이미 규정하고 있어 새 정책이 아니다.
- **영향**: `account/route.tsx` 는 역할을 따지지 않는다. 비로그인이면 역할별 로그인 화면을 고를 수 없어
  랜딩(`/`)으로 보내고 목적지만 보존한다 — 랜딩에 역할 선택이 붙으면 자연스럽게 이어진다.

### 3. 프론트 테스트 러너

- **물었던 것**: `frontend` 에 테스트 러너가 없다. 가드는 분기가 많아 테스트 가치가 확실한데,
  러너 추가는 새 의존성이라 `CLAUDE.md` 상 사람 확인이 필요하다.
- **선택지**:
  - (A) vitest 도입 — 가드 분기를 자동 회귀 방어 / devDependency 1개 추가
  - (B) 러너 없이 typecheck·build + 수동 확인 — 의존성 없음 / 회귀 방어 없음, 완료 조건 미충족
- **고른 것**: (A)
- **근거**: 사람 확인 — "vitest 도입".
- **영향**: `vitest.config.ts`, `pnpm test` 스크립트가 생겼다. 이후 프론트 이슈는 이 인프라를 재사용한다.
  `@testing-library` 는 넣지 않았다 — 이번에 테스트한 것이 전부 순수 함수라 렌더러가 필요 없었다.
  컴포넌트 테스트가 필요해지는 이슈에서 추가 판단.

## 스스로 판단한 것

- **가드 판정을 순수 함수로 떼어낸 것**(`shared/auth/guard.ts`): 라우트 파일은 `redirect` 를 던지는
  일만 하고, "어디로 보낼지"는 세션 정보와 경로만 받는 함수가 결정한다. 라우터를 띄우지 않고
  분기를 전부 테스트할 수 있는 것이 이 분리의 목적이다.

- **라이더 상태 강제를 3개 화면끼리만 적용한 것**: 이슈는 `BUSY→rider/delivery`,
  `AVAILABLE→rider/requests`, `UNAVAILABLE→rider/index` 매핑만 적어 뒀는데, 이걸 라이더 전체 라우트에
  적용하면 BUSY 라이더가 `rider/history`·`rider/points` 를 아예 열 수 없다(상태 홈으로 계속 튕김).
  매핑의 목적은 "홈/콜목록/진행배송 중 지금 맞는 화면으로 보내기"이지 라이더를 한 화면에 가두는 것이
  아니라고 읽었다. 이력·정산·콜 상세는 상태와 무관하게 열린다 — 회귀 테스트로 고정해 뒀다.

- **비인증 가드(`auth/*`)만 세션 확인 실패 시 열어주는 것**: 인증 가드는 실패를 만료로 처리하지 않고
  오류 화면을 보여준다(이슈 예외 흐름). 그런데 같은 규칙을 가입 화면에 적용하면 세션 조회 장애 때
  아무도 가입할 수 없다. 잘못 열려도 손해는 "이미 로그인한 사람이 가입 화면을 본다" 정도라 fail-open 으로 했다.

- **파일 이동 대신 `route.tsx` 레이아웃을 쓴 것**(`auth/`, `account/`): 이슈가 "`auth/*` 는 이동하지
  않는다"고 했으므로 `_authed` 하위로 옮기지 않고 디렉터리 레이아웃 라우트로 가드만 얹었다.

- **401 인터셉터에서 리다이렉트 대상을 정하지 않고 `router.invalidate()` 를 부른 것**: 인터셉터는
  역할을 모르고 현재 라우트도 모른다. 재평가하면 지금 있는 라우트의 가드가 자기 역할에 맞는 로그인
  화면으로 목적지까지 보존해 보낸다. 리다이렉트 경로가 가드 한 곳에만 존재하게 된다.

- **인터셉터에서 세션 확인·로그인 경로를 제외한 것**: 세션 확인의 401 은 가드의 정상 판정 신호다
  (제외하지 않으면 비인증 가드가 401 을 받는 순간 로그인 화면으로 튕긴다). 로그인의 401 은 자격 증명
  오류라 폼에 표시해야 하는데 리다이렉트하면 입력이 날아간다.

- **`?redirect=` 를 같은 출처 절대 경로로만 제한한 것**: 주소창으로 들어오는 값을 그대로 믿고 이동하면
  오픈 리다이렉트가 된다(`?redirect=https://evil.example`, `//evil.example`).

- **세션 캐시 유효 시간을 5분으로 둔 것**: 세션 TTL 은 2시간 고정이고 서버가 슬라이딩 갱신을 하지
  않으므로(#27) 화면 전환마다 확인해도 TTL 은 늘지 않고 요청만 늘어난다. 무한 캐싱은 다른 탭에서
  로그아웃한 뒤에도 통과시킨다. 실제 만료는 어차피 API 401 → 인터셉터가 잡는다.

- **캐시 단축 경로를 넣은 것**: 401 은 캐시되지 않으므로 단순 구현이면 라우트를 옮길 때마다
  "내 역할이 아닌 쪽" 세션 API 에 실패가 예정된 요청을 매번 보낸다. 신선한 세션이 캐시에 있으면
  그것만으로 판정한다 — 이슈의 "화면마다 다시 요청하지 않도록 캐시를 공유한다"를 만족시키는 지점이다.

- **`src/lib/axios.ts` 의 `baseURL` 을 `''` 로 고친 것**: 아래 「함께 고친 버그」 참고.

## 함께 고친 버그 (#194 생성물과 겹치는 지점)

`baseURL` 이 `'/api'` 인데 Orval 생성 코드가 넘기는 url 도 `/api/customer/session` 이라
실제 요청이 **`/api/api/customer/session`** 으로 나갔다. 즉 #194 로 생성한 훅은 어떤 것도 동작하지
않는 상태였다. 가드가 세션 API 를 호출해야 하므로 이번에 고칠 수밖에 없었다(`src/lib/axios.ts` 는
이슈가 명시한 대상 파일이다).

`baseURL` 기본값을 빈 문자열로 바꿨다. 개발은 vite proxy(`/api` → 8080), 배포는 CloudFront 의
`/api/*` behavior 가 받으므로 같은 출처 상대 경로로 충분하다. Origin 을 분리해야 하면
`VITE_API_BASE_URL` 에 origin 만 넣는다.

확인:

```text
axios baseURL='/api' + url='/api/customer/session' -> /api/api/customer/session   (기존, 404)
axios baseURL=''     + url='/api/customer/session' -> /api/customer/session       (수정 후, 401/200)
```

## 일부러 하지 않은 것

- **로그인 성공 후 `?redirect=` 로 실제 복귀시키는 것**: 로그인 폼이 아직 API 에 연결돼 있지 않다
  (화면 연동 이슈 범위). 이번엔 파라미터를 **보존·검증**하는 쪽만 만들었다. 폼을 붙이는 이슈에서
  `Route.useSearch().redirect` 를 읽어 이동시키면 된다.
- **`customer/login`·`rider/login`·`*/signup` 에 비인증 가드**: 이슈는 비인증 가드 대상을 `auth/*` 로
  한정했다. 로그인 상태로 로그인 화면에 들어가는 것도 막을 여지가 있지만 이슈 범위를 넘는다 — 미결로 남김.
- **`@testing-library/react` 도입**: 이번 테스트가 전부 순수 함수라 필요하지 않았다.
- **컴포넌트 렌더 테스트·라우터 통합 테스트**: 라우터를 띄우는 테스트는 두지 않았다.
- **`account/*`, `auth/*` 화면 내용**: 전부 `Hello …` 껍데기 그대로다. 가드만 얹었다.
- **`rider/requests/$deliveryId` 등 상세 화면의 상태 강제**: 위 판단대로 제외했다.

### 검증하지 못한 것

- **브라우저에서의 실제 화면 전환**(이슈 완료 조건의 "브라우저에서 비로그인 접근 차단 확인"):
  이 세션에 브라우저 자동화 도구가 없어 수행하지 못했다. 가드 판정은 단위 테스트로, 세션 API 경로·응답은
  실서버 호출로 확인했지만 **`beforeLoad` → `redirect` 가 주소창에서 실제로 도는 것은 확인되지 않았다.**
  리뷰 시 `pnpm dev` 로 띄워 비로그인 상태에서 `/customer/deliveries`, `/rider/delivery`,
  `/account/settings` 에 직접 접근해 각각 로그인 화면·랜딩으로 튕기는지 봐 주기 바란다.
- **로그인 상태에서의 상태별 리다이렉트**: 라이더 계정으로 `AVAILABLE`/`BUSY` 를 만들려면 배차·상태 전이
  API 가 필요해 실서버 시나리오로는 확인하지 못했다. 판정 로직은 단위 테스트로 고정돼 있다.
- **401 인터셉터의 실제 발동**: 세션이 도중에 만료되는 상황을 실서버에서 재현하지 않았다
  (TTL 2시간). 인터셉터 제외 경로와 핸들러 배선은 코드 검토로만 확인했다.

## 새로 생긴 미결 사항

- 로그인 화면(`customer/login`·`rider/login`)과 회원가입 화면에 비인증 가드를 걸지 미결. 지금은
  로그인 상태로도 로그인 화면이 열린다.
- 로그인 성공 후 `?redirect=` 목적지로 복귀시키는 처리가 아직 없다(폼이 API 에 미연결). 화면 연동
  이슈에서 반드시 연결해야 파라미터 보존이 의미를 갖는다.
- 세션 캐시 유효 시간 5분이 적절한지 미검증. "너무 자주 확인한다" 또는 "로그아웃이 늦게 반영된다"가
  실제로 문제되면 조정.
- 역할 무관 세션 확인이 요청 2번이다. 역할 무관 `GET /api/session` 이 생기면 `ensureSessionInfo` 를
  단순화할 수 있다(이번엔 백엔드 범위 밖이라 미룸).

## 2026-08-02 후속 변경 (#288)

위에서 선택한 두 역할 API 합성은 반대 역할 세션 API의 401 응답이 공용 `SESSION_ID` 만료 쿠키를 내려
유효한 로그인까지 삭제하는 문제를 만들었다. #288 임시 완화로 로그인 성공 시 역할 힌트를 저장하고,
이후 해당 역할의 세션 API 하나만 조회하도록 변경했다. 역할 힌트가 없으면 세션 조회를 생략한다.

이 변경은 당시 결정을 지우는 것이 아니라 운영 전 검증에서 드러난 실패 조건을 기록하는 후속이다.
최종 해법은 역할 무관 `GET /api/session`을 추가해 서버 응답의 역할을 정본으로 사용하는 것이다.
