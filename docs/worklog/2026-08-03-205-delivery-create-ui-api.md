## 무엇을 만들었나

정적 배송요청 생성 화면을 요금 견적과 배송요청 생성 API에 연결했다. 출발지·도착지는 다음
우편번호 검색에서 선택하고, 선택된 도로명주소를 카카오 Geocoder로 변환해 우편번호·위도·경도를
함께 폼 상태에 저장한다. 유효한 최신 견적이 있을 때만 제출할 수 있고, 생성 성공 후 해당 배송의
추적 화면으로 이동한다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/customer/deliveries/quote` | 주소 좌표·물품 종류 기준 예상 요금 조회 | 400 입력·거리 오류 |
| POST | `/api/customer/deliveries` | 견적 금액·UUID 멱등키를 포함한 배송요청 생성 | 402 포인트 부족, 409 진행 중 요청·요금 변경 |

### 화면

`customer/deliveries/new`가 Orval의 `useQuoteFare`, `useCreateCustomerDelivery`를 소비한다. 입력 변경은
400ms 뒤 견적을 다시 요청하며, 늦게 도착한 이전 응답은 revision 비교로 버린다. 생성 중에는 버튼을
잠가 중복 제출을 막고, 입력값과 requestKey는 실패 후 재시도에도 유지한다.

### 스키마 변경

해당 없음.

## 사람이 고른 선택

### 1. 주소와 좌표 입력 방식

- **물었던 것**: 별도 질문 없이 사용자가 다음 우편번호 + 카카오 Geocoder 예시를 직접 제시했다.
- **선택지**:
  - (A) 도로명주소·우편번호·좌표를 직접 입력 — 외부 SDK 없이 단순하지만 사용자 오류 가능성이 큼
  - (B) 우편번호 검색 후 좌표 자동 변환 — SDK 로딩·실패 처리가 필요하지만 입력 부담과 좌표 오류를 줄임
- **고른 것**: (B)
- **근거**: 사용자가 “주소 검색과 응답에 좌표값도 있으니 이걸로 수정”하도록 요청했다.
- **영향**: 실행 환경에 `VITE_KAKAO_MAP_KEY`가 필요하고, 카카오 앱 Web 플랫폼에 서비스 도메인이 등록돼야 한다.

## 스스로 판단한 것

- **SDK 로딩을 모듈 한 곳에서 수행**: HTML에 전역 스크립트를 고정하지 않고 기존 카카오맵 1회 로더에
  `services` 라이브러리를 추가했다. 우편번호 SDK도 같은 방식으로 중복 삽입을 막았다.
- **최신 견적만 제출 가능**: 견적 이후 주소·물품이 바뀌면 금액을 즉시 비워, 이전 입력의 금액으로
  주문을 생성할 수 없게 했다.
- **409 안내 기준**: 현재 오류 응답에 코드가 없어 message에 “진행 중”이 포함된 경우에만 이용기록
  화면 링크를 노출한다. 서버 응답이 최종 판단이다.

## 일부러 하지 않은 것

- **포인트 잔액 사전 조회**: #205 본문에서 #36 이후 범위로 제외했다. 생성 API의 402는 그대로 표시한다.
- **최근 주소**: #96 및 #212 범위이므로 저장·조회하지 않는다.
- **기사님 전달사항 전송**: 생성 API와 `delivery_order`에 대응 필드가 없어 입력 상태만 유지하고 전송하지
  않는다. 백엔드 계약이 생기면 연결해야 한다.
- **API 키 하드코딩**: 전달받은 예시 키를 소스에 넣지 않고 기존 `VITE_KAKAO_MAP_KEY`를 사용한다.
