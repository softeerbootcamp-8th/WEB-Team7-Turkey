# 세션 슬라이딩 갱신(BUSY 배송 중 세션 만료) 작업 기록

- 범위: backend, mobile(android)
- 작성일: 2026-08-11

## 무엇을 만들었나

**인증을 통과한 요청마다 세션 TTL을 다시 거는 슬라이딩 갱신**을 넣었다. #27이 "고정 TTL, 슬라이딩 없음"으로
정한 것을 뒤집은 결정이다(사람 지시).

이슈의 증상은 BUSY 라이더의 세션이 배송 도중 만료되면 ① 고객 추적 지도가 조용히 멈추고 ② 라이더가 배송
완료를 못 누르고 ③ 네이티브가 5초마다 헛POST를 쏘는 것이었다. 원인은 로그인~배송이 2시간을 넘기면 활동
중에도 세션이 만료되는 것이라, 만료 자체를 막는 쪽으로 고쳤다. BUSY 라이더의 5초 위치 전송이 그대로 활동
신호가 되므로 배송 중에는 세션이 만료되지 않는다.

### API

계약 변경 없음. 인증이 걸린 응답에 `Set-Cookie: SESSION_ID=...; Max-Age=7200`가 매번 실린다(값은 같고
수명만 갱신).

### 화면

프론트 변경 없음. 401 공통 처리(`lib/axios.ts` → `main.tsx`)는 이미 있어 만료 시 재로그인 유도가 동작한다.

### 스키마 변경

없음. Redis 세션 값 형식(`{memberId, role, expiresAt}`)도 그대로다 — `expiresAt`을 갱신만 한다.

## 사람이 고른 선택

### 1. 슬라이딩 범위: BUSY 한정 vs 전면

- **물었던 것**: 세션 슬라이딩을 배송 중(BUSY)에만 걸지, 인증 요청 전체에 걸지.
- **선택지**:
  - (A) BUSY 한정 — 라이더 인터셉터에서 `operatingStatus == BUSY`일 때만 연장. #27 결정을 배송 중에
    한해서만 뒤집고, 노출 창이 배송 종료 +2시간으로 유한하다 / 고객·AVAILABLE은 여전히 로그인 2시간에
    끊긴다.
  - (B) **전면 슬라이딩** — 고객·라이더 모두, 인증을 통과한 모든 요청에서 연장.
- **고른 것**: (B) 전면 슬라이딩.
- **근거**: 사람이 "세션 전면 슬라이딩으로 진행해"로 명시 선택.
- **영향**: **탭이나 앱을 열어 둔 사용자는 세션이 사실상 만료되지 않는다.** 프론트 세션 확인 폴링과
  BUSY 위치 전송이 모두 활동 신호로 취급되기 때문이다. 유출된 쿠키의 유효 기간도 같은 방식으로
  늘어난다 — 절대 수명 상한은 두지 않았다(아래 「남긴 것」).

## 스스로 판단한 것

### 세션 쿠키를 함께 다시 발급한다 (이게 절반이다)

서버 TTL만 늘리면 **아무것도 고쳐지지 않는다.** 세션 쿠키는 `maxAge(ttl)`이 붙은 영속 쿠키라
(`SessionCookie.of`), 브라우저·WebView가 로그인 +2시간에 쿠키를 스스로 버린다. 그 다음 요청은 쿠키 없이
나가고 결국 같은 401이다. 그래서 두 인터셉터가 `sessionStore.extend()`와 `Set-Cookie` 재발급을 함께 한다.

로그아웃 경로(`/api/rider/logout`, `/api/customer/logout`)는 인터셉터 `addPathPatterns`에 없어서 만료
쿠키와 슬라이딩 쿠키가 같은 응답에서 충돌하는 일은 없다.

### 슬라이딩을 `findMemberId()`의 부수효과로 두지 않았다

`RedisSessionStore.findMemberId`에 `EXPIRE`를 한 줄 넣는 것이 diff는 가장 작지만, 그 메서드는 인증 외에도
불린다(`RiderLogoutController`가 로그아웃 대상 회원을 풀 때). 이름이 `find`인 메서드가 세션을 연장하는
것도 3시에 해독할 종류의 코드다. 별도 `extend(sessionId, ttl)`를 두고 인증 통과 지점에서 명시적으로 부른다.

### `extend`는 없는 세션을 되살리지 않는다 (Redis 명령 순서)

`EXPIRE`는 없는 키에 아무 일도 하지 않고 false를 돌려주므로, 만료된 세션이 부활하지 않는다. **다만 순서가
중요하다** — `HSET expiresAt`을 먼저 하면 없는 키에 `memberId` 없는 반쪽 해시가 새로 생겨, 인증은 못
통과하지만 TTL을 물고 남는 쓰레기 키가 된다. 그래서 `EXPIRE`로 키 존재를 확인한 뒤에만 `expiresAt`을
갱신한다. `RedisSessionStoreIntegrationTest`가 두 성질(TTL이 실제로 늘어남 / 없는 세션은 안 생김)을 고정한다.

`expiresAt`을 굳이 함께 갱신하는 이유는 그 값을 읽는 코드가 없어도(현재 0곳) 저장값이 실제 TTL과 어긋나면
디버깅 함정이 되기 때문이다. 요청당 Redis 왕복 2회이고, BUSY 5초 경로는 이미 MySQL 3 + Redis 3을 쓴다.

### TTL 상수를 `SessionStore.DEFAULT_TTL` 한 곳으로 모았다

`Duration.ofHours(2)`가 두 로그인 서비스에 각각 있었고 슬라이딩이 세 번째·네 번째 사용처(인터셉터 2개)가
됐다. 서버 TTL과 쿠키 Max-Age가 갈리면 위의 "클라이언트가 먼저 죽는" 버그가 조용히 돌아온다.

### 안드로이드: 응답 Set-Cookie를 CookieManager에 되돌려 쓴다

배경 위치 POST는 WebView가 아니라 `HttpURLConnection`으로 나가므로, 갱신된 Max-Age가 WebView 쿠키
저장소에 자동 반영되지 않는다. **배송 중 WebView가 API를 한 번도 부르지 않는 시간이 2시간을 넘기면**
(화면을 켜 둔 채 백그라운드로 내려간 상태 — 라이더 배송 화면에는 주기 폴링이 없다) 쿠키를 잃고 401이
된다. `storeRefreshedCookies`가 이 구멍을 닫는다. 서버 슬라이딩만으로는 안드로이드에서 안 고쳐지는 절반이다.

함께 이슈 ③(배터리 낭비)도 닫았다: 기존 409에 더해 **401에서도 서비스를 멈춘다.**

## 테스트

- `CustomerSessionInterceptorTest` — 인증 통과 시 `extend` 1회 + `Set-Cookie` Max-Age 재발급 (8건 통과)
- `RiderSessionInterceptorTest` — BUSY 라이더 요청이 TTL·쿠키를 함께 연장 / 인증 실패 시 연장하지 않음 (6건 통과)
- `RedisSessionStoreIntegrationTest`(신규, 실 Redis) — 짧아진 TTL이 다시 2시간으로 늘어나고 `expiresAt`도
  갱신됨 / 없는 세션은 되살아나지 않음 (2건 통과)
- 회귀: `*SessionE2ETest`·`*LoginE2ETest`·`*LogoutE2ETest` 26건 통과(응답에 Set-Cookie가 늘어난 영향 확인)

안드로이드 쪽은 자동 테스트가 없다(기존에도 없음) — 실기기 확인 필요.

## 남긴 것 (미결)

- **세션 절대 수명 상한이 없다.** 열어 둔 탭·앱은 무기한 유지된다. 상한을 두려면 `create` 시점에
  `absoluteExpiresAt`을 세션 해시에 넣고 `extend`가 그 값을 넘지 못하게 자르면 된다.
- **긴 SSE 연결은 슬라이딩을 못 받는다.** 요청이 한 번뿐이라 연장 시점도 한 번이다. 고객 추적 화면은
  ETA 폴링(1분)이 대신 연장하지만 그 폴링은 탭이 백그라운드면 멈춘다.
- **고객 측 "연결 지연/재연결 중" 안내(이슈 후보 3)는 만들지 않았다.** 스트림이 조용해지는 남은 원인은
  heartbeat 부재(별도 미결)라, 임계값을 heartbeat 주기와 함께 정해야 한다.
- **이슈의 "실제 빈도 확인"은 하지 않았다.** 빈도를 재는 계측을 붙이는 비용이 이 수정보다 크다.
- CSRF 정책은 그대로다(`SameSite=Lax`). 슬라이딩이 쿠키 탈취의 유효 기간을 늘리는 것은 위의 절대 수명
  상한과 같은 사안이다.
