# 최신 위치 저장의 원자적 조건부 갱신 작업 기록

- 이슈: [#250](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/250)
- 브랜치: `feature/250-atomic-location-cas` (base: `feature/82-location-filter`)
- 범위: backend
- 작성일: 2026-07-29

## 무엇을 만들었나

라이더 최신 위치 저장을 `find → 시각 비교 → save` 세 단계에서 **Redis 안에서 한 번에 실행되는 조건부
갱신** 하나로 바꿨다. 수평 확장에서 같은 라이더의 요청 둘이 다른 인스턴스에서 처리될 때 오래된 좌표가
최신을 덮는 문제(#81 `NON_MONOTONIC` 검사가 무력해지는 문제)를 닫는다.

그러기 위해 Redis 값 형식을 바꿨다 — Lua 가 측정 시각을 비교할 수 있어야 하고, 그러려면 시각이 **값의
맨 앞**에 있고 **고정 폭**이어야 한다. `RiderLocationSnapshot` 의 측정 시각도 밀리초로 절단해 왕복이
정확히 맞게 했다.

### API

**변경 없음.** `POST /api/rider/location` 의 요청·응답 스키마가 그대로다. 조건부 갱신에서 진 요청은
기존 `reason=NON_MONOTONIC`(200)으로 응답한다(아래 「사람이 고른 선택」 1번). OpenAPI 스펙과 Orval
생성물도 재생성이 필요 없다.

### 화면

해당 없음.

### 스키마 변경

해당 없음. 값은 Redis 에만 있고 MySQL 스키마는 건드리지 않았다.

## 사람이 고른 선택

### 1. 조건부 갱신 실패의 응답 사유

- **물었던 것**: `saveIfNewer` 가 false(경쟁 패배)를 반환했을 때 서비스가 어떤 `reason` 으로 응답할까
- **선택지**:
  - (A) 기존 `NON_MONOTONIC` 재사용 — API 계약 무변경 / 로그에서 사전 검사 탈락과 경쟁 패배를 구분 못 함
  - (B) 새 enum 값(예: `LOST_RACE`) 추가 — 경쟁 발생을 관측·측정 가능 / 응답 계약에 값이 늘어 프론트가
    처리해야 하고 Orval 재생성이 필요한데, 정상 운행에서는 극히 드문 값이다
- **고른 것**: (A)
- **근거**: 클라이언트가 보는 의미가 "당신 좌표는 최신이 아니다"로 같다. 값을 따로 두면 프론트가 처리해야
  하는 계약만 늘고 정작 정상 운행에서는 거의 나오지 않는다.
- **영향**: 경쟁 빈도를 측정해야 할 상황(#78 이후 부하 테스트 등)이 오면 그때 값을 나눈다. 지금은 두 경로가
  같은 로그 라인을 쓴다는 것을 알고 있어야 한다 — `LOCATION_DISCARDED reason=NON_MONOTONIC` 만 보고
  "클라이언트가 순서를 어겨 보냈다"고 단정할 수 없다.

### 2. 서비스의 사전 단조성 검사 존치

- **물었던 것**: `RiderLocationService.isOutOfOrder` 를 CAS 도입 후에도 남길지
- **선택지**:
  - (A) 남긴다 — 순서 어긋난 요청 대부분에서 Redis 왕복을 절약 / 같은 규칙이 서비스와 Lua 두 곳에 있다
  - (B) 없애고 Lua 에만 둔다 — 규칙이 한 곳 / 과거 fix 가 `LocationFilter` 로 흘러가 음수 경과로 판정되고
    (속도 검사는 하한에 걸려 건너뛰지만 거리 기준으로 `DUPLICATE`/`ACCEPTED` 가 나온다) 판정 의미가
    흐려진다. 순서 어긋난 요청마다 EVAL 왕복이 늘어난다
- **고른 것**: (A)
- **근거**: `previous` 는 #82 필터 때문에 어차피 읽으므로 이 검사는 공짜인데, 통과시키면 Redis 왕복이
  한 번 더 든다.
- **영향**: 두 곳에 같은 판정 기준(과거이거나 같으면 거부)이 있다. 한쪽만 고치면 조용히 갈리므로,
  경계(같은 시각 거부)를 양쪽 테스트에서 각각 못 박아 뒀다 — `InMemoryRiderLocationStoreTest`
  `rejectsSameTimestamp` 와 `RedisRiderLocationStoreIntegrationTest` `rejectsSameTimestamp`.

### 3. `refreshTtl` 경쟁 처리 범위

- **물었던 것**: `find` 와 `refreshTtl` 사이에 TTL 이 만료되는 경쟁도 이번 이슈에서 손댈지
- **선택지**:
  - (A) 손대지 않는다 — 이슈 구현 범위에도 없다 / 만료 직후 한 주기(최대 5~30초) 동안 배차 후보에서 빠진다
  - (B) `refreshTtl` 이 false 면 `saveIfNewer` 로 폴백 — 복구가 한 주기 빨라진다 / `DUPLICATE` 인데
    저장되는 경로가 생겨 "중복이면 기준선을 전진시키지 않는다"(#82 의 핵심 규칙)에 예외 조건이 붙는다
- **고른 것**: (A)
- **근거**: `EXPIRE` 는 값을 덮지 않으므로 이 이슈가 고치려는 "오래된 좌표가 최신을 덮는" 문제 자체가
  없다. 남는 것은 TTL 만료 틈뿐이고 다음 갱신이 최초 좌표로 복구한다.
- **영향**: `RedisRiderLocationStore.refreshTtl` 에 이 판단을 주석으로 남겼다. 나중에 이 틈이 실제
  문제가 되면(#83 배차 후보 검색이 붙은 뒤) 그때 다시 본다.

## 스스로 판단한 것

- **측정 시각을 epoch 밀리초가 아니라 고정 폭 ISO 문자열(`uuuu-MM-dd'T'HH:mm:ss.SSS`, 23자)로 인코딩**
  — 이슈는 "고정 폭"만 요구했고 표현은 정하지 않았다. epoch 은 `LocalDateTime` 에 시간대가 없어 변환에
  시간대를 가정해야 하고(그 가정이 어긋나면 9시간 틀어진 값이 조용히 저장된다 — #234 가 요청 타입을
  `Instant` 로 고른 것과 같은 위험), `redis-cli` 로 값을 봤을 때 사람이 읽을 수 없다. 고정 폭과 사전순
  정합은 ISO 로도 둘 다 만족한다.
- **Lua 가 저장된 값의 앞부분을 정규식으로 검증한 뒤 비교한다** — 사전순 비교만 하면 `"garbage"` 같은
  손상된 값이 어떤 시각보다도 크게 나와(`'g' > '2'`) 영원히 덮이지 않는다. 이슈의 「예외 흐름」이 요구한
  "손상된 값은 덮는다"가 그냥은 성립하지 않는다.
- **폭(23)을 Java 상수로 만들어 Lua 에 넘기지 않았다** — Lua 의 패턴이 폭을 함께 정의하므로
  `#storedAt` 으로 새 값을 자른다. 같은 숫자를 두 언어에 적어 두면 한쪽만 고쳐지는 날이 온다.
- **무조건 덮어쓰는 `save` 를 인터페이스에서 없앴다**(이슈는 "연산 추가"만 요구했다) — 둘을 함께 두면
  다음 사람이 더 짧은 이름을 고르고, 그 실수는 응답 200 으로 조용히 지나가 테스트에도 잘 안 걸린다.
  운영 호출처가 1곳뿐이라 지금이 없앨 수 있는 시점이다.
- **측정 시각은 반올림이 아니라 절단**(좌표는 `HALF_UP` 반올림인데 시각만 다르다) — 반올림하면 측정하지
  않은 미래 시각이 만들어지고, 미래 시각 판정(#234)은 이미 통과한 뒤라 그 값이 그대로 저장된다.
- **인메모리 대체의 `saveIfNewer` 는 반환값을 인자와 비교해 판정하지 않는다** — `compute` 결과를
  인자와 동일성 비교하면 같은 인스턴스를 두 번 넘길 때 "쓰지 않았는데 썼다"가 된다. 서비스가 그 값으로
  `NON_MONOTONIC` 을 판정하므로 대체가 틀리면 단위 테스트가 조용히 갈린다. 케이스로 고정해 뒀다.
- **`LocationFilterTest.elapsedForAtMostSpeed` 를 나노초에서 밀리초 올림으로 바꿨다** — #82 테스트지만
  이번 변경의 직접적 결과다. 목표 속도가 나오도록 경과 시간을 나노초로 올려 만들던 헬퍼가, 스냅샷이
  밀리초로 절단하면서 다시 내려 깎여 속도가 50 을 넘었다(실측 50.0022 m/s). 값 객체의 해상도와 맞춰
  계산해야 역산이 성립한다. **단언을 느슨하게 하지 않고 픽스처 계산을 고쳤다.**

## 일부러 하지 않은 것

- **배포 시 기존 Redis 값 마이그레이션**: 하지 않았다 — 이유: 값 형식이 바뀌어 이전 값(#233 형식)은 새
  파서로 읽히지 않는다. TTL 이 10분이고 BUSY 5초/AVAILABLE 30초 주기로 갱신되므로 첫 요청에서 새 형식으로
  덮인다. 조건부 갱신이 손상된 값을 덮도록 만든 것이 이 경우를 함께 처리한다 — 후속: 미등록(감내)
- **`refreshTtl` 의 조건부화**: 위 「사람이 고른 선택」 3번 — 후속: 미등록
- **`delete` 추가**: 하지 않았다 — 이유: 이 이슈 범위가 아니고, 운행 상태 변경 API 가 아직 없어 부를 곳이
  없다(`RiderLocationStore` Javadoc 에 이미 적혀 있는 한계) — 후속: 운행 상태 변경 이슈
- **경쟁 빈도 계측(메트릭)**: 하지 않았다 — 이유: 사유를 `NON_MONOTONIC` 으로 통일해 두 경로가 구분되지
  않는다. 계측이 필요해지면 값을 나누는 것과 함께 판단해야 한다 — 후속: 미등록

### 실제 경쟁을 재현했는가 — 이슈가 판단하라고 한 항목

**재현했다.** 이슈 본문 「검증 한계」는 "통합·E2E 가 Redis 를 인메모리 대체로 바꾸므로 Lua 의 원자성은
그 층에서 검증되지 않는다"고 적었지만, **그 전제는 2026-07-29 결정으로 낡았다** — 통합·E2E 는 로컬
Docker Redis 에 붙는다(`docs/05-local-dev.md` 「Redis」, `testing.md` 「Redis도 컨테이너에 붙는다」).
그래서 실제 Redis 로 스레드 16개를 동시에 풀어 재현했다.

테스트가 정말로 이 버그를 잡는지도 확인했다. `saveIfNewer` 를 비원자적 구현(`find` → 비교 →
`SET`)으로 **잠시 되돌려** 통합 테스트를 돌렸고, 두 동시성 케이스가 정확히 실패했다:

```text
같은 측정 시각으로 동시에 쓰면 정확히 하나만 성공한다 FAILED
  expected: 1
   but was: 16                      ← 16 스레드가 모두 검사를 통과해 전부 썼다

서로 다른 시각으로 동시에 쓰면 최종 값은 항상 가장 최신이다 FAILED
  [라운드 0 의 최종 값] measuredAt=2026-07-29T12:08 을 담고 있으나
  기대한 것은 measuredAt=2026-07-29T12:15  ← 오래된 좌표가 최신을 덮었다
```

단일 요청 케이스 10개는 비원자적 구현에서도 통과했다 — 그게 이 이슈의 요점이다. **순차 실행만 보는
테스트로는 이 버그를 잡을 수 없다.** 확인 후 원자적 구현으로 되돌렸고 전체 테스트를 다시 돌렸다.

라운드를 5번 도는 이유: 한 번은 우연히 가장 최신 쓰기가 마지막에 도착해 통과할 수 있다(16스레드면
약 1/16). 라운드마다 다른 라이더 id 를 쓴다 — 같은 키를 재사용하면 앞 라운드 값이 다음 라운드의
기준선이 된다.

### 검증하지 못한 것

- **실제 TTL 만료 동작**(키가 시간이 지나 사라지는 것)은 여전히 검증하지 않는다 — 10분을 기다려야 한다.
  이번에 새로 확인한 것은 "TTL 이 저장과 함께 걸린다"(`getExpire` 가 양수이고 600초 이하)까지다.
- **여러 JVM(실제 다중 인스턴스)에서의 경쟁**은 재현하지 않았다. 스레드 16개는 한 JVM 안에 있다. 다만
  Lua 의 원자성은 Redis 서버가 스크립트를 직렬화 실행하는 성질이므로, 경쟁 주체가 스레드인지 프로세스인지는
  검증 대상과 무관하다 — 어느 쪽이든 같은 Redis 커넥션 풀 밖에서 동시에 도착한다. 인스턴스가 정말 두 대일
  때만 드러나는 것(SSE 팬아웃 등)은 plan.md 의 「다중 인스턴스 로컬 검증 환경」 몫이다.
- **CI 는 여전히 테스트를 돌리지 않는다**(`deploy.yml` 의 `-x test`). 이슈의 완료 조건에 "CI 테스트 통과"가
  있지만 CI 에 테스트 단계 자체가 없어 로컬 실행으로 갈음했다. MySQL·Redis 서비스 컨테이너가 필요하다.

## 새로 생긴 미결 사항

- **`NON_MONOTONIC` 이 두 원인을 겸한다** — 클라이언트가 순서를 어겨 보낸 것과 인스턴스 간 경쟁에서 진 것이
  같은 사유·같은 로그 라인으로 나간다. 경쟁 빈도를 알아야 할 때(부하 테스트, 인스턴스 수 조정) 값을 나눌지
  판단해야 한다.
- **배포 직후 최대 10분간 이전 형식 값이 "위치 없음"으로 읽힌다** — 조건부 갱신이 덮으므로 첫 위치 요청에서
