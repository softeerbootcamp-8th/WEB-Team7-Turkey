# 배송요청 생성 + 배송요금 포인트 차감 작업 기록

- 이슈: [#37](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/37) (REQ-ORD-002),
  [#40](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/40) (CUS-PAY-002)
- 브랜치: `feature/37-req-ord-002-배송-주문-생성`
- 범위: backend
- 작성일: 2026-08-01

## 무엇을 만들었나

`POST /api/customer/deliveries` 를 구현했다. 그동안 `return null` 이던 자리다.
주문 생성(#37)과 포인트 차감(#40)을 **한 이슈처럼 한 트랜잭션에** 넣었다 — 양쪽 이슈 비고가
"하나의 상위 트랜잭션으로 처리하여 하나라도 실패하면 전체 롤백"이라고 명시한다.

한 번의 호출에서 일어나는 일: 멱등 조회 → 서버 요금 재계산·대조 → `delivery_order`(WAITING) →
`order_fare_snapshot`(ESTIMATE) → `point_wallet` 차감 → `point_transaction`(ORDER_USE).

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/customer/deliveries` | 배송요청 생성 + 요금 포인트 차감 | 401 미로그인 / 402 포인트 부족 / 409 진행 중 요청·동시 재전송·요금 변경 / 400 입력 오류·거리 초과·정책 없음 |

요청 계약은 #175에서 정의된 `DeliveryCreateRequest` 를 쓰되 **`estimatedFare` 를 추가**했다(아래 1번).

### 화면

해당 없음. 프론트 연동은 이 이슈 범위 밖이다. 다만 요청 스키마가 바뀌었으므로 Orval 재생성이 필요하다.

### 스키마 변경

`V18__relax_point_transaction_request_key_unique.sql` 한 건. `point_transaction` 의 요청키 유니크를
`(request_key)` 에서 `(request_key, transaction_type)` 으로 완화한다.

V17의 두 제약이 서로 다른 말을 하고 있었다 — `uk_point_transaction_order_type` 은 한 주문에
ORDER_USE 1건 + ORDER_REFUND 1건을 허용하는데, `uk_point_transaction_request` 가 그 두 행이 같은
키를 갖는 것을 막았다. `CHAR(36)` 고정폭이라 접미사도 못 붙이므로, 환불이 아무것도 식별하지 못하는
새 UUID를 지어내야 했다. 제약을 **넓히는** 방향이라 기존 데이터로 실패할 수 없고 롤링 배포에서도
구 버전 코드가 깨지지 않는다.

나머지 테이블·제약은 V10·V12·V17에 이미 있다.

## 사람이 고른 선택

### 1. 요청에 예상 요금(estimatedFare)을 받아 대조할 것인가

- **물었던 것**: 이슈 #37 입력값에 "예상 요금"이 있고 예외 처리에 "서버 계산 요금과 요청 요금
  불일치"가 있는데, #175에서 확정된 `DeliveryCreateRequest` 에는 금액 필드가 없다. 어느 쪽을 따를까
- **선택지**:
  - (A) 받지 않는다 — 현재 DTO 유지 / 이슈의 그 예외 케이스가 사라진다
  - (B) 받고 불일치 시 실패 — 이슈에 충실 / 계약에 필드 추가, 요금이 바뀌면 사용자가 막힌다
  - (C) 받되 서버 값으로 진행하고 응답으로 알린다 — 왕복이 없다 / 동의하지 않은 금액이 결제된다
- **고른 것**: (B)
- **근거**: 사람의 말 그대로 — *"결제 화면에 5천원이래서 결제하기 했더니 비용 계산 다시해서 5500원
  결제되면 어쩌려고"*. (A)도 같은 결과를 낳는다는 점이 결정적이었다. (C)는 그 시나리오 자체다.
- **영향**: `DeliveryCreateRequest` 에 `estimatedFare`(필수, 양수)가 생겼다. **결제 금액으로는 쓰이지
  않는다** — 차감 금액은 항상 서버 재계산값이고 이 필드는 대조 전용이다. 프론트는 `/quote` 응답의
  `fare.totalFare` 를 그대로 실어 보내면 된다.

### 2. 포인트 차감을 어떻게 구현할 것인가

- **물었던 것**: 이슈 #40 흐름 ⑤가 "조건부 갱신으로 차감"이라고 적혀 있는데, 원장에
  `balance_before` 가 필요해서(`ck_point_transaction_balance`) 조건부 UPDATE 만으로는 값을 모른다
- **선택지**:
  - (A) `FOR UPDATE` 로 읽고 차감 — #33(충전 승인) 선례와 동일 / 이슈 문구와 글자 그대로는 다르다
  - (B) 조건부 UPDATE 후 재조회로 before 역산 — 이슈 문구 충실 / 원장 값을 역산으로 만든다
- **고른 것**: (A)
- **근거**: 잔액 변경 경로가 충전 승인과 하나의 방식으로 통일된다.
- **영향**: `PointChargeApprover` 와 같은 순서(잠금 → before 읽기 → 증감 → 원장 저장)를 그대로 따랐다.
  "동시 요청 중 한 건만 성공"(#40 예외 처리)은 조건부 UPDATE 가 아니라 이 잠금이 보장한다.

### 3. 포인트 부족 시 응답 코드

- **물었던 것**: 400 / 409 / 402 중 무엇
- **선택지**:
  - (A) 402 PAYMENT_REQUIRED — 프론트가 코드만으로 충전 화면 분기 / 저장소에 선례 없음
  - (B) 409 — 관례 일치 / 진행 중 1건 위반과 같은 코드라 message 로만 구분(#56과 같은 문제)
  - (C) 409 + 응답 본문에 부족액 — 정보까지 준다 / `ApiResponse`·`GlobalExceptionHandler` 구조 변경
- **고른 것**: (A)
- **근거**: #36(결제 가능 여부 확인 API)을 접으면서 **이 실패 응답이 "포인트가 모자란다"를 알려 줄
  유일한 수단**이 됐다. 구분 가능성이 그만큼 중요해졌다.
- **영향**: 이 저장소에서 402를 쓰는 첫 API다. E2E가 실제로 402가 나가는지 고정한다.

## 스스로 판단한 것

- **`payForOrder` 를 `CustomerPaymentService` 에 두었다** — 처음에는 `OrderPointPaymentService` 를
  따로 만들었다가 되돌렸다. 분리 근거로 "소스 FK가 다르다"와 "생성자가 바뀌어 기존 테스트가 깨진다"를
  들었는데, 뒤엣것은 설계 이유가 아니라 번거로움 앞엣것도 클래스를 나눌 만큼은 아니었다.
  **순환 의존과도 무관하다** — `CustomerPaymentService` 는 order 서비스를 참조하지 않으므로 어느
  쪽이든 단방향이다. 대신 그 클래스가 충전과 주문 결제를 함께 갖게 됐다.
  CUS-PAY-003(ORDER_REFUND)도 여기 붙는다.
- **차감 메서드를 `Propagation.MANDATORY` 로 선언했다** — 근거: 두 이슈 비고의 "하나의 상위
  트랜잭션"을 애노테이션으로 강제한 것이다. 기본값(`REQUIRED`)이면 누군가 이 메서드만 따로 호출했을
  때 조용히 새 트랜잭션이 열려 **주문 없이 포인트만 빠져나가는** 경로가 생긴다.
- **의존 방향은 order → payment 다** — 근거: 반대로 하면 빈 순환이 되어 기동이 실패한다(Boot 3.4는
  순환 참조 기본 금지). #36 작업 중에 발견한 것이고, 이번에 그 방향으로 실제 코드가 생겼다.
  payment 가 order 를 참조하는 것은 엔터티까지(`PointTransaction.deliveryOrder`)이고 서비스는 아니다.
- **중복·동시성 판정을 앱이 아니라 DB 제약에 맡겼다** — 근거: 조회 후 판단하면 그 사이에 다른 요청이
  끼어드는 창이 남는다. `uk_delivery_customer_request`(멱등키), `uk_delivery_active_customer`(진행 중
  1건), `uk_point_transaction_order_type`(이중 차감) 세 개가 판정하고, 앱은
  `DataIntegrityViolationException` 을 409로 바꾸기만 한다. `save` 가 아니라 `saveAndFlush` 를 쓴 이유도
  같다 — 지연 flush 면 제약 위반이 커밋 시점에 터져 catch 를 빠져나간다(#32에서 확인된 것).
- **요금 변경을 400이 아니라 409로 했다** — 근거: 요청 자체는 형식·값 모두 유효하고, 어긋난 것은 그
  사이 바뀐 서버의 요금 정책이다. 이 엔드포인트의 400은 Bean Validation 오류로 이미 많이 나가는데,
  요금 변경은 사용자가 입력을 고쳐 해결할 수 있는 종류가 아니라 화면이 요금을 다시 받아 보여줘야
  하는 상황이라 섞이면 안 된다.
- **멱등 재전송의 응답 요금을 저장된 ESTIMATE 스냅샷에서 되읽는다** — 근거: 그 시점에 다시 계산하면
  정책이 바뀐 뒤에는 **실제 청구된 금액과 다른 값**을 돌려주게 된다. 통합 테스트로 고정했다.
- **요금 계산을 `FareCalculation` 레코드로 감쌌다** — 근거: 견적(#39)은 요금 분해만 있으면 되지만
  주문 생성은 `order_fare_snapshot.fare_policy_id` FK 때문에 **정책 엔터티까지** 필요하다. 계산을
  복제하지 않으려면 두 경로가 같은 내부 메서드를 써야 했다. `quoteFare` 의 동작은 그대로다.
- **원장 `request_key` 로 주문 요청키를 그대로 썼다** — 근거: 컬럼이 `CHAR(36)` 고정폭이라 접미사를
  붙일 수 없다. 아래 미결 참조.
- **인터셉터에 와일드카드가 아니라 정확 경로를 등록했다** — 근거: `/api/customer/deliveries/**` 로
  넓히면 형제 경로 `/quote`(비로그인 견적)가 조용히 401이 된다. "쿠키 없이 `/quote` 는 200"을 E2E
  회귀로 고정했다.
- **`@ResponseStatus(CREATED)` 를 구현체에도 달았다** — 근거: 인터페이스에도 있지만(#175) 그 위치는
  이 저장소에서 201을 실제로 내보낸 적이 없는 자리다. 201을 내보내는 다른 API는 모두 구현체에 달고
  있고 `references/backend.md` 도 그렇게 하라고 한다.

### 검증하지 못한 것

- **컴파일과 테스트 실행.** 사람이 직접 돌리기로 해서 실행하지 않았다. 생성자 인자가 늘어난
  `DeliveryService`(4개 추가)의 수동 생성 지점은 `DeliveryServiceTest` 하나뿐이고 `@Mock` 으로 채웠다.
- **진짜 동시 요청.** 통합 테스트는 순차 호출이다. 같은 고객의 동시 주문은
  `uk_delivery_active_customer` 가, 잔액 경쟁은 지갑 행 잠금이 막지만 멀티스레드로 재현하지 않았다
  (#25 회원가입과 같은 상태).
- **`@ResponseStatus` 가 인터페이스에서도 동작하는지.** 구현체에 달아 회피했으므로 이 PR로는
  알 수 없다.

## 새로 생긴 미결 사항

- (해소됨) 원장 요청키 제약은 V18로 `(request_key, transaction_type)` 으로 완화했다. 다만 **Flyway
  파일이 순번 방식이라 동시에 열린 다른 브랜치와 V18이 충돌할 수 있다** — 머지 전에 원격 브랜치의
  최신 번호를 확인해야 한다.
- **진행 중 1건 위반과 동시 재전송이 같은 409로 나간다**(#37). 둘 다 같은 INSERT 의
  `DataIntegrityViolationException` 이라 앱에서 구분할 수 없다 — 구분하려면 위반한 제약명을 예외
  메시지에서 파싱해야 하는데 DB 벤더 문자열에 의존하게 된다. 여기에 "요금 변경" 409까지 더해져
  이 엔드포인트의 409는 세 가지 의미를 겸한다. #56의 에러코드 체계 논의와 같은 사안이다.
- **402를 이 저장소에서 처음 쓴다**(#40). 다른 결제 실패 경로(충전 승인 거절 등)와 코드 사용이
  일관되지 않을 수 있어, 결제 관련 응답 코드 표를 한 번 정리할지 판단이 필요하다.
- **`/api/customer/deliveries` 아래 인증은 정확 경로로 한 건씩 등록한다**(#37). `/quote` 가 비로그인
  API 인 동안은 와일드카드를 쓸 수 없다. 목록·상세·취소 API 를 구현할 때마다 등록을 추가해야 한다.
