## 사람이 고른 선택

### 1. #61(인증 등록)과 이미 병합된 #62(완료 처리)의 관계를 어떻게 가져갈지

- **물었던 것**: #61은 "완료 인증 등록만으로 COMPLETED로 바뀌지 않는다"고 명시해 등록과 완료를
  별도 단계로 요구한다. #62 이슈 본문도 원래 "완료 인증정보 존재 여부 확인"이라고 적어 인증이
  먼저 존재한다는 전제였다. 하지만 실제 구현(`RiderDeliveryService.complete()`)은 완료 요청
  안에서 인증정보(`RiderDeliveryCompleteRequest.proofType/proofValue`)를 그 자리에서 새로
  생성하는 1단계로 두 이슈를 병합해 버렸다. 이 상태에서 #61을 어떻게 처리할지 물었다.
- **선택지**:
  - (A) 현재 방식 유지 — #62가 이미 원자적으로 처리 중이라 새 엔드포인트를 만들지 않고, "완료
    요청에 인증정보가 항상 필요하다"는 사실만 문서화. 이미 병합된 코드를 안 건드려 리스크가 가장
    낮음. 단, #61 이슈 스펙(등록/완료 분리)을 문자 그대로 구현하지는 않음.
  - (B) 완전 분리 — #61을 별도 "인증 등록" API로 새로 만들고, #62의 완료 API에서 인증
    파라미터를 없애 "이미 등록된 인증이 있어야 완료 가능"으로 바꿈. 원래 이슈 스펙대로지만 이미
    병합된 #62 코드(요청 DTO·서비스 검증)를 수정해야 하고, 완료 가능 여부 판정이 두 요청에
    걸쳐 일어나 정합성 검증 지점이 늘어남.
  - (C) 하이브리드 — #61을 새 엔드포인트로 추가하되 #62 완료 API는 그대로 두고, "인증이 이미
    있으면 그걸 쓰고 없으면 요청값으로 새로 생성"으로 확장. 기존 동작과 100% 호환되지만 분기가
    하나 늘어남.
- **고른 것**: (A) 현재 방식 유지
- **근거**: 사용자 확인(AskUserQuestion, 2026-08-04) — "현재 방식 유지 (추천)"을 선택.
- **영향**: `RiderDeliveryCompleteRequest`(`proofType`/`proofValue` 필수)와
  `RiderDeliveryService.complete()`의 검증 순서는 변경되지 않는다. 완료 요청은 앞으로도 계속
  인증정보를 함께 받는다 — 사진 등 인증정보 없이 배송을 완료할 수 없다(이번 검토에서 확인한 현재
  동작 그대로 유지). 프론트가 이 완료 화면(`CompleteDeliveryStage.tsx`, 아직 API 미연동 정적
  시안)을 연동할 때도 이 계약을 그대로 따라야 한다.
