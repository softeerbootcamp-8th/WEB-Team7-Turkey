- 브랜치: `feature/21-phone-verification-confirm` (`feature/20-phone-verification-request` 위에 스택 — 아래 참고)
- 범위: backend
- 작성일: 2026-07-28

## 무엇을 만들었나

`#20`에서 저장한 인증번호를 검증하는 API를 만들었다. 검증에 성공하면 그 코드는 즉시 지워 재사용을 막고,
일회성 "인증 완료 토큰"을 새로 발급한다 — 이 토큰이 `#25`(회원가입)·`#22`(아이디 찾기)가 "휴대전화 인증
완료"를 확인하는 방법이 된다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/phone-verifications/confirm` | 인증번호 검증 + 일회성 토큰 발급 | 404 요청 이력 없음/만료, 400 불일치, 429 시도 횟수(5회) 초과 |

### 화면

해당 없음 (백엔드 API만).

### 스키마 변경

해당 없음. Redis TTL로만 관리.

## 브랜치를 #20 위에 쌓은 이유

`#21`은 `#20`이 만든 `VerificationCodeStore`/`RedisVerificationCodeStore`를 그대로 확장해야 하는데,
`#20`의 PR([#174](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/pull/174))이 아직 `dev`에
머지되지 않았다. `dev`에서 새로 브랜치를 따면 그 클래스들이 없어서, `feature/20-phone-verification-request`
위에 `feature/21-phone-verification-confirm`을 쌓았다. **`#174`가 먼저 머지된 뒤에 이 브랜치의 PR을 올리거나,
PR 베이스를 `feature/20-...`으로 잡아야 diff가 깔끔하다.**

## 사람이 고른 선택

### 1. 인증 완료 결과를 어떻게 다음 이슈(#25)로 넘길 것인가

- **물었던 것**: 검증 성공 뒤 "인증 완료" 상태를 어떻게 전달할지 — 이게 `#25`의 요청 계약도 같이 정한다.
- **선택지**:
  - (A) 일회성 토큰 발급 — 인증을 실제로 수행한 요청자만 다음 단계를 진행할 수 있음(보안 정확) / `#25` 요청에
    `verificationToken` 필드가 필요해짐
  - (B) 전화번호 기준 재조회(플래그) — `#25`가 토큰 없이 phoneNumber만 재확인하면 됨(구현 단순) / 다른 주체가
    같은 전화번호로 10분 안에 가로채 회원가입을 시도해도 서버가 구분 못함
- **고른 것**: (A)
- **근거**: 처음에는 사용자가 "플래그면 Redis에 계속 쌓이는 거 아니냐" "토큰이면 성능이 떨어지지 않냐"고
  되물어서, 두 방식 다 TTL 기반 Redis 키 하나씩이라 메모리·성능 특성은 사실상 동일하다고 먼저 설명했다.
  실제 차이는 보안(인증 수행자와 다음 단계 요청자가 같은 주체임을 증명할 수 있는지)이라는 걸 확인한 뒤,
  토큰 방식으로 결정.
- **영향**: `#25`(고객 회원가입)와 `#22`(아이디 찾기) 요청 DTO에 `verificationToken` 필드가 필요하다.
  이 필드로 Redis `phone-verification:verified:{token}` 키를 조회해 `purpose:phoneNumber`가 일치하는지
  검증해야 한다 — **이 조회·소비(consume) 로직은 이번에 만들지 않았다** (아래 「일부러 하지 않은 것」).

### 2. 인증번호 오입력 허용 횟수

- **고른 것**: 5회 (추천안 그대로)
- **영향**: `PhoneVerificationService.MAX_ATTEMPTS = 5`. `phone-verification:attempts:{purpose}:{phoneNumber}`
  키로 카운트하며, 코드와 같은 TTL(5분)로 만료된다.

### 3. 인증 완료 토큰의 유효시간

- **고른 것**: 10분 (추천안 그대로)
- **근거**: 인증 직후 회원가입 폼 입력을 마칠 시간을 고려해, 코드 자체의 5분보다 약간 길게.
- **영향**: `PhoneVerificationService.VERIFIED_TOKEN_TTL = Duration.ofMinutes(10)`.

## 스스로 판단한 것

- **"이력 없음"과 "만료"를 구분하지 않음**: 이슈 예외 목록엔 둘이 따로 있지만, Redis는 키가 없으면 그게
  "한 번도 요청 안 함"인지 "요청했지만 만료됨"인지 구분할 수 없다(같은 신호). 둘 다 404 + "다시 요청해
  주세요" 메시지로 묶었다.
- **HTTP 상태 코드 배정**: `#20`이 이미 409/429/502를 의미별로 나눠 쓴 선례가 있어서, `#21`도 이어서
  코드없음/만료 → 404(조회할 대상이 없음), 불일치 → 400(입력값 문제), 시도횟수 초과 → 429(레이트 제한,
  `#20`의 쿨다운 429와 같은 의미 범주)로 나눴다.
- **시도 횟수는 코드 존재 확인 다음에 증가**: 코드가 아예 없는(이력없음/만료) 경우엔 시도 횟수를 늘리지
  않는다 — 애초에 시도할 대상이 없었으니 "오입력"으로 볼 수 없다고 판단.
- **검증 성공 시 코드+시도횟수만 지우고 쿨다운은 그대로 둠**: 쿨다운은 "SMS 재전송" 남용을 막는 게
  목적이라, 검증 성공과는 관계가 없어서 굳이 지우지 않았다. 60초짜리라 어차피 금방 만료된다.
- **토큰 생성 방식**: `SecureRandom` 24바이트를 URL-safe Base32(Base64 URL 인코딩, 패딩 제거)로 인코딩.
  기존 `generateCode()`가 이미 같은 `SecureRandom` 인스턴스를 쓰고 있어 재사용했다.

## 일부러 하지 않은 것

- **토큰 소비(consume) API**: `#25`/`#22`가 `verificationToken`을 받아 Redis에서 조회하고 1회성으로
  삭제하는 로직은 이번에 만들지 않았다. `VerificationCodeStore`엔 `saveVerifiedToken()`만 추가했고, 읽는
  쪽은 그 이슈에서 실제로 필요할 때 추가한다. — 후속: `#25`, `#22`
- **토큰의 purpose 검증**: 토큰 값에 `purpose:phoneNumber`를 같이 저장해뒀지만, 그걸 실제로 검사해서
  "FIND_ID로 받은 토큰을 SIGNUP에 쓰지 못하게 막는" 로직은 소비 쪽(`#25`)에서 구현해야 한다. 지금은
  값만 준비해뒀다.
- **동시에 같은 코드로 확인 요청이 여러 번 온 경우의 경쟁 조건**: 요청(`request`)의 쿨다운 선점처럼
  원자적으로 만들지 않았다. `getCode` → `incrementAttempts` → 비교 → `clearVerification` 사이에 이론상
  경쟁 창이 있지만(예: 두 요청이 동시에 올바른 코드로 확인하면 토큰이 두 개 발급될 수 있음), 브루트포스
  방어(시도 횟수 제한)만큼 중요한 경쟁은 아니라고 판단해 이번엔 다루지 않았다. — 후속: 미등록(필요성
  재검토 후)

### 검증하지 못한 것

- Redis 실제 TTL 만료(코드 5분, 시도횟수 5분, 토큰 10분) — 인메모리 대체로만 검증했다(`#20`과 동일한 한계).
- `incrementAttempts`의 "카운터가 처음 생겼을 때만 TTL을 건다" 로직(INCR 후 조건부 EXPIRE)의 실제 Redis
  동작 — 인메모리 구현은 이 부분을 단순 카운터로 흉내내서 TTL 타이밍 자체는 검증하지 못했다.
- 로컬 Docker(MySQL+Redis) 실기동 확인 — `#20`과 같은 이유(Docker Desktop 미가동)로 스킵.

## 새로 생긴 미결 사항

- 인증 완료 토큰의 소비(조회+1회성 삭제) 로직은 `#25`/`#22`에서 구현 필요 — `saveVerifiedToken()`은
  준비됐지만 읽는 쪽이 아직 없음
- `confirm()`에 `request()`의 쿨다운 선점 같은 원자적 보호가 없어, 동시에 같은 유효 코드로 확인 요청이
  오면 토큰이 중복 발급될 수 있음 — 발생 가능성과 실제 영향을 재검토해 필요하면 원자적 처리로 바꿀 것
