## 무엇을 만들었나

`GET /api/rider/requests`의 keyset(커서) 페이지네이션(`size`/`after*`/`hasNext`)은 #60에서 이미
구현·테스트돼 있었고, 프론트 연동만 이 이슈 범위였다. WAITING 콜이 페이지 크기(기본 20건)를
넘으면 그 이후 항목을 볼 수단이 화면에 없던 문제(#496 작업 중 발견)를 고쳤다.

### API

해당 없음. 백엔드는 #60에서 이미 완성돼 있고 이번에는 건드리지 않았다.

### 화면

`rider/_authed/requests/index.tsx`에 다음 페이지 누적 상태(커서·목록·`hasNext`)와 "더보기" 버튼을
추가했다. 순수 로직(`buildNextRequestCursor`)은 `-requestList.ts`로 분리했다.

### 스키마 변경

해당 없음.

## 사람이 고른 선택

### 1. 다음 페이지 진입 UI 방식 — 더보기 버튼 vs 무한 스크롤

- **물었던 것**: 이슈 자체가 "계약 확정 단계에서 결정"하라고 명시적으로 남겨둔 항목.
- **선택지**:
  - (A) 더보기 버튼 — 요청 시점이 명확해 구현·테스트가 단순. 매번 눌러야 하는 수고가 있음.
  - (B) 무한 스크롤(IntersectionObserver) — 스크롤만 하면 되는 익숙한 패턴. 테스트에
    `IntersectionObserver` 모킹이 필요.
- **고른 것**: (A)
- **근거**: 처음 든 이유(테스트 복잡도)는 사용자 본인에게 실익이 없다는 지적을 받고 재검토했다.
  최종적으로 남은, 이 화면·이 API에 실제로 걸리는 이유는 두 가지다.
  1. 이 화면은 정렬된 상위 후보 중에서 빠르게 골라 수락하는 화면이라(#56, 다른 라이더와 경쟁),
     20건을 넘겨 더 보는 것 자체가 드문 경로다. 자주 안 쓰이는 경로에 무한 스크롤의 매끄러움을
     투자할 이유가 약하다.
  2. `RiderDeliveryRequestService.getDeliveryRequests`는 페이지 요청마다 bounding box 조회(인덱스
     사용, 가벼움) 이후 **candidate 전체에 대해 거리 계산·필터·정렬·커서 선형 스캔을 처음부터
     다시 수행**한다(#60에서 목록이 초 단위로 바뀌는 도메인이라 의도적으로 이렇게 설계함, 후보는
     "수백 건" 규모 전제, #367). 무한 스크롤은 모바일 관성(모멘텀) 스크롤 특성상 사용자가 한 번
     스크롤한 것만으로 이 무거운 재계산이 연달아 여러 번(감지 지점을 관성으로 통과) 트리거될 수
     있다 — 사용자가 실제로 요청한 횟수와 서버 재계산 횟수가 비례하지 않게 된다. 명시적 버튼은
     "탭 1번 = 재계산 1번"을 보장한다.
- **영향**: 백엔드 API·계약은 변경 없음. 화면 상태 관리(커서 누적)를 직접 구현해야 했다(아래
  "스스로 판단한 것" 참고).

### 2. 더보기 버튼 배치 — 목록 끝 인라인 vs 화면 하단 고정 영역

- **물었던 것**: 처음엔 묻지 않고 "하단 고정 영역(언제든 누를 수 있게)"으로 임의 추천했다가,
  실제 화면에서 "목록 끝까지 스크롤해야 버튼이 보인다"는 지적을 받고 다시 논의했다.
- **선택지**:
  - (A) 하단 고정 영역(기존 "새로고침" 버튼 자리) — 스크롤 위치와 무관하게 언제든 누를 수 있음.
  - (B) 목록 끝 인라인(현재 구현) — 로드된 카드를 전부 스크롤해야 버튼이 나타남.
- **고른 것**: (B), 기존 구현 유지
- **근거**: "탭 1번 = 재계산 1번"이라는 성질은 버튼 위치와 무관하게 둘 다 성립해서, 결정 1번의
  논리로는 (A)/(B)를 가를 수 없었다. 대신 인라인 배치는 "지금 로드된 20건을 전부 보고, 그중
  마음에 드는 게 없을 때만 다음 페이지를 요청"하게 만드는 자연스러운 장치로 작동한다 — 이미
  정렬된 목록이라 좋은 후보는 위쪽에 있으므로, 다 보지 않고 성급하게 다음 페이지를 요청할 이유가
  이 도메인에는 없다. 하단 고정 배치가 주는 "언제든 누를 수 있음"은 이 화면에 실제로 필요한
  이득이 아니었다(범용적인 UI 편의성 직관이었을 뿐, 이 화면 특성에서 온 근거가 아니었음).
- **영향**: 코드 변경 없음(원래 인라인 구조를 그대로 유지).

## 스스로 판단한 것

- **커서 필드 선택을 `hasPosition`(좌표 유무)으로 판단함**: 화면은 정렬 기준을 항상 `DISTANCE`로
  보내지만, 백엔드는 좌표가 없으면 `REQUESTED_AT`으로 조용히 대체한다(#55 계약,
  `RiderDeliveryRequestService.getDeliveryRequests`의 `effectiveSort`). `requireCursorMatchesSort`가
  이 실제 적용 기준과 커서 필드가 안 맞으면 400을 던지므로, `buildNextRequestCursor`는 "요청한
  sort"가 아니라 좌표 유무로 커서 필드(`afterDistanceMeters` vs `afterRequestedAt`)를 고른다.
- **itemFilter는 변경 시 커서·누적 목록을 초기화하지 않음**: 이슈 문구("필터·정렬 기준이 바뀌면
  커서를 초기화")는 서버 필터를 염두에 둔 일반론이지만, 이 화면의 물품 크기 필터는 서버 요청
  파라미터가 아니라 순수 클라이언트 로컬 필터다(#60 당시에도 프론트 연동 자체가 없어 서버 필터
  파라미터가 화면에 노출된 적이 없음). 그래서 바뀌어도 재조회할 필요가 없고, 이미 불러온 페이지를
  버리면 오히려 손해다 — 필터링만 다시 적용한다.
- **반경(`radiusMeters`)·좌표 변경 시에만 커서·누적 목록을 초기화**: 이 둘은 실제 서버 요청
  파라미터라 바뀌면 이전 페이지들의 정렬·필터 기준 자체가 달라지므로 첫 페이지부터 다시 쌓는다.
- **`hasLoadedOnce` 플래그로 "목록이 사라지는 깜빡임"을 막음**: react-query는 쿼리 키(커서 포함)가
  바뀌면 그 키의 캐시가 없는 동안 `isSuccess`가 잠깐 꺼진다. "더보기" 클릭 시 이 순간에
  `isSuccess` 기준으로 목록을 그렸다면 이미 보여주던 카드들이 사라지고 스피너로 바뀌는 회귀가
  생긴다. 그래서 목록 렌더링은 `isSuccess`가 아니라 "한 번이라도 로드에 성공했는가"를 뜻하는
  별도 상태로 게이팅했다.
- **다음 페이지 요청 실패는 전체 오류 화면이 아니라 버튼 옆 인라인 오류로 처리**: 첫 페이지
  실패(커서 없음)는 기존처럼 전체 오류 화면을 쓰고, 이미 목록이 있는 상태에서 다음 페이지 요청만
  실패하면 이미 보여주던 목록은 유지하고 버튼 근처에만 오류 문구를 띄운다 — 이미 본 콜 목록을
  실패한 append 요청 하나 때문에 통째로 지울 이유가 없다.
- **중복 요청 방지**: "더보기"·"새로고침" 모두 `requestsQuery.isFetching`이면 무시하도록 가드했다
  (CLAUDE.md "중복 요청·동시 요청 고려" 원칙).
- **키셋 중복 제거(dedupe) 로직을 넣지 않음**: 백엔드가 매 요청마다 최신 목록을 다시 걸러 정렬한
  뒤 "커서보다 뒤"만 반환하도록 보장하므로(#60), 프론트에서 별도로 `deliveryId` 중복을 걸러낼
  필요가 없다고 판단했다.

  별도 이슈로.

## 새로 생긴 미결 사항

- "더보기"를 반복해서 누르면 그때마다 백엔드가 bounding box 후보 전체를 다시 필터·정렬한다
  (#60에서 이미 알려진 설계, 위 "사람이 고른 선택 1번" 참고). 지금은 후보 규모가 작아 문제
  없지만, `radiusMeters` 상한 미비(CLAUDE.md 기존 미결)와 겹쳐 후보가 커지면 "더보기"를 여러 번
  누르는 라이더가 늘 때의 비용이 실측된 적이 없다. CLAUDE.md에도 한 줄 추가함.
- **itemType(물품 종류) 필터가 서버 파라미터로 노출된 적이 없다는 게 이번에 드러났다**(#214부터
  클라이언트 전용). 이 이슈로 keyset 페이지네이션이 생기면서, 서버가 페이지를 자른 뒤 클라이언트가
  itemType을 거르는 구조가 `hasNext`와 화면에 보이는 개수를 어긋나게 만들 수 있다는 걸 확인했다
  (예: `hasNext=false`인데 특정 물품만 보면 화면엔 몇 건 안 보임). `#522`로 분리해 서버 필터로
  이관하기로 했다.
- **`sortDirection=DESC`(현재 `FARE` 기본값)와 keyset 커서가 결합됐을 때 정확히 동작하는지
  검증하는 테스트가 없다.** `isAfterCursor`/`comparatorFor` 코드를 추적한 결과로는 맞게 동작해야
  하지만(주 정렬키만 방향에 따라 부호를 뒤집고, `deliveryId` tiebreak는 항상 오름차순으로 고정 —
  둘이 같은 규칙을 공유), 단위·통합·E2E 테스트 어디에도 `FARE`+`DESC`+커서 조합을 실제로 확인하는
  케이스가 없다(서브에이전트로 세 테스트 파일 전수 확인). `#522`에서 테스트를 추가하기로 했다.
  CLAUDE.md에도 두 항목 모두 반영함.
