## 무엇을 만들었나

의미 있게 움직이지 않은 좌표와 물리적으로 불가능한 이동을 걸러 낸다. 새 엔드포인트는 없고
`POST /api/rider/location`(#81)의 응답에 판정 결과가 추가된다.

작업 중에 **테스트 인프라가 통째로 바뀌었다** — 통합·E2E가 Redis 인메모리 대체 대신 실제 Docker
Redis에 붙게 됐다(사람 지시). 그 과정에서 테스트가 컨테이너가 아닌 호스트 Redis로 돌고 있었다는
것을 발견했다(아래 「스스로 판단한 것」·「검증하지 못한 것」).

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/rider/location` | 변경 없음. 응답 `reason` 에 `DUPLICATE`·`IMPLAUSIBLE_SPEED` 가 추가됨 | 기존과 동일 |

`DUPLICATE` 는 `applied=true, published=false` 다 — **저장은 하되 전파하지 않는 유일한 판정**이다.

## 사람이 고른 선택

### 1. 기준선 오염 복구 방식

- **물었던 것**: 이상 속도 판정의 기준이 되는 "이전 위치"가 오염되면 이후 정상 좌표가 전부 막힌다.
  최초 좌표는 비교 대상이 없어 무조건 통과하므로 실제로 일어날 수 있다. 어떻게 복구할까?
- **선택지**:
  - (A) 이전 위치가 30초 이상 지났으면 무조건 새 기준으로 — 상태를 추가하지 않는다 / 복구 약 35초
  - (B) Redis 카운터로 연속 3회를 센다 — 복구 약 15초로 빠르다 / 라이더당 키가 하나 늘고 TTL 관리가
    붙으며 매 거부마다 라운드트립이 하나 더 생긴다
  - (C) 복구 장치 없이 TTL 10분에 맡긴다 — 가장 단순 / **라이더가 최대 10분간 지도에서 사라진다**
- **고른 것**: (A)
- **근거**: 사람 확인. 상태를 추가하지 않는 쪽.
- **영향**: 이 결정이 규칙의 형태를 바꿨다. "오염되면 복구한다"가 아니라 **"속도 검사는 경과 1초 ~
  30초 사이에만 적용한다"** 는 유효 구간으로 표현된다. 거부된 좌표는 기준을 전진시키지 않으므로 기준은
  거부될 때마다 늙고, 30초를 넘기면 자동 교체된다. 복구는 부수 효과로 따라온다.
  그리고 이 형태가 **원래 의도보다 더 옳다** — 앱이 백그라운드였거나 터널을 지나 30초 이상 끊긴 뒤의
  큰 이동은 실제로 정상이고, 그걸 이상 속도로 버리면 안 된다. 카운터 방식으로는 그 경우를 구분하지
  못한다. 새 CLAUDE.md 규칙(상태를 JVM에 두지 않는다)과도 맞는다.

### 2. `find` → `save` 의 원자성

- **물었던 것**: 수평 확장으로 같은 라이더의 요청 둘이 다른 인스턴스에서 동시에 처리되면 오래된
  좌표가 나중에 덮을 수 있다.
- **선택지**: (A) 문서화만 하고 다음 이벤트가 복구하도록 둔다 / (B) Lua 스크립트로 원자적 CAS
- **고른 것**: (B)
- **근거**: 사람 확인.
- **영향**: **#82 범위가 아니라고 판단해 [#250](https://github.com/softeerbootcamp-8th/WEB-Team7-Turkey/issues/250)
  으로 분리했다**(#81 계열). 필터링이 아니라 저장 계층의 경쟁 문제이고, 수평 확장 요구사항에서
  파생됐다. 미착수다. `refreshTtl` 도 같은 경쟁을 갖고 있어 그 이슈에서 함께 봐야 한다.

### 3. Redis 테스트를 실제 컨테이너로

- **물었던 것**(작업 중 지시): "Redis 쓰는 테스트는 지금부터 MySQL 처럼 Redis 도커를 띄워 검증한다."
  이어서 테스트용 Redis 를 개발용과 어떻게 분리할지.
- **선택지**: (A) 별도 로직 DB(`database: 1`) + `FLUSHDB` / (B) 개발과 같은 DB 0 공유(MySQL 과 동일
  방식이지만 테스트마다 개발 세션이 끊긴다) / (C) 키 접두어 분리(운영 코드에 테스트 개념이 새어든다)
- **고른 것**: (A)
- **근거**: 사람 확인. MySQL 은 개발 스키마를 공유해 테스트가 개발 데이터를 지우지만, Redis 세션이
  지워지면 브라우저에서 매번 다시 로그인해야 해서 비용이 크다. 같은 엔진이라 검증 충실도는 동일하다.
- **영향**: `RedisCleaner` 추가, `IntegrationTestSupport` 가 MySQL·Redis 양쪽을 비운다. E2E 9개
  파일에서 인메모리 `@Primary` 대체를 제거했다. **단위 테스트 6개 파일은 그대로 뒀다** — 단위가
  컨테이너를 요구하면 `testing.md` 의 층 구분이 무너진다(이건 내가 판단했다).

### 4. 호스트 Redis 포트 경합 해소

- **물었던 것**: 호스트 Homebrew Redis(8.8.0)가 6379 를 잡아 컨테이너(7.4.10)에 못 붙는다.
- **선택지**: (A) 컨테이너를 6380 으로 이동 / (B) 호스트 Redis 제거 / (C) 발견만 기록
- **고른 것**: 처음 (A) → 이후 **(B) 로 변경**(호스트 Redis 삭제 후 포트 6379 롤백)
- **근거**: 사람 확인. db0 의 개발 데이터(`riders:geo`)는 불필요하다고 확인받고 함께 삭제.
- **영향**: 포트는 표준 6379 로 돌아왔지만 **근본 원인은 남아 있다** — 누군가 다시 설치하면 반복된다.
  그래서 `RedisCleaner` 의 버전 검사를 남겼고, `docker-compose.yml`·`docs/05-local-dev.md`·
  `CLAUDE.md` 에 "개발 PC 에 Redis 를 직접 설치하지 않는다"를 명시했다.

## 스스로 판단한 것

- **이슈 본문의 지시를 따르지 않은 곳이 있다**(#249). 본문은 "20m 미만도 Redis 를 갱신한다"고 적었는데
  그대로 새 좌표로 덮으면 버그다. 기준선이 함께 전진하므로 **느리게 움직이는 라이더는 영원히 전송
  대상이 되지 않는다** — 1 m/s 로 걷는 라이더가 5초 주기로 5m 움직이는데 기준선도 5m 전진하면 거리는
  영원히 5m 고, 고객 지도의 마커가 얼어붙는다. 그래서 **좌표는 두고 TTL 만 갱신**한다
  (`RiderLocationStore.refreshTtl`). 누적 이동이 20m 를 넘는 순간 전송된다(위 예에서 20초마다).
  대가는 저장된 최신 위치가 실제보다 최대 20m 뒤처지는 것인데 배차 반경이 km 단위라 무의미하다.
  이슈 본문과 코멘트를 정정했다.

- **`isAccepted()` 를 `shouldStore()`/`shouldPublish()` 로 갈랐다.** `DUPLICATE` 만 "저장은 하되 전송
  하지 않는" 값이라 하나로 물을 수 없다. 합치면 전송 기준이면 정지한 라이더의 TTL 이 안 갱신돼 배차
  후보에서 빠지고, 저장 기준이면 같은 좌표가 고객에게 계속 간다.

- **응답 팩토리를 `accept`/`discard` 에서 `of(outcome, published)` 하나로 합쳤다.** 세 번째 상태가
  생기면서 두 팩토리로 표현할 수 없게 됐고, `applied` 를 호출자가 정하게 두면 `applied=false` 인데
  `reason=ACCEPTED` 같은 어긋난 조합이 만들어진다. 저장 여부는 판정값이 이미 알고 있다.

- **하버사인을 썼다.** 이 거리 규모에서는 평면 근사도 충분하지만 위도 의존 오차를 따질 필요가 없고
  알려진 좌표쌍으로 검증하기 쉽다. 날짜변경선을 넘는 좌표가 지구 반대편으로 계산되지 않는지도 테스트로
  덮었다 — 단순 경도 차이로 계산하면 22m 가 4만km 가 된다.

- **`LocationFilter` 를 `location/policy/` 가 아니라 `location/service/` 에 뒀다.** `location` 패키지의
  골격(`controller`·`dto`·`repository`·`service`·`sse`)을 벗어나지 않으려고. `#233` 에서 저장소를
  `store/` 대신 `service/` 에 둔 것과 같은 이유다.

- **`InMemoryRiderLocationStore.clear()` 를 지웠다.** Redis 전환으로 E2E 가 쓰지 않게 되면서 미사용이
  됐고, 단위 테스트는 테스트마다 새로 만든다.

- **`feature/82` 를 `docs/multi-instance-assumption-fix` 위로 리베이스했다.** 세 브랜치가 각자
  `CLAUDE.md` 「확인이 필요한 항목」을 고치고 있어 머지 충돌이 예정돼 있었다. 푸시 전이라 비용이 없었다.

### 검증하지 못한 것

- **`#233` 의 "실제 Redis 왕복" 보고를 정정한다.** 그때 "Redis 컨테이너에 직접 붙여 확인했다"고
  적었는데 사실이 아니었다. 호스트 Homebrew Redis(8.8.0)에 붙어 있었다 — 호스트는
  `127.0.0.1:6379`, 컨테이너는 `*:6379` 에 바인딩하고 **더 구체적인 호스트 쪽이 이긴다.**
  실제 Redis 였으므로 왕복·TTL 600초·값 형식 검증 자체는 유효하지만, `docker-compose` 가 고정한
  버전이 아니었다. H2 로 통과하고 MySQL 에서 깨졌던 것과 같은 종류의 문제다. 지금은 호스트 Redis 를
  제거하고 `RedisCleaner` 가 인스턴스 버전을 확인한다.
- **실제 TTL 만료 동작**(10분 뒤 키가 사라지는 것). 대기 시간 때문에 테스트하지 않았다.
- **다중 인스턴스 동시 갱신 경쟁**. #250 의 주제이고, 인스턴스 2대 환경이 없어 재현하지 못한다.
- **1초 미만 경과의 실제 발생 여부.** 프론트 전송 주기가 최소 5초라 정상 흐름에서는 오지 않는다.
  방어적으로만 다뤘다.

## 새로 생긴 미결 사항

1. **테스트가 실제 TTL 만료를 검증하지 않는다.** 대기 시간 때문이다. 만료에 의존하는 로직
   (운행 종료 후 배차 후보에서 빠지는 것 등)은 여전히 근거가 없다.
2. **CI 가 테스트를 돌리지 않는다**(`deploy.yml` 의 `-x test`). 이제 MySQL·Redis 두 서비스 컨테이너가
   필요해져 CI 도입 비용이 올라갔다. 도입하지 않으면 위 격리 규칙들이 로컬에서만 지켜진다.
3. **`refreshTtl` 도 원자적이지 않다.** `find` → `refreshTtl` 사이에 TTL 이 만료되면 갱신할 값이 없다.
   다음 갱신이 최초 좌표로 저장해 복구되지만, #250 에서 `save` 와 함께 다뤄야 한다.
4. **Redis 대체 저장소가 늘면 E2E 격리 함정이 재발한다.** `DatabaseCleaner` 의 TRUNCATE 가
   AUTO_INCREMENT 를 1로 리셋해 모든 테스트의 첫 회원이 같은 `member_id` 를 받으므로, member id 로 키를
   만드는 저장소는 반드시 오염된다. 지금은 `RedisCleaner` 가 `FLUSHDB` 로 덮지만, Redis 밖의 상태를
   갖는 컴포넌트가 생기면 같은 문제가 다시 생긴다.
