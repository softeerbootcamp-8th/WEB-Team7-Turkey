## 무엇을 만들었나

배정된 BUSY 라이더가 픽업지 이동 시작 행위를 요청하면 주문을 `ASSIGNED`에서
`MOVING_TO_PICKUP`으로 변경하고 시작 시각을 저장한다. 주문 ID·배정 라이더·현재 상태를 조건부
UPDATE에서 함께 검사해 동시 중복 요청은 하나만 성공하도록 했다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/rider/deliveries/{deliveryId}/transition` | 픽업지 이동 시작 | 401 미인증, 403 라이더 불일치/BUSY 아님, 404 주문 없음, 409 상태 불일치·중복 |

### 화면

해당 없음.

### 스키마 변경

해당 없음. 기존 `moving_to_pickup_at` 컬럼을 사용한다.

## 사람이 고른 선택

### 1. 패키지 책임 분리

- **물었던 것**: 라이더 행위이자 주문 상태 전이인 기능을 어느 패키지에 둘 것인가.
- **선택지**:
  - (A) 라이더 패키지에 전부 배치 — 유스케이스는 모이지만 주문 규칙이 라이더 쪽으로 샌다.
  - (B) API·서비스는 라이더, 상태 규칙·저장소는 주문 — 행위 주체와 데이터 소유권을 함께 지킨다.
- **고른 것**: (B)
- **근거**: 라이더가 실행하는 유스케이스지만 상태와 전이 불변식은 주문이 소유한다.
- **영향**: 라이더 서비스가 주문 저장소를 사용하고, 주문 상태를 직접 대입하지 않는다.

### 2. 기존 전체 API 계약 보존

- **물었던 것**: #58만 구현하면서 미구현 조회·완료 계약을 제거할 것인가.
- **선택지**:
  - (A) #58 외 메서드 제거 — 당장 구현체는 단순하지만 후속 기능 계약을 훼손한다.
  - (B) 전체 계약을 유지하고 실제 구현 계약만 분리 — 미구현 라우트를 노출하지 않으면서 설계를 보존한다.
- **고른 것**: (B)
- **근거**: 이미 합의된 배달 완료 등의 계약을 구현 편의 때문에 없애면 안 된다.
- **영향**: `RiderDeliveryApi`는 전체 계약을 유지하고 #58 컨트롤러는 전이 계약만 구현한다.

## 스스로 판단한 것

- **동시 중복 요청 처리**: 이슈의 예외 조건을 우선해 409로 거부했다. 조건부 UPDATE로 동시 요청도 같은 결과를 보장한다.
- **응답 구성**: 전이 후 화면이 추가 조회 없이 갱신할 수 있도록 기존 `RiderDeliveryResponse` 전체를 반환한다.

## 일부러 하지 않은 것

- **고객 상태 변경 알림**: 현재 `member_notification`과 주문 상태 알림 전송 계약이 구현 전이라 제외했다. 후속 이슈에서 알림 채널·형식을 확정해야 한다.
- **픽업 완료·배송 출발·배송 완료 구현**: #58 범위 밖이므로 API 계약만 유지했다.
