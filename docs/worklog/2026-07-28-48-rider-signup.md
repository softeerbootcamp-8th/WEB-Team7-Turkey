## 무엇을 만들었나

`POST /api/rider/signup` — `CustomerSignupService`(#25)와 처리 흐름이 거의 동일하다. 다른 점은
역할이 `RIDER`라는 것과, 회원 저장과 같은 트랜잭션에서 라이더 프로필(`RiderProfile`, 초기 운행
상태 `UNAVAILABLE`)을 함께 생성한다는 것뿐이다.

이 작업은 `#48`~`#50`을 한 브랜치·한 사이클로 묶어 진행했다(사람 확인, 아래 「사람이 고른
선택」 참고). `#51`·`#52`는 라이더 운행 상태 전이(BUSY 거부, AVAILABLE→UNAVAILABLE)라는
실제 새 로직이 있어 별도로 진행한다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| POST | `/api/rider/signup` | 라이더 계정 + 라이더 프로필 생성 | 409(아이디·휴대전화 중복), 400(형식 오류·인증 미완료·필수 약관 미동의) |

### 화면

해당 없음(백엔드만).

### 스키마 변경

해당 없음(`rider_profile` 테이블은 `V2` 마이그레이션으로 이미 존재).

## 사람이 고른 선택

### 1. 48~52를 어떻게 진행할지

- **물었던 것**: `#48`~`#52`가 `#25`~`#29`(고객 회원가입~세션 만료)의 라이더 버전으로 보이는데,
  전부 한 번에 진행할지 물었다.
- **선택지**:
  - (A) 5개 다 한 번에 — 속도는 가장 빠르지만 `#51`/`#52`의 상태 전이 로직(BUSY 거부, 예외 처리
    방식)도 계약 확인 없이 바로 구현하게 됨
  - (B) 48+49+50 한 번에, 51+52 따로 — 회원가입/로그인/세션확인은 #25~27과 거의 동일한 구조라
    바로 구현, 로그아웃/세션만료는 배차 도메인과 엮인 실제 새 로직이 있어 별도 계약 확인
- **고른 것**: (B)
- **근거**: "48+49+50 한 번에, 51+52 따로 (추천)" 선택.
- **영향**: 이 워크로그를 포함해 `#48`/`#49`/`#50`은 한 브랜치(`feature/48-49-50-rider-auth`)·한
  PR로 진행하되, 이슈별로 커밋과 작업 기록은 분리했다.

## 스스로 판단한 것

- **`RiderProfileRepository`를 새로 만듦**: 기존에 `RiderProfile` 엔티티는 있었지만(다른
  이슈에서 이미 구현됨) 리포지터리가 없었다. `JpaRepository<RiderProfile, Long>` 형태로 최소
  구현했다(공유 PK라 `memberId`가 곧 PK).
- **비밀번호 규칙 없음(고객과 동일 결정 재사용)**: `#25` 계약 확인에서 "비밀번호 규칙도 필요
  없다"고 결정된 걸 그대로 따랐다 — 이슈 본문 문구("비밀번호 규칙 검증")는 고객 가입 이슈와
  동일한 표현이라, 같은 결정이 적용된다고 판단했다. 재차 묻지 않았다.
- **가입 실패 응답 코드·순서(중복 확인 → 약관 검증 → 인증 토큰 소비 → 저장)를 고객과 동일하게
  유지**: `#25`에서 코드 리뷰로 다듬어진 순서(약관 검증을 토큰 소비보다 먼저 해서, 약관만
  고쳐 재시도할 때 토큰이 낭비되지 않게 함)를 그대로 재사용했다.

## 일부러 하지 않은 것

- **라이더 전용 추가 입력값**: 이슈 입력값이 고객 가입과 동일(로그인 ID·비밀번호·이름·휴대전화·
  인증·약관)해서 라이더 전용 필드(예: 차량 정보)는 없다 — ERD/이슈 어디에도 없다.
