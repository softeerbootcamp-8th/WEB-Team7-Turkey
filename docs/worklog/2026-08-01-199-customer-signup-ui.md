## 무엇을 만들었나

정적 고객 회원가입 폼을 제어 컴포넌트로 전환하고 아이디 중복 확인, 휴대전화 인증번호 발송·확인,
고객 회원가입 API를 연결했다. 입력 변경에 따라 이전 중복 확인과 휴대전화 인증 결과를 무효화하며,
필드 오류·서버 오류·네트워크 오류·요청 중 중복 제출 방지를 화면에 표시한다.

### API

| 메서드 | 경로 | 설명 | 주요 실패 응답 |
|---|---|---|---|
| GET | `/api/login-ids/availability` | 로그인 ID 사용 가능 여부 확인 | 400 입력 오류 |
| POST | `/api/phone-verifications` | 가입용 휴대전화 인증번호 발송 | 409 가입 번호, 429 재전송 제한, 502 발송 실패 |
| POST | `/api/phone-verifications/confirm` | 인증번호 확인 및 일회성 토큰 발급 | 400 불일치, 404 만료·이력 없음, 429 시도 초과 |
| POST | `/api/customer/signup` | 인증 토큰을 포함한 고객 회원가입 | 400 입력·인증·약관 오류, 409 아이디·전화번호 중복 |

### 화면

`/customer/signup`에서 생성된 Orval 훅을 소비한다. 아이디가 바뀌면 중복 확인 결과를 제거하고,
휴대전화 번호가 바뀌면 발급된 인증 완료 토큰을 제거한다. 가입 성공 시 `/customer/login`으로 이동한다.

### 스키마 변경

해당 없음.

## 사람이 고른 선택

### 1. 휴대전화 인증 화면 구성

- **물었던 것**: 인증 완료 토큰을 별도 `auth/verify` 화면에서 검색 파라미터로 전달할지 React Query 캐시로 전달할지.
- **선택지**:
  - (A) 별도 인증 화면 + 메모리 캐시 — 토큰이 URL에 노출되지 않음 / 폼 상태 보존과 화면 왕복이 필요함
  - (B) 회원가입 폼 안에서 인증 — 별도 전달 상태가 필요 없음 / 회원가입 화면의 책임이 커짐
- **고른 것**: (B)
- **근거**: 사용자 확인 — "폰 인증하는데 별도의 페이지에서 한다는 거야? 그냥 회원가입 폼에 이미 폰 번호 입력하는 칸이 있는데?"
- **영향**: 전화번호 입력 아래에 인증번호 입력·확인 영역이 펼쳐지며 `auth/verify`는 수정하지 않았다.

## 스스로 판단한 것

- **비밀번호 규칙**: #25에서 비밀번호 형식 규칙을 두지 않기로 이미 결정했으므로 필수값과 확인 일치만 검사했다. 정적 화면의 “영문·숫자·특수문자 조합” 문구도 실제 계약과 맞게 제거했다.
- **서버 중복 응답 우선**: 사전 중복 확인을 통과했어도 가입 요청이 409를 반환하면 확인 상태를 무효화하고 서버 메시지를 해당 필드에 표시한다.
- **인증번호 재시작**: 확인 API의 404·429는 기존 코드로 계속 진행할 수 없으므로 인증 상태를 초기화하고 재발송을 안내한다.
- **local 인증번호 표시**: local 프로파일 응답의 `debugCode`가 있을 때만 화면에 표시하고, 운영 응답에서는 영역 자체가 나타나지 않는다.

## 일부러 하지 않은 것

- **약관 목록·동의 연결**: #72가 아직 열려 있어 약관 ID를 알 수 없으므로 요청에는 빈 `agreedTermIds`를 전달한다. 활성 필수 약관이 등록된 환경에서는 서버가 가입을 거부할 수 있다. — 후속: #72
- **별도 `auth/verify` 화면 구현**: 사용자 선택에 따라 회원가입 폼 내부 인증으로 대체했다.
- **역할 공용 세션 구조 수정**: #288의 범위이며 이 회원가입 화면에서는 세션 조회를 추가하지 않았다. — 후속: #288
