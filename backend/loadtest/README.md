# 부하 테스트

시나리오 스크립트와 실측 결과. 실행 방법은 각 스크립트 상단 주석과 `../docker-compose.yml` 의
`k6` 서비스 주석에 있다.

## 디렉터리 구분 (2026-08-11 결정)

**대상이 로컬인지 배포인지에 따라 디렉터리가 갈린다.** 같은 명령처럼 보이면 실수로 팀 공용
환경을 때리기 때문이다.

| 위치 | 대상 | 내용 |
|---|---|---|
| `local/` | 로컬 docker 앱 | 시나리오(`rider-location-update.js`, `rider-call-list.js`) + API 경유 시드 `seed.js` |
| `remote/` | **배포 서버** | SQL 직접 시드 `ec2-seed.sh` + 매니페스트 로그인 `ec2-login.js`. 가드는 `remote/README.md` |
| 최상위 | 공용 | `collect.py`(지표 수집), arm 스크립트(`polling-arm.js`·`sse-arm.js`), `cleanup-seed.sql` |

- **대상 전환은 `BASE_URL`**, **시딩 방식 전환은 `RUN_ID`** 다(`RUN_ID` 가 있으면 arm 이 매니페스트
  기반 `loginPairs()`, 없으면 API 시딩 `seedPairs()`).
- `seed.js` 가 `local/` 인 이유: 회원가입 API의 `debugCode` 가 **local 프로파일에서만** 채워져
  배포에서는 쓸 수 없다.

arm 스크립트를 대상별로 복사하지 않는 이유는, 두 벌이 되면 한쪽만 고쳐져 **로컬·배포 수치를
직접 비교할 수 없게** 되기 때문이다. 대상 전환은 `BASE_URL` 하나로 한다.

측정은 **앱을 컨테이너로 띄우고**(`--profile app`) k6·앱·MySQL·Redis 를 같은 docker 네트워크에
두고 한다. 앱 컨테이너는 배포 EC2 와 같은 **1GiB / 2 vCPU** 로 묶여 있다.

> 앱 코드를 바꿨거나 브랜치를 옮겼으면 **이미지를 반드시 다시 빌드한다**(`build app`).
> 낡은 이미지로 재면 조용히 다른 코드를 측정한다.

```bash
# 1) 관측 스택(Prometheus + Grafana + exporter). 세 번째 파일이 exporter 를 부하 대상으로 돌린다 —
#    빼면 MySQL·Redis 수치가 무관한 빈 컨테이너 값으로 채워진다.
cd infra/monitoring-ec2
docker compose -f docker-compose.yml -f docker-compose.local.yml -f docker-compose.loadtest.yml up -d
# 스크레이프 대상 6개가 전부 up 인지 본다(`/-/ready` 는 200 이면서 대상이 0개일 수 있다).
curl -s 'localhost:9099/api/v1/targets?state=any' | python3 -c "import sys,json; \
t=json.load(sys.stdin)['data']['activeTargets']; \
print(f'타깃 {len(t)}개,', [x['labels']['job'] for x in t if x['health']!='up'] or '전부 up')"

# 2) 부하 대상 + 시드
cd ../../backend
docker compose --profile app up -d --build --wait   # healthcheck 로 기동 완료까지 블록
./loadtest/sample-stats.sh &                        # 컨테이너 CPU 병행 샘플링(Prometheus 에 없는 값)
docker compose exec -T mysql mysql -uturkey -plocal turkey < scripts/reset-and-seed-local.sql
# BUSY 라이더 100명(+고객 100명, 진행 중 배송 100건). VU 수보다 많게 잡는다.
docker compose exec -T mysql mysql -uturkey -plocal turkey < scripts/seed-loadtest-riders.sql

# 3) 실행 → 리포트. testid 를 빼먹으면 Grafana 대시보드와 collect.py 가 런을 구분하지 못한다.
ID=location-$(date +%Y%m%d-%H%M%S)
docker compose run --rm -e BASE_URL=http://app:8080 -e RIDER_COUNT=100 \
  k6 run --tag testid=$ID /scripts/local/rider-location-update.js
./loadtest/collect.py --latest --steps > ../docs/loadtest/$(date +%F)-${ID}.md
```

Grafana 는 `https://localhost:8443`(자체서명, 최초 1회 "고급 > 계속 진행") 의 **k6 Prometheus**
대시보드에서 `testid` 를 골라 본다. 런 단위 p95/p99 는 k6 가 종료할 때 터미널에 찍는 summary 가
정본이다 — 퍼센타일은 구간별로 나뉘어 저장되므로 시간축으로 평균낼 수 없다.

`RIDER_COUNT` 를 생략하면 기본 시드의 BUSY 라이더 3명만 쓴다 — 계정을 공유하면 같은 행·같은
Redis 키만 두드려 수치가 왜곡된다(아래 A vs B 비교). 계정 수는 `seed-loadtest-riders.sql` 의
`SET @n` 으로 바꾼다.

> 호스트에서 `bootRun` 으로 재면 안 된다. 개발 PC 자원을 다 쓰는 데다, macOS·Windows 에서는
> 앱↔DB 트래픽이 Docker VM 경계를 넘어 지연이 붙는다. 실제로 그 구성에서 나온 첫 측정은
> 커넥션 풀 대기가 부풀려져 병목을 잘못 짚었다(아래 「측정 이력」).

## local/rider-location-update.js — 라이더 위치 갱신

`POST /api/rider/location`. BUSY 라이더가 5초마다 때리는 유일한 상시 쓰기 경로다.

부하: VU 10 → 30 → 60 로 90초 램프(유지 구간 없음), think time 0. 계정은 VU 보다 많게 잡아
VU 당 라이더 1명이 배분되게 한다.

`STEPS=n` 을 주면 **계단 램프**가 된다(`MAX_VU/n` 간격 n 단, 각 단 전이 `RAMP_SECONDS`(10초) +
유지 `HOLD_SECONDS`(90초)). 유지 구간이 있어야 **어느 동시성에서 병목의 성격이 바뀌는지**를 볼 수
있다 — 유지 90초는 Prometheus 15초 스크레이프가 `increase()` 창을 채우는 최소값이다. 단계별 표는
`collect.py --steps` 가 VU 타임라인에서 유지 구간을 찾아 자동으로 만든다(단 경계를 따로 넘기지 않는다). `STEPS` 를 주지 않으면 기존 4단 램프 그대로라 이전 런과 비교가 유지된다.

### 결과 (2026-08-10, dev `affb49d` + 이 브랜치, 앱 컨테이너 1GiB/2vCPU)

**dev 는 가상 스레드가 켜져 있다**(`spring.threads.virtual.enabled`). 아래 A 가 정본이고,
B 는 가상 스레드가 없던 브랜치에서 잰 같은 조건이다 — 이 항목 하나로 수치가 크게 갈린다.

| **p95 / p99** | **18.3 / 27.9 ms** | 48.8 / 61.6 |
| 서버측 평균(Micrometer) | 5.83 ms | 4.80 ms |
| 실패 | 0건 | 0건 |
| 앱 CPU | **100% (2코어 만석)** | 100% |
| Hikari 활성 / 대기 최대 | 10/10 · 43 | 10/10 · 36 |
| **JVM 플랫폼 스레드 최대** | **36** | (Tomcat busy 59) |
| Tomcat 현재 연결 최대 | 57 (= VU 수) | — |
| GC | SerialGC 1,513회 · 정지 4.19초 | SerialGC · 정지 4.28초 |
| 힙 사용 / 상한 | 150 / 247 MiB | 90 / 247 MiB |
| MySQL 문장 / Redis 커맨드 (요청당) | **13.00 / 5.00** | 13.00 / 4.99 |

- **가상 스레드가 지연을 2.7배 줄였다**(p95 48.8 → 18.3ms). 처리량은 거의 같다(둘 다 CPU 100%).
  즉 같은 처리량을 **훨씬 낮은 지연으로** 낸다.
- **플랫폼 스레드가 36개뿐이다.** 60 VU 든 500 VU 든 36 으로 같다(아래 B′ 참고) — 요청당 스레드를
  잡지 않는다는 것이 그대로 관측된다. 이전에는 요청 수만큼 Tomcat 워커가 붙었다.
- **요청당 왕복 수는 스레드 모델과 무관하게 동일하다**(MySQL 13.00 / Redis 5.00). 계정 100개에서
  Redis 가 이론값 5.00 에 정확히 붙어 `saveIfNewer` 경쟁이 없음이 다시 확인됐다.

### 결론

- **처리량을 제한하는 것은 CPU 다.** 2 vCPU 가 100% 로 붙는다. 가상 스레드는 지연을 줄여 주지만
  CPU 한도를 넘겨 주지는 않는다 — 이 API 는 스케일 아웃(인스턴스 추가)이 그대로 먹힌다.
- **포화점은 약 28 VU 다.** 15초 해상도 처리량이 VU 28 에서 피크(4,632 rps)를 찍고 57 VU 에서
  4,151 로 완만히 떨어진다. 플랫폼 스레드 때는 무릎이 **12 VU** 였으니, 가상 스레드가 무릎을
  뒤로 밀고 이후 열화도 완만하게 만들었다.
- **직렬화 지점은 Hikari 풀(10)이다.** 스레드가 더는 병목이 아니게 되면서 대기가 그대로 드러난다
  (60 VU 43건 → 500 VU 397건). 다만 CPU 가 이미 100% 라 **풀만 키워서 처리량이 늘어난다고
  단정할 수 없다** — 확인하려면 `maximum-pool-size` 를 바꿔 다시 재야 한다.
- **1GiB 에서는 JVM 이 G1 대신 SerialGC 를 고른다**(힙 247MiB). GC 정지가 90초 중 4.19초,
  벽시계의 4.7% 다. 사이징을 올리기 전에 이 항목을 먼저 보는 게 좋다.
- **그래도 지금 고칠 이유는 없다.** 실제 부하는 배송 1건당 0.2 req/s(5초 주기)라 3,839 req/s 는
  동시 진행 배송 약 19,000건에 해당한다. MVP 규모와 자릿수가 다르다.

### 결과 (2026-08-11, 계단 램프 VU 100→1000, testid `location-stair-20260811-204322`)

원본 수치·단계별 표는 `docs/loadtest/2026-08-11-location-stair-20260811-204322.md`.

> **이 런은 위 A/B 와 직접 비교할 수 없다.** MySQL·Redis 컨테이너에 **각 2 CPU / 1 GiB 제한이
> 새로 걸린** 상태에서 쟀다(A/B 는 DB·Redis 무제한). 앱은 양쪽 모두 1GiB/2vCPU + 가상 스레드.

| VU | 100 | 300 | 600 | 700 | 800 | 900 | 1000 |
|---|---|---|---|---|---|---|---|
| 처리량 | 4,402 | 4,269 | 3,842 | 3,644 | 3,370 | 2,777 | **1,973 req/s** |
| p95(구간) | 43.7 | 100.0 | 201.6 | 246.9 | 293.1 | 354.2 | 435.8 ms |
| **앱 CPU** | **203%** | **203%** | 200% | 196% | 190% | 178% | **168%** |
| **GC 정지 비율** | 4.7% | 8.7% | 17.5% | 22.1% | 29.1% | 39.2% | **51.3%** |
| Hikari 활성 / 대기 | 10 / 87 | 10 / 286 | 10 / 584 | 10 / 689 | 10 / 790 | 10 / 890 | 10 / **988** |
| MySQL 문장 / Redis 커맨드 (요청당) | 12.98 / 4.99 | 12.98 / 4.99 | 13.06 / 5.02 | 13.00 / 5.00 | 13.00 / 5.00 | 12.93 / 4.98 | 13.04 / 5.02 |

실패 **0건**(370만 요청) · 5xx 0건 · 드롭 0건. 런 단위 p95/p99 = **441.3 / 742.4 ms**, max 2.65s.

**병목은 체제가 둘이다.**

1. **처리량이 한 번도 늘지 않는다**(4,402 → 1,973 단조 감소). 100 VU 에서 이미 앱 CPU 가 203%
   (2코어 만석)라 **무릎은 100 VU 아래**다(A 의 28 VU 추정과 방향 일치). 이 계단은 무릎 측정이
   아니라 **포화 이후 열화 곡선**이다.
2. **100~600 VU: 앱 CPU 가 천장.** 300 VU 고정 프로브의 컨테이너별 CPU — 앱 **203%/200%(만석)**,
   MySQL 142%(71%), Redis 12%(6%), k6 48%. 앱만 제한을 채운다.
3. **700 VU 이상: SerialGC 가 CPU 를 빼앗는다.** 앱 CPU 가 **떨어지는데**(203→168%) 처리량도 같이
   무너진다 — 자원이 남는데 못 쓴다. GC 정지가 90초 중 19.9 → 46.2초(51%)로 폭발하고, **횟수는
   줄면서**(941→532) **1회 정지가 21 → 87ms 로 4배** 길어진다. 1GiB 라 SerialGC(단일 스레드)라서
   정지 중 코어 1개만 도는 것이 168% 라는 값과 산술로 맞는다. 대기 요청이 각자 객체를 붙잡아
   **살아 있는 객체가 동시성에 비례**하고, 힙은 191~239 MiB / 상한 248 MiB 로 상시 거의 꽉 차 있다.
4. **리틀의 법칙이 정확히 성립한다** — `처리량 × 서버측 평균`이 VU 수와 일치(100 VU→97.5,
   500→496.9, 1000→993.4). 늘어난 지연은 **전부 큐 대기**이고 처리 능력은 고정이다.
5. **Hikari 대기(988)는 원인이 아니라 결과다.** 활성은 전 구간 10(풀 상한), 대기는 `VU−11` 로 정확히
   따라온다. 그 앞에서 앱 CPU 가 이미 100% 라 **풀을 키워도 돌릴 CPU 가 없다.** 같은 오독으로
   과거에 결론을 냈다 철회한 적이 있어(아래 「측정 이력」) **여기서도 단정하지 않는다** —
   확증에는 `maximum-pool-size` 를 바꾼 재측정이 필요하다. 남은 유일한 열린 항목.
6. **요청당 왕복 수는 전 단계에서 불변**(MySQL 13.0 / Redis 5.0). 부하가 10배가 돼도 요청당 일의
   양이 그대로 — 락 경쟁·재시도·N+1 폭발이 없다. 계정 1:1 이라 `saveIfNewer` 경쟁도 없다.

**개선 순서**(앞의 둘은 이 API 전용이 아니라 모든 라이더 API 공통):
① GC — 1GiB→2GiB 로 G1 이 선택되게 하거나 `-XX:+UseG1GC` 명시. 사이징을 올리기 전에 먼저 볼 항목.
② 요청당 MySQL 13회 중 **10회가 트랜잭션 부대비용**(SET 8 + COMMIT 2) — 인터셉터 조회 합치기,
커넥션 속성으로 SET 왕복 줄이기.
③ 스케일 아웃이 그대로 먹힌다(MySQL 71%·Redis 6%). 단 **MySQL 이 다음 천장**이다 — 71% × 2대면 초과.

**실사용 환산(#391 미결 항목의 답).** 지속 처리량 약 4,400 req/s. BUSY 전송은 최소 0.5초 간격이라
라이더당 최악 2 req/s → 동시 BUSY 라이더 **약 2,200명**(5초 주기 상당인 0.2 req/s 면 22,000명).
단일 인스턴스 기준으로 MVP 규모와 자릿수가 다르다.

### VU 를 어디까지 둘 수 있나

상한이 네 겹이고, **먼저 걸리는 것은 기술적 한계가 아니라 "의미"** 다.

| 상한 | 값 | 근거 |
|---|---|---|
| **의미 있는 상한** | **약 28 VU(포화), 관찰용으로 60** | 28 VU 에서 처리량 피크. 그 위는 처리량이 안 늘고 지연만 커진다 |
| 계정 수 | `RIDER_COUNT` | VU > 계정 수면 라이더를 공유해 수치가 왜곡된다(스크립트가 경고를 찍는다). 시드는 재귀 CTE 기본 상한 1000 까지 |
| 앱 하드 상한 | **동시 연결 8192**(`tomcat_connections_config_max_connections`) | 가상 스레드라 스레드 풀 상한이 없다. 500 VU 에서 연결 500 개가 그대로 붙었다 |
| 부하 생성기 | 수천 VU (11코어/18GiB) | k6 는 VU 당 1~5MiB. 앱과 같은 머신이지만 **1000 VU 에서도 k6 CPU 는 48%**(2026-08-11 계단 런 실측)라 이 범위에서는 측정을 흐리지 않는다 |

**1000 VU 까지 실측했다**(계단 램프, 위 절): 실패 0 · 5xx 0 · 드롭 0, Tomcat 연결이 VU 와 1:1 로
1,001 까지 붙는다. 다만 **700 VU 이상은 SerialGC 가 지배**해 처리량이 무너지므로(1,973 rps),
관찰 가치가 있는 상한은 **600 VU** 다.

| **Hikari 대기** | 43 | **397** |
| GC 정지(90초 중) | 4.19초 | 7.85초 |
| 앱 컨테이너 메모리 | — | **677 MiB / 1 GiB** |

- **`tomcat_threads_*` 는 가상 스레드에서 전부 `-1` 이다.** 스레드 풀이 없어 보고할 값이 없다.
  따라서 **"Tomcat 스레드 200 이 앱의 하드 상한"이라는 이전 결론은 dev 에서 성립하지 않는다.**
  동시성은 `tomcat_connections_current_connections`(VU 수와 1:1) 로 본다.
- **500 VU 에서도 에러가 0 이다.** 과부하는 실패가 아니라 **지연으로 나타난다**(p99 216ms).
  이 구간의 사용자 경험은 프론트 타임아웃 설정이 좌우한다.
- 스레드가 늘지 않으니(36 고정) 메모리도 거의 그대로다(677MiB/1GiB). 대신 **대기가 Hikari 로
  모인다**(397건) — 플랫폼 스레드 때 200개 스레드가 하던 "자연 유량 제한"이 없어졌기 때문이다.
- 권장: 포화점 탐색은 `MAX_VU=60`(기본), 한계·안정성 확인은 `MAX_VU=500`.
  더 큰 부하를 의미 있게 재려면 **부하 생성기를 별도 머신으로** 빼야 한다.

### 실측: 요청 1건당 비용

문서(CLAUDE.md)에는 "MySQL 3회 + Redis 3회"로 적혀 있었다. 실제 왕복은 더 많다.
아래는 단일 라이더 200건 기준이고, 계정 100개 부하 측정에서도 MySQL 13.00 / Redis 5.00 으로 같았다.
가상 스레드 여부와 무관하게 동일하다(스레드 모델이 아니라 코드 경로가 정하는 값이다).

| MySQL 문장 | 회/요청 | 정체 |
|---|---|---|
| SELECT | 3.00 | 문서의 3회(인터셉터의 member·rider_profile + 수행 중 배송) |
| COMMIT | 2.00 | 트랜잭션이 요청당 2개 |
| SET | 8.00 | 트랜잭션마다 autocommit·read-only 세션 설정/복구 |
| **합계(Questions)** | **13.03** | |

**13번의 왕복 중 10번이 트랜잭션 부대비용**이다. 줄이는 방향은 ① 인터셉터의 회원·프로필 조회를
한 쿼리로 합치기, ② MySQL 커넥션 속성(`useLocalSessionState` 등)으로 SET 왕복 줄이기 —
둘 다 이 경로 전용이 아니라 **모든 라이더 API 공통**이다.

| Redis 커맨드 | 회/요청 | 정체 |
|---|---|---|
| HGET | 1.00 | 세션 조회 |
| EVALSHA | 1.00 | 최신 위치 조건부 갱신(Lua) |
| GET + SET | 2.00 | 위 Lua 내부(Redis 는 Lua 내부 커맨드도 센다) |
| PUBLISH | 1.00 | SSE 팬아웃 채널 발행 |
| **합계** | **5.00** | |

### 부산물

- **조건부 갱신(`saveIfNewer`) 경쟁은 계정 공유가 만든 것이었다.** 계정 3개일 때 Redis 커맨드가
  4.32/요청(이론값 5.00)이어서 "절반이 폐기된다"고 읽었는데, 계정 100개로 늘리자 4.99 가 되어
  경쟁이 사라졌다. 라이더 1명당 기기 1대인 실제 운행에서는 이 경쟁이 사실상 없다고 봐도 된다
  (CLAUDE.md 미결 항목에 대한 답). 다만 같은 라이더가 기기를 두 대로 보내는 상황이 생기면
  **폐기가 아무 신호도 남기지 않는다**는 점은 그대로다.
- **알림 규칙이 실제 지표에 반응했다.** 첫 측정에서 `HikariPoolPending` 이 pending 까지 갔다
  (테스트 90초 < 규칙의 `for: 2m` 이라 firing 전에 종료).

### 측정 이력(위치 갱신)

1. **첫 측정** — 앱을 호스트 `bootRun`, 계정 3개: 2,287 req/s · Hikari 대기 36. 이걸 보고
   "커넥션 풀이 병목"이라고 결론지었다.
2. **앱을 컨테이너로**(B) — 대기가 36 → 5 로 떨어졌다. 첫 측정의 대기는 앱↔DB 가 Docker VM
   경계를 넘느라 커넥션을 오래 잡은 탓이 컸다.
3. **계정 100개로**(A) — 대기가 다시 36 이 됐다. 이번엔 원인이 다르다(라이더마다 다른 행을 읽어
   버퍼풀 지역성이 떨어짐). 우연히 같은 숫자가 나왔을 뿐이다.

4. **dev(가상 스레드) 기준으로 재측정** — dev 는 `spring.threads.virtual.enabled` 가 켜져 있는데
   앞의 셋은 그 설정이 없는 브랜치에서 쟀다. 다시 재니 p95 가 48.8 → 18.3ms 로 줄고, 무릎이
   12 → 28 VU 로 밀렸다. **`tomcat_threads_*` 가 -1 이 되어 "스레드 200 이 하드 상한"이라는
   결론은 폐기했다.**

5. **계단 램프 100→1000 VU**(위 절) — 1000 VU 까지 실패 0 이고, **700 VU 부터 병목이 CPU 에서
   SerialGC 로 넘어간다**는 새 사실이 나왔다. 앞의 네 측정이 60~500 VU 라 이 전환을 못 봤다.
   단, **DB·Redis 에 자원 제한이 새로 걸린 상태**라 A/B 와 같은 축에 놓을 수 없다.

6. **측정 중 사람이 스택을 건드려 런 하나를 버렸다**(`location-stair-20260811-201929`, VU 400 이후
   무효). 같은 로컬 스택에서 컨테이너 재시작 2건 + 별도 60 VU 부하가 겹쳤다. **로컬 스택도
   1인 전용이 아니다** — `remote/` 에만 공용 가드를 적어 둔 것이 공백이었다. **실행 전에
   활성 런을 확인한다**: `curl -s --get 'localhost:9099/api/v1/query' --data-urlencode
   'query=sum(k6_vus)'` 가 0 이 아니면 시작하지 않는다. 사후 유효성 게이트로는 앱·MySQL
   `uptime` 단조증가(재시작 없음)와 `sum(k6_vus)` == 자기 testid 의 VU(외부 부하 없음)를 본다.
   부수적으로, **k6 출력을 grep 으로 걸러 실행하면 `k6-report.py` 훅이 조용히 빠진다**
   (`running (...)` 줄에서 측정 구간을 역산하기 때문). 백그라운드 실행도 마찬가지다.

**"커넥션 풀이 병목"이라는 첫 결론은 철회한다.** 네 측정 모두에서 처리량을 정한 것은 CPU 였다
(제약 있는 런은 전부 CPU 100%, 한도 없는 런은 CPU 37% 에서 처리량 2배). 요청당 왕복 수
(MySQL 13.00 / Redis 5.00)는 네 구성에서 모두 같았다.

## local/mixed-realistic.js — 실사용 근사 혼합 부하 (#502 힙·GC·Hikari 튜닝)

원본·상세 근거는 `docs/loadtest/2026-08-14-502-heap-gc-hikari-tuning-final-report.md`(콜드
스타트 방법론 전환점, Hikari 10 vs 30, G1 vs SerialGC 결론)와
`docs/loadtest/2026-08-15-mixed-callorder-fullscale-20260815-163946.md`(AVAILABLE 700명 3초
새로고침 + 주문 생성 300건 + COMPLETED 이력 1만 건 확장). 여기는 누적 결론만 적는다.

- **`-Xms=-Xmx=512m` + G1GC를 배포(`deploy.yml` systemd override)에도 반영**했다(2026-08-15,
  기존 228m ergonomic 기본값에서 상향). 로컬 `docker-compose.yml`의 `JAVA_HEAP_OPTS` 기본값도
  같은 값으로 맞췄다 — 배포와 로컬이 이제 같은 힙 설정으로 시작한다.
  t4g.micro(906MiB) 스와핑 여유가 줄어든 채로 배포되므로 배포 후 메모리 지표를 지켜볼 것
  (「알려진 결함」이 아니라 관찰 필요 항목).
- 이 값은 700 VU 콜 목록(3초 간격) + 동시 주문 생성 300건 + `delivery_order` 15,000행 규모
  에서도 힙 사용 최대 403MiB(상한의 79%), GC 정지 비율 0.1%로 전혀 압박받지 않았다 — 단
  이 시나리오는 `#502` 최종 리포트의 무거운 시나리오(VU 2,100, 닫힌 루프 콜 목록 + 상태
  전이)보다 훨씬 가벼워 **512m가 버티는 새 증거는 아니고, 부작용이 없다는 재확인**이다.
- `mixed-realistic.js`가 `CUSTOMER_ORDER_COUNT`(주문 생성, 계정당 1회) ·
  `AVAILABLE_POLL_INTERVAL_SEC`(콜 목록 재요청 간격, 기본 0=닫힌 모델) 파라미터로 확장됐다.
  `seed-loadtest-mixed.sql`은 `lt_oc*`(주문 생성 고객) 및 `@completed_history_extra`(고정
  이력 건수, ratio 계산과 무관하게 추가)를 지원한다.
- **미규명 결함(영향 미미)**: 주문 생성 300건 중 1건이 `uk_delivery_active_customer` 위반으로
  실패했다 — 서버 동시성 제어는 정확히 의도대로 거부했으나, k6 VU 인덱스 매핑이 왜 같은
  세션을 두 번 골랐는지는 못 밝혔다(위 2026-08-15 리포트 참고). 43,600건 중 1건이라 이번
  튜닝 결론에는 영향 없음.

## local/order-create-cancel.js — 배송요청 생성 포화(생성→취소 사이클)

`POST /api/customer/deliveries`는 상태 소진형(고객당 진행 중 1건)이라, 매 iteration 에서 생성 직후
취소해 슬롯을 비우는 **닫힌 모델 생성→취소 사이클**로 쓰기 경로 포화를 본다(`mixed-realistic.js`의
"계정당 1회 생성"과 다른 질문 — 이쪽은 write 경로 스트레스, 저쪽은 실사용 혼합). 정본 수치는
`docs/loadtest/2026-08-17-order-create-warm2-20260817-212122.md`(웜·512m·25~200 VU 8단, 유실 없음).
선행 런은 `2026-08-14-...`(콜드+228m)와 `2026-08-17-...-043544`(웜이나 OOM 유실, warm2 가 대체).

- **처리량 천장 ~1,000~1,100 req/s(≈510 사이클/s), 무릎은 Hikari 풀 크기 부근(~10~15 VU).**
  25 VU 에서 982 req/s, 200 VU 에서 1,012 req/s 로 **처리량은 25 VU 부터 평탄**하고 그 위 VU 는 전부
  지연(p95 41→253ms)·Hikari 대기(15→190)만 선형으로 키운다. **Hikari 활성은 25 VU 부터 10 고정**
  (풀 만석)이라 무릎이 풀 크기와 맞물린다.
- **병목은 HikariCP 풀(10)이고 CPU 가 아니다**(warm2 확정). 앱 CPU 최대 165%·MySQL 평균 123%로
  2코어 cap(200%)에 여유가 있다 — CPU 는 더 일할 수 있는데 커넥션 10개가 동시 처리량을 묶는다.
  **따라서 이 워크로드에선 풀을 키우면 처리량이 실제로 늘 여지가 크다.** 이는 콜드 런(앱 CPU 219%
  cap)에서 "풀 확대 무의미"라던 판정과 정반대다 — 풀 크기 비교 실험이 다음 후보이며, 반드시 **웜
  상태에서**(스킬 원칙 3) 비교할 것.
- **콜드 JVM 아티팩트 확정**(#502 원칙). 콜드+228m 로 40→200 VU 재니 40 VU 부터 포화로 보였다
  (앱 CPU 219% cap, p95 502ms, max 31.2s, `uk_delivery_active_customer` 409 1,330건, Hikari 30s
  타임아웃 14건). 웜+512m 로 재니 200 VU 까지 p95 254ms·max 1.95s·실패 0%·409 0건. 그 "40 VU 무릎"과
  409 캐스케이드는 **콜드 JVM + 작은 힙 아티팩트**였다.
- **409 캐스케이드는 시나리오 취약점**(서버 버그 아님): cancel 이 타임아웃하면 그 계정이 슬롯을 못
  비워 남은 런 내내 409 를 쏟는다(콜드 런에서 3계정이 1,330건 전부). 개선안: create 가 409 면 기존
  active 주문을 먼저 취소하고 재시도. 웜 런에서는 타임아웃이 없어 409 가 0 이었다.
- **MySQL 데드락(warm2 419k create 중 6건, 0.0005%)**: `insert into delivery_order` 가 갭락/포인트
  잠금 교차로 데드락→5xx. 빈도는 무시 가능하나 생성 실패 재시도 정책과 함께 볼 것.
- **측정 이력 — Prometheus OOM 은 VU 가 아니라 `name` 태그 누락이 원인이었다.** cancel URL 의
  `deliveryId` 가 k6 name 라벨로 들어가 매 요청이 새 시계열을 만들어(실측 69,234 종) prometheus 가
  수백만 시리즈로 OOM 났다(200·120 VU 두 런). **cancel 에 상수 `name` 태그**를 달아 카디널리티를 1 로
  묶으니 200 VU 전 범위가 prometheus 111 MiB·k6 컨테이너 389 MiB(수정 전 1.8 GB)로 유실 없이 완주했다.
  path param 이 있는 요청은 반드시 `name` 태그로 묶을 것(고정 URL 인 위치 갱신·create 는 무관).
