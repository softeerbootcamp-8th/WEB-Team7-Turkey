# 부하 테스트

시나리오 스크립트와 실측 결과. 실행 방법은 각 스크립트 상단 주석과 `../docker-compose.yml` 의
`k6` 서비스 주석에 있다.

측정은 **앱을 컨테이너로 띄우고**(`--profile app`) k6·앱·MySQL·Redis 를 같은 docker 네트워크에
두고 한다. 앱 컨테이너는 배포 EC2 와 같은 **1GiB / 2 vCPU** 로 묶여 있다.

```bash
cd backend
docker compose --profile app up -d --build
docker compose exec -T mysql mysql -uturkey -plocal turkey < scripts/reset-and-seed-local.sql
# BUSY 라이더 100명(+고객 100명, 진행 중 배송 100건). VU 수보다 많게 잡는다.
docker compose exec -T mysql mysql -uturkey -plocal turkey < scripts/seed-loadtest-riders.sql
docker compose --profile loadtest run --rm -e BASE_URL=http://app:8080 -e RIDER_COUNT=100 \
  k6 run /scripts/rider-location-update.js
```

`RIDER_COUNT` 를 생략하면 기본 시드의 BUSY 라이더 3명만 쓴다 — 계정을 공유하면 같은 행·같은
Redis 키만 두드려 수치가 왜곡된다(아래 A vs B 비교). 계정 수는 `seed-loadtest-riders.sql` 의
`SET @n` 으로 바꾼다.

> 호스트에서 `bootRun` 으로 재면 안 된다. 개발 PC 자원을 다 쓰는 데다, macOS·Windows 에서는
> 앱↔DB 트래픽이 Docker VM 경계를 넘어 지연이 붙는다. 실제로 그 구성에서 나온 첫 측정은
> 커넥션 풀 대기가 부풀려져 병목을 잘못 짚었다(아래 「측정 이력」).

## rider-location-update.js — 라이더 위치 갱신

`POST /api/rider/location`. BUSY 라이더가 5초마다 때리는 유일한 상시 쓰기 경로다.

부하: VU 10 → 30 → 60 로 90초 램프(유지 구간 없음), think time 0. 계정은 VU 보다 많게 잡아
VU 당 라이더 1명이 배분되게 한다.

### 결과 (2026-08-10, 앱 컨테이너)

> **주의: 아래 수치는 `feature/401-waiting-sse-connection` 기준으로 측정했고, 그 브랜치에는
> `spring.threads.virtual.enabled` 가 없었다.** dev 는 가상 스레드가 켜져 있어 스레드 모델이
> 다르다. 특히 **"Tomcat 스레드 200 이 앱의 하드 상한"이라는 결론은 dev 에서 그대로 성립하지
> 않는다** — 가상 스레드에서는 요청당 플랫폼 스레드를 잡지 않으므로 200 개 풀이 한계로 작동하지
> 않고, 직렬화 지점은 Hikari 풀(10)로 옮겨간다. CPU 병목·요청당 왕복 수(MySQL 13 / Redis 5)는
> 스레드 모델과 무관하므로 유효하다. **dev 기준 재측정이 필요하다.**

**정본은 A** 다 — 배포와 같은 자원, VU 당 라이더 1명. B·C 는 비교용이다.

| 항목 | **A. 1GiB/2vCPU · 계정 100** | B. 1GiB/2vCPU · 계정 3 | C. 한도 없음 · 계정 3 |
|---|---|---|---|
| 처리량(평균 / 피크) | **3,749 / 4,660 req/s** | 3,992 / 4,687 | 7,625 / 9,309 |
| p95 / p99 | **48.8 / 61.6 ms** | 48.1 / 61.3 | 7.8 / 11.1 |
| 서버측 평균(Micrometer) | 4.80 ms | 4.81 ms | 2.61 ms |
| 실패 | 0건 | 0건 | 0건 |
| **앱 CPU** | **100% (2코어 만석)** | 100% | 37% |
| Hikari 활성 / **대기 최대** | 10/10 · **36** | 10/10 · 5 | 10/10 · 8 |
| Tomcat 처리중 스레드 최대 | 59 / 200 | 45 / 200 | 51 / 200 |
| GC | SerialGC · 정지 4.28초 | SerialGC · 정지 4.22초 | G1 · 정지 1.27초 |
| 힙 사용 / 상한 | 90 / 247 MiB | 84 / 247 MiB | 297 MiB / 2.36 GiB |
| **Redis 커맨드/요청** | **4.99** | 4.32 | 4.32 |
| MySQL 문장/요청 | 13.00 | 13.00 | 13.00 |

계정 수를 3 → 100 으로 늘렸을 때(B → A) 바뀐 것과 안 바뀐 것이 뚜렷하다.

- **처리량·지연은 거의 그대로**(-6%). CPU 가 여전히 먼저 막히기 때문이다.
- **Redis 4.32 → 4.99.** 계정 공유가 만들던 `saveIfNewer` 경쟁이 사라졌다 — 이론값 5.00 에
  붙었으니 사실상 모든 갱신이 이긴다. 앞선 "절반이 폐기된다"는 수치는 **측정 방식의 산물이었다.**
- **Hikari 대기 5 → 36.** 라이더마다 다른 행을 읽으니 버퍼풀 지역성이 떨어져 커넥션을 더 오래
  잡는다. 이쪽이 실제에 가까운 그림이다.
- Redis 키 `rider:location:*` 가 정확히 **60개**(= 최대 VU 수) 생겼다. VU 당 라이더 1명이
  실제로 배분됐다는 확인이다(계정 100개 중 60개만 쓰였다 — 여유분).

### 결론

- **배포 사이징에서 처리량을 제한하는 것은 CPU 다.** A·B 모두 2 vCPU 가 100% 로 붙고, 한도를
  없앤 C 는 CPU 37% 에서 처리량이 2배다. 이 API 는 스케일 아웃(인스턴스 추가)이 그대로 먹힌다.
- **포화점은 약 12 VU 다.** 15초 해상도로 본 처리량은 12 VU 에서 피크(4,660 rps)를 찍고 그 뒤
  VU 를 5배로 늘려도 늘지 않는다(4,100~4,300). 60 VU 는 지연만 키운다.
- **Tomcat 스레드는 한계가 아니다**(59 / 200). 이번에 지표를 켜서
  (`server.tomcat.mbeanregistry.enabled`) 확정할 수 있게 된 사실이다.
- **커넥션 풀은 만석이고 대기가 36 까지 쌓인다**(A). 다만 CPU 가 이미 100% 라 **풀만 키우면
  처리량이 늘어난다고 단정할 수 없다** — 확인하려면 `maximum-pool-size` 를 바꿔 한 번 더 재야 한다.
- **1GiB 에서는 JVM 이 G1 대신 SerialGC 를 고른다**(힙 247MiB). GC 정지가 90초 중 4.28초,
  벽시계의 4.8% 다. 사이징을 올리기 전에 이 항목을 먼저 보는 게 좋다.
- **그래도 지금 고칠 이유는 없다.** 실제 부하는 배송 1건당 0.2 req/s(5초 주기)라 3,749 req/s 는
  동시 진행 배송 약 18,700건에 해당한다. MVP 규모와 자릿수가 다르다.

### VU 를 어디까지 둘 수 있나

상한이 네 겹이고, **먼저 걸리는 것은 기술적 한계가 아니라 "의미"** 다.

| 상한 | 값 | 근거 |
|---|---|---|
| **의미 있는 상한** | **약 12 VU(포화), 관찰용으로 60** | 12 VU 에서 처리량 피크. 그 위는 처리량이 안 늘고 지연만 커진다 |
| 계정 수 | `RIDER_COUNT` | VU > 계정 수면 나머지 연산으로 라이더를 공유해 수치가 왜곡된다(스크립트가 경고를 찍는다). 시드는 재귀 CTE 기본 상한 1000 까지 |
| 앱 하드 상한 | **Tomcat 스레드 200**(기본값) | 500 VU 에서 정확히 200 에 붙었다. 초과 요청은 accept 큐(기본 100)에서 대기 |
| 부하 생성기 | 수천 VU (11코어/18GiB) | k6 는 VU 당 1~5MiB. 다만 앱과 같은 머신이라 k6 가 CPU 를 가져가 측정을 흐린다 |

실측(계정 500 · MAX_VU 500, 90초):

| | 60 VU | 500 VU |
|---|---|---|
| 처리량 | 3,749 rps | **2,811 rps** (-25%) |
| p95 / p99 | 48.8 / 61.6 ms | **167 / 199 ms** (3배) |
| 실패 | 0건 | **0건** |
| Tomcat 처리중 | 59 / 200 | **200 / 200 (만석)** |
| Hikari 대기 | 36 | 169 |
| GC 정지(90초 중) | 4.28초 | 7.44초 |
| 앱 컨테이너 메모리 | — | **671 MiB / 1 GiB** |

- **500 VU 에서도 에러가 0 이다.** Tomcat 이 거부하지 않고 큐에 세워 기다리게 한다 — 즉 과부하는
  실패가 아니라 **지연으로 나타난다.** 프론트 타임아웃 설정이 이 구간의 사용자 경험을 좌우한다.
- 스레드 200 개가 붙으면 컨테이너 메모리가 **1 GiB 의 67%** 까지 올라간다(스레드 스택 + 힙).
  `max-threads` 를 기본값 위로 올릴 때는 이 여유부터 확인해야 한다.
- 권장: 포화점 탐색은 `MAX_VU=60`, 한계·안정성 확인은 `MAX_VU=200`(스레드 상한과 같은 지점).
  그 이상은 새 정보가 없다 — 더 큰 부하를 의미 있게 재려면 **부하 생성기를 별도 머신으로** 빼야 한다.

### 실측: 요청 1건당 비용

문서(CLAUDE.md)에는 "MySQL 3회 + Redis 3회"로 적혀 있었다. 실제 왕복은 더 많다.
아래는 단일 라이더 200건 기준이고, 계정 100개 부하 측정(A)에서도 MySQL 13.00 / Redis 4.99 로 같았다.

| MySQL 문장 | 회/요청 | 정체 |
|---|---|---|
| SELECT | 3.00 | 문서의 3회(인터셉터의 member·rider_profile + 수행 중 배송) |
| COMMIT | 2.00 | 트랜잭션이 요청당 2개 |
| SET | 8.00 | 트랜잭션마다 autocommit·read-only 세션 설정/복구 |
| **합계(Questions)** | **13.03** | |

**13번의 왕복 중 10번이 트랜잭션 부대비용**이다. 줄이는 방향은 ① 인터셉터의 회원·프로필 조회를
한 쿼리로 합치기, ② MySQL 커넥션 속성(`useLocalSessionState` 등)으로 SET 왕복 줄이기 —
둘 다 이 경로 전용이 아니라 **모든 라이더 API 공통**이다.

| Redis 커맨드 | 회/요청 | 정체 |
|---|---|---|
| HGET | 1.00 | 세션 조회 |
| EVALSHA | 1.00 | 최신 위치 조건부 갱신(Lua) |
| GET + SET | 2.00 | 위 Lua 내부(Redis 는 Lua 내부 커맨드도 센다) |
| PUBLISH | 1.00 | SSE 팬아웃 채널 발행 |
| **합계** | **5.00** | |

### 부산물

- **조건부 갱신(`saveIfNewer`) 경쟁은 계정 공유가 만든 것이었다.** 계정 3개일 때 Redis 커맨드가
  4.32/요청(이론값 5.00)이어서 "절반이 폐기된다"고 읽었는데, 계정 100개로 늘리자 4.99 가 되어
  경쟁이 사라졌다. 라이더 1명당 기기 1대인 실제 운행에서는 이 경쟁이 사실상 없다고 봐도 된다
  (CLAUDE.md 미결 항목에 대한 답). 다만 같은 라이더가 기기를 두 대로 보내는 상황이 생기면
  **폐기가 아무 신호도 남기지 않는다**는 점은 그대로다.
- **알림 규칙이 실제 지표에 반응했다.** 첫 측정에서 `HikariPoolPending` 이 pending 까지 갔다
  (테스트 90초 < 규칙의 `for: 2m` 이라 firing 전에 종료).

### 측정 이력

1. **첫 측정** — 앱을 호스트 `bootRun`, 계정 3개: 2,287 req/s · Hikari 대기 36. 이걸 보고
   "커넥션 풀이 병목"이라고 결론지었다.
2. **앱을 컨테이너로**(B) — 대기가 36 → 5 로 떨어졌다. 첫 측정의 대기는 앱↔DB 가 Docker VM
   경계를 넘느라 커넥션을 오래 잡은 탓이 컸다.
3. **계정 100개로**(A) — 대기가 다시 36 이 됐다. 이번엔 원인이 다르다(라이더마다 다른 행을 읽어
   버퍼풀 지역성이 떨어짐). 우연히 같은 숫자가 나왔을 뿐이다.

**"커넥션 풀이 병목"이라는 첫 결론은 철회한다.** 세 측정 모두에서 처리량을 정한 것은 CPU 였다
(A·B 는 CPU 100%, C 는 CPU 37% 에서 처리량 2배). 요청당 문장 수 13.00 은 세 구성에서 모두 같았다.
