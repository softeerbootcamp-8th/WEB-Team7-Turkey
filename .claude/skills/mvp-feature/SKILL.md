# MVP 기능 개발 파이프라인

이슈 하나를 "구현 + 테스트 + 기록"까지 **한 사이클**로 끝내기 위한 스킬이다.

설계 문서를 먼저 쓰고 계획서를 쓰고 다시 구현하는 방식은 이 팀의 MVP 속도에 맞지 않는다.
그래서 이 스킬은 **문서를 앞에 두지 않는다.** 대신 순서를 이렇게 뒤집는다:

- 사람에게 물어볼 것은 **한 번에 모아서 한 게이트에서** 묻는다 (단계 2).
- 문서는 **끝나고 한 번** 쓴다. 이미 일어난 일과 사람이 고른 선택만 기록하므로 추측이 없다 (단계 6).
- 참고 문서(`references/`)는 **이번 이슈에 해당하는 것만** 읽는다. 백엔드 이슈에 프론트 규칙을 읽지 않는다.

`CLAUDE.md`의 규칙(금지 기술, 상태 전이, 확정된 결정)은 이미 컨텍스트에 있다.
여기 다시 옮기지 않았으니, 충돌하면 항상 `CLAUDE.md`가 우선이다.

## 단계 1 — 이슈 읽기와 범위 판정

`mcp__github__issue_read`로 이슈 본문·라벨·코멘트를 읽는다 (repo: `softeerbootcamp-8th/WEB-Team7-Turkey`).
이슈에 `Part of #N`, `Depends on #N`이 있으면 그 상위 이슈도 읽어 단계 분할 맥락을 파악한다.

읽은 뒤 **범위를 스스로 판정**한다. 이 판정이 이후 단계에서 무엇을 읽고 무엇을 건너뛸지 결정한다.

| 이슈에 나오는 것 | 범위 | 수행 단계 |
|---|---|---|
| 엔터티·마이그레이션·도메인 규칙만 (API 없음) | `domain` | 3 → 5(단위) → 6 |
| 엔드포인트·요청/응답·서비스 로직 | `backend` | 3 → 5(단위·통합·E2E) → 6 |
| 화면·라우트·버튼·표시 항목 + API | `fullstack` | 3 → 4 → 5(전부) → 6 |
| 화면만, 이미 있는 API 소비 | `frontend` | 4 → 5(E2E) → 6 |

애매하면 좁게 잡는다. 이슈에 안 적힌 화면을 상상해서 만들지 않는다.
이슈 범위를 벗어나는 게 옳아 보이면 구현하지 말고 단계 2의 질문으로 올린다.

작업 브랜치는 이슈 번호를 포함해 만든다: `feature/<이슈번호>-<영문-슬러그>`.
(단, 세션 시스템 프롬프트에 지정 브랜치가 있으면 그 브랜치를 따른다.)

## 단계 2 — 계약 확정 게이트 (사람에게 묻는 유일한 지점)

코드를 쓰기 전에 **결정해야 하는 것**을 정리한다. 목적은 두 가지다:
구현 도중 되돌리는 일을 없애는 것, 그리고 단계 6 문서에 들어갈 "사람이 고른 선택과 근거"를 확보하는 것.

먼저 **계약 초안**을 3~15줄로 짧게 제시한다. 문서 파일로 만들지 말고 대화에 직접 쓴다:

```
[#142 배송요청 생성]
POST /api/customer/deliveries  → 201, ApiResponse<DeliveryCreateResponse>
  요청: pickup/dropoff 주소·연락처, itemType, memo
  상태: WAITING 으로 생성. 고객당 진행 중 1건 제한 위반 시 409
  예외: 요금 정책 ACTIVE 없음 → 500 계열이 아니라 503 로 구분
프론트: customer/deliveries/new 의 DeliveryForm 을 생성 훅에 연결
```

그다음 **정말 갈리는 지점만** `AskUserQuestion`으로 묻는다. 한 번에 최대 3개, 이 게이트에서 끝낸다.
질문 하나마다 선택지에 **트레이드오프를 한 줄씩** 적어야 사람이 근거를 남길 수 있다.

물어볼 가치가 있는 것 (이 저장소에서 실제로 갈리는 것들):

- `CLAUDE.md`의 「확인이 필요한 항목」에 걸리는 주제 — 배차 동시성 제어 방식, 멱등성 키, 포인트 선차감 시점, SSE 재연결 정책 등
- 상태 전이·트랜잭션 경계가 두 가지 이상으로 설계될 수 있을 때
- 에러 응답 코드·정책이 이슈에 없고 기존 코드에도 선례가 없을 때
- 새 라이브러리·AWS 서비스가 필요할 때 (`CLAUDE.md` 규칙상 반드시 사람 확인)

물어보지 말 것: 관례가 이미 있는 것(패키지 위치, 네이밍, `ApiResponse` 래핑, 테스트 파일 위치),
이슈 본문에 이미 답이 있는 것, 되돌리기 쉬운 것.
**질문할 게 없으면 묻지 말고 진행한다.** 게이트의 목적은 의식이 아니라 되돌림 방지다.

받은 답변은 그대로 메모해 둔다 (질문 / 선택지 / 고른 것 / 사람이 덧붙인 말).
단계 6에서 이 메모가 문서의 핵심이 된다.

## 단계 3 — 백엔드 구현

`references/backend.md`를 읽고 그 규칙대로 계층을 만든다.
Repository → Service → DTO → Controller 순으로 쓰고, springdoc 어노테이션은 컨트롤러에 같이 단다.
DB 스키마 변경이 있으면 Flyway 마이그레이션을 **다음 버전 번호로** 추가한다 (기존 파일 수정 금지).

## 단계 4 — 프론트 API 연동

범위가 `fullstack` 또는 `frontend`일 때만 수행한다.
`references/frontend.md`를 읽는다. 요약하면: 백엔드를 local 프로파일로 띄우고 →
`pnpm generate:api`로 Orval 훅을 재생성하고 → 화면에서 그 훅만 소비한다.
`src/api/generated/`는 절대 손으로 고치지 않는다.

## 단계 5 — 테스트

`references/testing.md`를 읽는다. 세 층을 모두 쓰되, **범위에 해당하는 층만** 쓴다.

- **단위** — 도메인 규칙·상태 전이·계산. 스프링 컨텍스트 없이. 항상 쓴다.
- **통합** — 서비스 + JPA + 트랜잭션 경계. DB가 개입하는 정합성(동시성, 제약 위반)을 여기서 검증한다.
- **E2E** — 이슈의 「완료 조건」을 사용자 시나리오 그대로. 백엔드는 실제 HTTP, 풀스택은 브라우저.

정상 흐름만 쓰면 이 스킬을 쓴 의미가 없다. `CLAUDE.md`가 요구하는 대로
중복 요청·동시 요청·연결 종료·재시도·부분 실패 중 **이 기능에 실제로 일어날 수 있는 것**을 골라 테스트한다.

테스트는 반드시 **실행**한다. 실행하지 않은 테스트를 통과했다고 쓰지 않는다.
실패하면 실패 출력을 그대로 보고하고 고친 뒤 다시 돌린다.

```bash
cd backend && ./gradlew test          # 전체
cd backend && ./gradlew test --tests '*DeliveryOrderServiceTest'
cd frontend && pnpm typecheck
```

## 단계 6 — 작업 기록 문서

`assets/worklog-template.md`를 복사해 `docs/worklog/YYYY-MM-DD-<이슈번호>-<슬러그>.md`로 채운다.

이 문서의 존재 이유는 **나중에 "왜 이렇게 했더라"를 다시 캐지 않기 위해서**다.
그러니 코드를 읽으면 알 수 있는 것(클래스 목록, 메서드 시그니처 나열)은 쓰지 말고,
코드에 남지 않는 것을 쓴다:

- 단계 2에서 사람이 고른 선택과 그 이유 — **이게 문서의 본체다.** 고르지 않은 대안도 왜 탈락했는지 한 줄씩.
- 구현 중에 스스로 판단한 것 (사람에게 물을 만큼은 아니었지만 다르게 갈 수도 있었던 것)
- 이슈 범위에서 **일부러 뺀 것**과 그 이유
- 새로 생긴 미결 사항 → 동시에 `CLAUDE.md`의 「확인이 필요한 항목」에도 한 줄 추가한다

문서는 이슈당 하나다. 같은 이슈로 다시 작업하면 새 파일을 만들지 말고 기존 문서에 이어 쓴다.

## 단계 7 — 커밋과 마무리

`CLAUDE.md`의 협업 규칙을 따른다. 커밋 메시지에 이슈 번호를 넣고,
기능과 무관한 포맷팅·파일 이동을 섞지 않는다.

```
feat: 배송요청 생성 API 구현 (#142)
test: 배송요청 생성 단위·통합·E2E 테스트 (#142)
docs: 배송요청 생성 작업 기록 (#142)
```

푸시는 지정 브랜치로 `git push -u origin <branch>`.
**PR은 사람이 명시적으로 요청할 때만 만든다.** 만들 때는 `.github/PULL_REQUEST_TEMPLATE.md` 구조를 채운다.

마지막에 사람에게 보고할 것: 만든 엔드포인트, 테스트 결과(실제 출력 기준), 기록 문서 경로,
그리고 **이슈에서 빼놓은 것**. 빼놓은 게 있으면 반드시 말한다.

## 이 파이프라인에서 하지 말 것

- `docs/superpowers/` 아래 계획서·설계서를 새로 만드는 것 — 이 스킬은 그 방식을 대체한다
- 이슈에 없는 기능을 "있으면 좋을 것 같아서" 덧붙이는 것
- 사람 확인 없이 새 라이브러리·AWS 서비스를 추가하는 것
- `src/api/generated/`, `routeTree.gen.ts` 같은 자동 생성물을 손으로 고치는 것
- 테스트를 나중에 몰아서 쓰겠다고 미루는 것 — 층별로 구현 직후에 쓴다
- 정합성이 중요한 코드(배차·포인트·상태 전이·정산)를 단위 테스트만으로 끝내는 것
